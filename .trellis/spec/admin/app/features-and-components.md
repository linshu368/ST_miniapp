# Admin 功能与组件规范

## 功能地图

1. **鉴权与工作区**：`LoginPage` 获取运营会话；`App`/工作区控制导航、退出和环境。
2. **运行时配置**：配置读取、编辑草稿、Zod 校验、发布、查看历史与回滚；专题编辑器只负责本领域值。
3. **模型与回复长度**：模型目录、价格/能力配置和拖拽排序；档位必须保持唯一、顺序和边界合法。
4. **角色卡运营**：创建、布局、上下架、软删除/恢复、排序与版本管理。
5. **公告**：列表、创建/修改、发布状态和删除。
6. **邀请裂变**：邀请中心/奖励规则配置及邀请关系查询。
7. **回访赠送**：按明确用户标识赠送星尘，属于高风险计费写操作。

## 组件契约

- 编辑器 SHOULD 采用受控 `value/onChange/disabled`，父层拥有草稿和保存生命周期；不得同时维护未同步的第二份配置真相。
- 请求状态至少区分初始、loading、success、empty、error；mutation 期间禁用重复提交。
- Modal/Drawer 关闭前处理未保存修改；破坏性操作必须展示对象、环境和后果并二次确认。
- Table 的 row key 必须稳定；排序结果必须由稳定 ID 表达，禁止用展示名称充当身份。
- 组件不可直接解释数据库列或 Supabase 原始错误，应消费 helper 返回的领域结果。

## 高风险写操作

发布、回滚、赠送、删除/恢复、上下架均 MUST：

1. 在 UI 中明确目标环境与对象；
2. 防重复点击；对后端可重试写入要求 idempotency 由契约明确支持，前端不得盲重试；
3. 成功后刷新权威数据而非只做永久乐观假设；
4. 失败保留用户输入并显示可行动错误；
5. 设计中说明审计、补偿或人工恢复路径。

## 规划门禁

复杂功能 design 必须回答：现有哪个组件/helper/schema 可复用；状态真相在哪里；环境切换如何隔离；外部依赖失败、并发提交、超时和部分成功如何处理；最小新增 API/文件是什么；如何兼容和回滚。无真实故障场景时，不添加通用重试、缓存或全局状态框架。
