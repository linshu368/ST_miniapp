# Admin UI、状态与校验规范

## UI 与状态

- 优先 Ant Design 现有组件与 token；不要并行引入第二套组件库。
- server/session 数据、编辑草稿、瞬时 UI（Modal、选中项）必须分开命名和管理；派生数据用纯函数计算，不复制为可变 state。
- 状态优先靠近使用者；只有多个远层组件共享且生命周期一致时才提升。不得仅为减少 props 引入全局状态库。
- 异步 effect 必须处理卸载、环境变化和竞态；旧环境响应不得覆盖当前视图。

## 运行时校验

- 不可信 JSON、运营配置和 provider 返回值在边界用 Zod 校验；仅 TypeScript 类型不能替代运行时校验。
- 复用 shared schema/default；Admin 专用表单 schema 放 `lib/configSchemas.ts`，不得与保存端规则悄然分叉。
- 展示字段错误并保留输入；发布前必须进行完整对象校验。数字处理 NaN、范围、精度和货币单位；列表处理唯一键与稳定顺序。

## 可用性与可访问性

- 表单控件必须有 label/说明/错误关联；图标按钮提供可访问名称。
- 不只依赖颜色表达状态；loading 不应造成布局跳变，空态与错误态需可重试。
- 键盘可操作 Modal、Drawer、拖拽排序（至少提供替代上/下移动能力）；焦点关闭后回到触发点。
- `styles.css` 使用语义类和响应式规则；避免脆弱的 AntD 内部 DOM 选择器和无说明 `!important`。

## 简洁与复用

- 复用稳定的受控编辑器、校验与纯函数，不抽取只有一个调用者且无独立职责的 wrapper。
- 新组件 props 保持最小且领域化；避免将整个 App state 或 client 透传。
- 可读的显式分支优于高度参数化的“万能表单”；新增依赖需记录 bundle、维护和安全成本。
