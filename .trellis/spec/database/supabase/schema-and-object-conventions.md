# Schema 划分与对象约定

本规范用于决定新增表、视图、物化视图和数据库函数应进入哪个 schema。先按业务不变量确定归属，再设计对象和 migration；不得因为现有代码访问方便、某个页面使用它，或为了避开权限配置而选择 schema。

## 八域地图

按现有迁移和 schema 拆分资料，MiniApp 业务域包括 `app_core`、`miniapp_features`、`experience`、`billing`、`admin`、`cs_platform`、`miniapp_traffic`、`miniapp_analytics`。`public`、`graphql_public`、旧 `analytics`、`miniapp` 的实况和兼容用途必须通过目标环境核验，不凭历史文档推断。

| Schema              | 负责的业务真相                                                       | 典型对象                                     |
| ------------------- | -------------------------------------------------------------------- | -------------------------------------------- |
| `app_core`          | 多个业务域共同依赖、不会随单个功能下线而消失的根实体和运行时全局配置 | 用户、用户长期偏好、角色卡、运行时配置       |
| `miniapp_features`  | MiniApp 某个具体产品功能产生的状态或运行时投影                       | 收藏、签到、许愿、通知、排行榜分数           |
| `experience`        | 用户核心互动产生的内容及其处理状态                                   | 文本会话、消息历史、语音与图片产物           |
| `billing`           | 金钱、余额、计费、免费权益及其审计和幂等事实                         | 支付订单、钱包流水、余额、用量扣费、免费额度 |
| `admin`             | 运营平台自身的账号、草稿、发布过程和操作审计                         | 运营账号、配置草稿、发布快照、运营审计       |
| `cs_platform`       | 客服业务、用户画像、人群和主动触达                                   | 站内客服、回访人群、触达会话、客服审计       |
| `miniapp_traffic`   | 渠道投放、入口点击、邀请关系与归因                                   | 投放链接、点击、邀请码、邀请关系和奖励记录   |
| `miniapp_analytics` | 只用于分析、报表和离线指标的派生数据                                 | 分析视图、漏斗、留存、LTV、历史快照          |

对象清单和数据库实况会演进；具体表名以当前源码、migration、`docs/ARCHITECTURE.md` 和经确认的目标环境为准。本表定义的是稳定的归属边界，不证明某张表已经部署。

## 新对象归属判定流程

新建对象前依次回答以下问题，命中后停止；不能明确回答时不得先建表再补归属说明。

1. **它是否记录金额、余额、扣费、退款、免费权益或相关审计/幂等事实？** 是则进入 `billing`。支付金额以订单为准，星尘变化以流水为准，钱包余额是可重建的当前投影。
2. **它是否保存用户核心互动内容或互动产物？** 文本对话、语音、图片及其生成处理状态进入 `experience`。
3. **它是否由独立后台平台拥有？** 运营人员的账号、草稿、发布和审计进入 `admin`；客服会话、画像、人群与触达进入 `cs_platform`。被运营平台编辑不等于归 `admin`：角色卡和已发布运行时配置仍是 `app_core` 的产品运行真相。
4. **它是否描述渠道、投放、点击、邀请或归因？** 是则进入 `miniapp_traffic`。用户最终归属的渠道字段可以留在 `app_core.users`，渠道资产和过程事实归 `miniapp_traffic`。
5. **它是否只用于看数，且产品运行时不读取？** 是则进入 `miniapp_analytics`。如果结果会驱动线上功能，例如大厅推荐分数，它是产品运行状态，应进入 `miniapp_features`。
6. **它是否是跨多个领域共享的根身份、长期状态或全局运行配置？** 是则进入 `app_core`。
7. **它是否随某个具体 MiniApp 功能一起上线、关闭或删除？** 是则进入 `miniapp_features`。
8. 仍无法判定时，在任务的 `design.md` 中列出候选 schema、业务不变量、权威写入方、运行时消费者、生命周期和跨 schema 依赖，完成评审后再创建 migration。不得新建兜底 schema，也不得放入 `public`。

### `app_core` 与 `miniapp_features` 的最终判断

用“功能删除测试”判断最容易混淆的边界：

> 删除某个具体功能后，对象作为多个领域共同依赖的根数据仍必须存在，则属于 `app_core`；对象可以随该功能一起删除，则属于 `miniapp_features`。

辅助判断如下：

| 判断维度 | `app_core`                       | `miniapp_features`           |
| -------- | -------------------------------- | ---------------------------- |
| 数据性质 | 用户、角色等根实体和全局运行配置 | 收藏、签到、通知等功能状态   |
| 依赖范围 | 多个业务域共同依赖               | 单个或少数产品功能依赖       |
| 生命周期 | 长期存在，不跟随单个功能开关     | 跟随具体功能上线和下线       |
| 典型增长 | 相对稳定的主数据                 | 随功能使用持续增长或周期刷新 |

角色卡属于 `app_core`，因为对话、额度、收藏、大厅、分析和运营管理共同引用它；收藏关系属于 `miniapp_features`，因为收藏功能下线后该关系可以删除。

## 同一流程跨 schema 的拆分原则

归属按每个对象维护的业务真相判断，不按“它们出现在同一个用户流程”归堆。一个流程可以安全地跨多个 schema：

- 签到行为记录属于 `miniapp_features`，由签到发放的星尘变化必须进入 `billing.wallet_ledger`。
- 运营配置的草稿、发布记录和审计属于 `admin`，发布后供产品运行读取的配置真相属于 `app_core.runtime_config`。
- 渠道链接、点击和邀请过程属于 `miniapp_traffic`，用户身份和最终渠道归属字段可以属于 `app_core.users`。
- 分析报表和离线快照属于 `miniapp_analytics`；若某个计算结果被线上请求直接读取并决定产品行为，应迁回拥有该功能状态的运行时 schema。

跨 schema FK、函数、视图、触发器或事务会扩大权限和发布耦合，必须在设计中列出方向、失败行为、RLS/grant 和回滚顺序。不要为了减少跨 schema 引用而复制权威数据。

## 新建表前的必填说明

涉及新表的 `prd.md` 或 `design.md` 至少记录：

1. 建议的 `schema.table` 与一句话业务含义；
2. 该表维护的业务不变量和权威写入方；
3. 采用上述判定流程得出的归属理由，尤其是 `app_core`/`miniapp_features` 边界；
4. 生命周期：是否随功能下线、是否允许删除、历史数据保留要求；
5. 运行时读写消费者，以及产品运行是否依赖该表；
6. 跨 schema FK、函数、视图、触发器和事务依赖；
7. RLS、grant、索引、容量、迁移顺序和回滚/forward-fix；
8. 是否已有同一业务真相的表或投影，如何避免双写和双重事实源。

评审时若无法用一句话说清“这张表维护什么真相、为何由该 schema 拥有”，视为归属未完成。

## 对象规则

- 新表/函数进入拥有该领域不变量的 schema；禁止为规避权限或 import 边界堆入 `public`。
- 视图、物化视图和函数默认跟随其业务用途或维护的不变量，不因主要来源表位于另一个 schema 就自动跟随来源表。
- 不得为了一个新功能创建新的 schema；扩展八域需要单独的架构决策、权限模型、迁移顺序和回滚方案。
- 表/列/function 使用 snake_case；PK/FK/unique/check/index/policy/trigger 显式命名，便于诊断和回滚。
- PK 类型与 FK 完全一致；FK 说明删除/更新策略并为高频连接列评估索引。
- `timestamptz` 表达绝对时间；金额/credits 明确单位和精度；状态优先 check/enum 并规划演进。
- `NOT NULL`、default、check 应表达数据库不变量；新增非空列需处理历史数据并避免长锁。
- 表、关键列、函数和非常规索引 SHOULD 有 comment，描述业务语义、单位和限制，不写 secret。
- view/materialized view/function 必须有所有者、依赖和刷新/安全语义；跨 schema 依赖在设计中列出。

## 可靠性与简洁性

事务只包裹必须原子化的最小写集；关键钱包/奖励写入评估幂等键和并发冲突。索引基于查询与 explain 证据，不为所有列预建；触发器/RPC 仅在数据库必须维护跨写一致性时使用，避免隐藏业务流。
