# Trellis 功能模块知识库与归档同步规划

## 目标

在 `.trellis/spec/` 中建立按 package、功能模块可检索的“当前实现知识库”，并把知识同步纳入 Trellis 任务归档门禁，使后续任务规划能读取可信的模块现状，而不是重复从全仓库猜测。

## 需求

### 模块知识文件

- 覆盖 `frontend`、`backend`、`admin`、`cs-platform`、`shared` 五个 workspace package；数据库能力沿用 `database/supabase` 独立域，workspace 外 `botlink` 作为后续可选范围，不伪装成 package。
- 每个可独立演进、可独立验收的功能模块使用一个 Markdown 文件；业务能力按业务功能拆分，基础设施、公共组件/工具、跨模块公共能力必须与业务文件分开。
- 每个文件至少描述：模块职责与边界、当前状态、用户/系统入口、涉及文件路径、关键实现调用链、数据/契约/外部依赖、关键节点与约束、验证入口、已知缺口。
- “关键节点”描述当前实现中的稳定决策、风险点和重要状态，不把完整任务流水账复制进模块文件；历史证据可链接已归档任务。
- package 模块目录必须有索引和分类，能区分 `business`、`infrastructure`、`shared`；跨 package 功能允许各包分别描述本包实现，并由总索引链接，禁止制造第二份互相竞争的事实源。
- 功能文件只描述仓库当前事实，不替代现有编码规范；无法由源码、测试、迁移或已验收文档证明的内容必须标为待核验。

### 任务声明与归档同步

- 新任务规划时必须声明涉及模块；若新增模块，先声明稳定模块 ID、归属 package、分类和目标文件。
- 实施完成后，任务必须提供结构化的模块变更清单，明确每个模块是 `create`、`update`、`rename` 或 `delete`，并记录证据路径和更新后的当前状态摘要。
- `task.py archive` 必须在移动目录和归档自动提交之前运行同步与校验；同步失败、声明缺失、路径越界、内容不完整或实际改动与声明明显不一致时，归档失败且任务保持原位、状态不变。
- 归档流程只能确定性地应用任务中已审核的结构化内容，不能在无 AI/无人工审核的 hook 中根据 diff 自由生成业务描述。
- 无模块影响的任务必须显式声明 `no_module_change` 及理由；不能用空文件或遗漏绕过。
- 自动同步应支持补充、改写、重命名和删除过时模块内容；删除必须确认模块实现已不存在或被替代，并保留归档任务作为审计证据。
- 更新结果与归档任务必须进入同一归档提交；不得沿用当前“归档提交完成后才执行 `after_archive` hook”的顺序来写 spec。

### 正确性与可恢复性

- 同步操作必须先校验后写入，使用临时文件/原子替换；任一步失败不得留下半更新 spec 或半归档任务。
- 重复执行必须幂等；并发归档必须通过仓库级锁或等价机制避免同时改写同一索引/模块。
- 提供 `check`/`dry-run` 模式，用于 CI 和归档前预览；输出仅包含路径、模块 ID、操作与错误摘要，不输出 secret 或业务数据。
- 首次上线需要从当前源码建立基线并人工审核；不能仅靠历史任务反推当前状态。
- 兼容存量任务：启用日期之前创建的任务可通过显式 legacy 豁免归档；启用之后的新任务必须使用新声明，豁免要可审计且不可永久默认开启。

### 人工审核与 Git 安全门禁

- 所有 Trellis 工作产生的新增、修改、删除文件必须在最终内容和验证完成后由人工审核；系统需展示变更路径、diff/摘要、验证结果和拟提交清单。
- 未取得人工明确确认前，任何 Trellis 命令、hook、任务归档、session/journal 工具或 AI 都不得执行 `git add`、`git commit` 或等价提交操作。
- 人工确认只对当次展示的内容摘要和文件集合有效；确认后内容或范围变化必须重新审核确认。
- 归档同步完成后先停在工作区供审核，再由人工明确确认提交；模块更新与任务归档仍应作为同一逻辑提交批次，但不能由 archive 自动提交。
- 禁止自动 `git push`。即使人工已确认并完成 commit，push 仍需另一次明确人工授权或由人工自行执行；commit 授权不得推定为 push 授权。
- 在自动提交能力完成改造前，所有任务归档强制使用 `task.py archive <task> --no-commit`，并关闭 `session_auto_commit`，避免现有 archive/journal 自动提交绕过审核。

## 约束

- 本任务只产出规划，不修改产品代码、Trellis 运行脚本或模块知识基线。
- 不引入数据库、网络服务、向量库或新的运行时依赖；优先复用 `task.json`、任务目录、`task.py archive` 和现有 spec package 入口。
- Markdown 以中文编写；路径使用仓库相对路径；不得写入环境变量值、业务行数据、token 或个人信息。
- 上游 Trellis 代码视为受保护：实现时以小范围项目扩展为主；若必须修改通用 `task.py` 归档顺序，保留现有行为并增加回归测试，不顺手重构。

## 验收标准

- [ ] 给出五个 workspace package 与 database 域的目录约定、模块分类、命名规则、单文件模板和索引方案。
- [ ] 给出首批模块盘点与基线生成/人工审核策略，明确公共基建和业务模块如何拆分。
- [ ] 给出任务侧结构化影响声明与模块更新载荷格式，覆盖 create/update/rename/delete/no-change。
- [ ] 给出归档事务顺序，保证“校验与同步 → 归档移动 → 同一批提交”，失败时不改变任务状态和目录。
- [ ] 覆盖幂等、并发、原子写、路径安全、误删防护、存量兼容、CI 检查、日志和恢复方案。
- [ ] 归档和 session/journal 等 Trellis 路径均不能自动提交或推送；最终变更必须经人工审核并明确确认，且确认与最终摘要绑定。
- [ ] 明确新任务规划如何发现和注入模块知识，且不会把功能事实与编码规范混为一谈。
- [ ] 实施计划包含自动测试、失败路径、人工抽检、可执行命令、灰度启用与回滚/forward-fix。
- [ ] 规划通过 `task.py validate`，且 `implement.jsonl`、`check.jsonl` 含真实规范/研究上下文。

## 非目标

- 不在本次规划中撰写所有现有功能模块的最终基线正文。
- 不依赖大模型在 archive 命令执行期间自动阅读并改写文档。
- 不把模块文件做成版本发布日志、代码所有权系统或精确到每个源文件的自动架构图。
