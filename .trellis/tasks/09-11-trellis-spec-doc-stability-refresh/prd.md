# Trellis 规范与系统文档稳定性重整

## 目标

在不改动产品行为的前提下，以近期提交和当前实现为证据，重新对齐项目文档、Trellis spec、模块知识与工作流门禁，降低后续 AI/人工开发引用过时规则的风险。

## 需求

- 建立一份带 commit、代码和配置来源的系统事实基线，区分现行事实、历史留档、待办和未知项。
- 按“事实审计 → spec/module 同步 → 根文档/流程收口”顺序执行三个子任务；前一阶段结论需经审核后才能成为后一阶段输入。
- 修复近期 P1/P2/P3/R1/R2/R3、ST/botlink 退场、迁移账本与 legacy guard 变化造成的文档漂移。
- 复杂方法、业务编排、非显然约束、关键状态转换和边界处理应尽量补充解释“为什么”的必要注释；简单且自解释的方法无需注释，禁止机械复述代码。
- 默认不因新增或修改代码而自动创建测试文件；只有用户明确要求、规划/验收标准确认需要，或确认某风险必须用回归测试锁定时才创建。该规则不得弱化 typecheck、lint、现有相关测试、构建、静态检查和人工回归。
- 保留专项强制注释与验证要求，例如 `@frontend-ready`、迁移头注释、数据库对象注释和生产迁移验证。
- 不修改历史已执行 migration，不把历史文档重新包装成当前事实，不改产品代码或数据库。

## 验收标准

- [ ] 三个子任务都有独立 PRD、设计、实施计划、任务分解和上下文清单，并明确依赖顺序。
- [ ] 所有已识别的 P0 漂移被修正：迁移命名/账本、ST 与 `LLM_PROXY_TOKEN_SECRET` 现行配置误述、已删除 st-bridge/旧模型档位等。
- [ ] package spec、module spec、README、ARCHITECTURE、重构实施方案之间不存在已知的现行事实冲突或失效链接。
- [ ] implement/check agent、Cursor inline check、workflow/process 与包级 spec 对注释和测试策略表达一致。
- [ ] 新测试文件采用“先确认必要性再创建”，但受影响范围验证仍有可执行命令或可重复人工场景。
- [ ] 完成全局关键词漂移扫描、Trellis task validate、module knowledge check、Markdown 格式检查；无法执行项记录原因和风险。
- [ ] 每个子任务分开审核、实施和提交，最终由父任务进行跨子任务集成复核；不自动提交或推送。

## 约束

- `docs/ARCHITECTURE.md` 是当前候选事实基线，但仍必须用实现、配置和 commit 交叉核验，不能无条件反向覆盖代码事实。
- test 与 production 不保证同构；本任务不读取业务行，也不以 test 结论替代 production。
- 上游变更只读；若执行期间合入 `origin/dev`，保留上游行为，仅调整本任务文档。
