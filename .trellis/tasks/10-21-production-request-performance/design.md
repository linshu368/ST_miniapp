## 四主线设计边界

- L 首载：先测无缓存真实关键路径，优先有界请求与排序刷新合并，不默认分页/全量 UI 重写。
- N 进入会话：新建与继续历史分开；复用 POST 回填避免额外阻塞，缩短 ready 后开屏等待，不预创建会话。创建结果未知的恢复在实施前审核，禁止无幂等保证自动重发。
- S 消息回复：准备期复用同轮只读快照，首正文/流速/终态分别判定；不换模型或缩短输出冒充性能收益。
- C 连接治理：提升为 P0-C/P1-C 核心项，明确容量表、后台工作约束、专用连接异常清理及饱和恢复；P2 仅承载有证据的深度 SQL/部署优化。共享池不宣称天然优先级隔离。

## 可靠性门禁

- 超时：browser/proxy/body 纳入总预算；AI 复用 deadline，补 signal 传播而非只 Promise race。
- 重试：仅安全读、瞬时失败、预算充分时有限退避加抖动并尊重限流；生成/预留结果未知不得盲重试。
- 幂等与并发：不把 HTTP abort 当回滚；保留用户唯一约束、会话锁/CAS、charge id、预留释放和恢复。
- 事务：不跨 LLM 流持锁；排序事务级锁与聚合/落表必须同连接。
- 降级：允许有界旧排序/配置及失败 UI；不降级鉴权、钱包/额度或计费快照。
- 补偿：关键写入超时查真实状态，未确认释放不得解禁；沿用结算恢复，不建第二套账。
- 限流/容量：计入 API 副本、Worker、滚动发布、直连与 pooler 两层预算；不默认扩容。
- 可观测性：复用 pino/requestLogger；只记阶段和安全计数，失败率与延迟同时比较。
