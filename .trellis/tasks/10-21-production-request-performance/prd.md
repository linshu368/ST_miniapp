# 大厅首载、进入会话、消息回复与连接治理规划

## 目标

形成可审核的 Markdown 排查及优化对比文档，仅聚焦高影响模块，不立即实施优化。规划须纳入 **Sentry 生产延迟证据**（E18），把已归纳的慢问题排进可执行批次。

## 需求与约束

- R1：围绕大厅列表初次加载慢、点击列表进入会话卡顿、发送消息后回复慢三个生产反馈，分别定义用户等待链路，区分源码事实、用户反馈、历史记录和待验证假设。
- R2：覆盖连接池耗尽、锁等待、后台任务竞争与页面持续加载的排查方法。
- R3：给出优化前后对比、优先级、最小改动范围、失败路径、验收及回滚。
- R4：不得削弱鉴权、资源归属、额度预留、计费快照、CAS 和幂等恢复。
- R5：本轮仅改文档，不执行生产写入/配置变更、迁移、压测或 AI 生成；不新增依赖或测试文件。
- R6：生产未知项保持待验证，不能把 TEST、本地网络样本或官方默认参数当生产基线。
- R7：Prisma 连接易满、影响其他请求是核心治理项；覆盖连接层级、资源预算、后台竞争、异常释放和负载回落恢复，不能仅列为后置调参建议。
- R8：首次加载不能用缓存命中冒充提速；进入会话区分新建/继续历史；回复速度覆盖首正文、流中停顿与完整回复，不削弱输出质量与业务正确性。
- R9：**Sentry 归纳必须进入规划批次**：以 `wangqiao/st-miniapp` production 近 7 天 traces/issues 为 `SENTRY` 证据（主文档 E18）。至少覆盖并排期：
  - L：`GET /api/characters` p95 长尾、`/` pageload、`/chats` N+1 API（ST-MINIAPP-1Y）、latest-badge / favorites 长尾；
  - N：`GET /api/characters/:id` 高频长尾与 N+1 Query（ST-MINIAPP-3M）、`/chat/:characterId` pageload；
  - S：messages 路径 Consecutive HTTP（ST-MINIAPP-2G）；LLM 总耗时与可优化准备期分段报告；
  - C：Supabase REST ≈300s 慢调用（users / current_chat_history / runtime_config）与 Prisma 池分层治理；
  - 旁路：webhook / miniapp-entry 记入 P2-X，不阻塞四主线。
- R10：Sentry 采样与丢弃未单独审计时，不得把单次聚合写成唯一根因；改后须同查询窗口对照，并保留分段观测门禁。
