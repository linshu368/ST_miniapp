# 首 token 超时兜底与体验数据基建

## 目标与价值

减少用户发出请求到第一个 token 在界面出现的总等待，建立可追踪的首发、兜底与用户体验事实。先由负责人每 24 小时查看过去 24 小时数据、人工调整阈值，为后续判断机制保留可靠数据与既有配置入口。

## 已确认背景与边界

- 型号可在运营平台增删；同一型号的近期表现会变化。型号兜底等待默认4000ms。
- 用户最终确定全局首token总等待上限为6000ms，超时率目标为1%；两项只由人手动调整，型号调参不能改变。
- 兜底供应商为 OpenRouter，默认 `deepseek/deepseek-v4.1-flash-1017`，型号可在统一运营界面配置；复用现有凭据，不新增或复制 key；不额外控制思考模式，沿用型号默认行为。
- 每个型号过去 24h 不足 150 个独立请求，不具备未来自动调节资格；本期仅展示资格和事实，所有阈值调整由人决定。
- 用户只关心首个 token 出现，不等一段正文，不以整条回复完成时间评价本需求。
- 厂商 latency 与业务实测必须同时保留；差异用于定位工程链路和统计口径问题，厂商值不能替代用户体验。
- 2026-10-23 本轮用户明确确认：兜底成功沿用所选型号的原价格与免费权益，一轮只结算一次。
- 当前分支 `feat/first-token-fallback` 基于 `origin/dev`（1cf7d68e）；工作模式 `codex.dispatch_mode=inline`。

## 需求

### R1 型号配置

扩展现有模型目录：旧型号缺字段与新增型号都默认 4 秒；运营可手动编辑并经既有草稿、发布、历史恢复生效。一次请求冻结该型号及目录版本、当次阈值，不随中途配置改变。

### R2 固定首 token 兜底

阈值从首发向上游派发开始计时；响应头、心跳、角色、空增量与未展示的 reasoning 不算首 token。阈值内收到首个回复内容 token 则持续交付首发；超时仅启动一次固定兜底，并不可逆地选择兜底交付。切换后首发晚到内容不会混入用户回复，无交付竞速、无递归兜底。首 token 后断流沿用现有失败处理；本期不扩展其他错误重试策略。首发已是固定兜底型号时不重复派发相同型号，明确标记不适用。

### R3 完整尝试事实

即使首发被替代，也继续有界观察到其首 token 后停止；观察不阻塞兜底交付和收尾；用户6秒内仍未见交付token时终止两次尝试。兜底已经及时出token的请求，首发可继续有界观察至其首token，但不超过本轮既有110秒总预算。两次调用独立保留身份、派发、响应头、首 token、停止原因和厂商允许的统计。超时截断、上游错误、取消、进程中断、缺报均明确表示，未知不是零。

### R4 用户体验与工程耗时

send/regenerate 共用客户端单调计时，从用户提交本次请求到首个 token 已进入可见回复 DOM 并经过绘制机会。记录测量方法与前后台/可见性，客户端缺报不由服务端或厂商值补造。
分别保留：首发阶段占用、切换处理、兜底实测首 token、用户总等待，以及各调用厂商 latency/单位/来源。被替代首发后来的实测耗时独立保存，不重复相加。前置准备、网络、持久化、解析和显示的可测阶段及残差用于排障；不伪称能够跨机器精确拆分所有网络时间。

### R5 单次账务与取消

保留一个 chargeId、一次权益预留及所选型号的受理报价；仅最终交付调用进入既有结算与 provider 回捞。观察尝试没有用户扣款资格。显式取消停止两次尝试，取消/失败不扣费与额度释放规则维持。进程恢复不自动重发生成 POST，不用迟到观察结果覆盖业务取消或终态。

### R7 全局首 token 截止与体验超时率

新增由人手动设置、对所有型号与首发/兜底共同生效的首 token 总等待上限6秒（6000ms）。此上限从用户提交本次请求起累计，切换兜底不重置；首个 token 已显示后停止该首 token 计时，不把它改成整条回复时限。到点仍未见 token，显示温馨重试提示，记录全局首 token 超时并停止剩余尝试；结合既有取消确认/终态保护安全提供重试。
全局6秒上限和可接受超时率1%独立于每型号的兜底启动阈值，均由人手动调整；未来AI不得修改。1%是人工验收与监控目标，不是对不可控上游的代码保证。按型号与全局返回明确分母、窗口和覆盖率的超时率，失败、主动取消与缺报单列。
固定其他条件时，降低全局截止时间会提高或维持超时率；降低型号兜底启动阈值则可能更早得到兜底。两种调整不可混淆。

### R6 人工分析与 Grafana 接口

提供显式起止 `[from,to)` 的请求级投影及按型号聚合（默认使用者查过去24h），并交付可复用 SQL/Grafana 导入配置，不直接修改生产看板。
独立请求去重后统计型号总体是否满150，再按实际阈值、目录版本、provider/model 映射分组。返回请求量、兜底启动/选择/用户确认显示比例及其分母、用户总等待 P50/P90/P95 与样本数、主/兜底分组、首发占用/兜底耗时、被替代首发后来首 token 分布、厂商与实测对照、失败/取消/删失/未知/缺报数和覆盖率。

## 范围外

AI 调用、Prompt、智能调参算法、自动改配置、每日调参定时任务；模型质量评分、用户界面重做、整条回复完成时间指标、真实上游压测；自动 commit/push、生产迁移与部署。

## 验收标准

- AC1：旧 JSON、新增型号、编辑保存/发布/恢复均保留合法阈值，缺省为4000ms；非法值在前后端与SQL校验一致拒绝。（R1）
- AC2：阈值前/边界/后只选择一个交付来源；固定兜底最多一次；首发晚到不输出、不结算、不改变用户终态。（R2,R3）
- AC3：首发与兜底的 generation ID、模型、精确首 token 或未知下界均可追踪，无现有一对一 provider 身份冲突。（R3,R5）
- AC4：发送/重生成均记录客户端首 token 显示总等待；空片段/光标/等待提示不触发；短回复、离屏/隐藏、取消和缺报可区分。（R4）
- AC5：正常/免费/VIP/余额不足、切换、断流、取消、恢复均维持一次原价结算；观察调用无用户扣费路径。（R5）
- AC6：首发占用与后台观察值不混淆；阶段耗时有同钟来源，厂商数据有单位/口径，不用成功样本/零值伪造分布。（R3,R4）
- AC7：149/150、同日多阈值、两attempt去重、NULL/删失/取消/缺报与客户端覆盖率的24h报表可重复验证。（R6）
- AC9：首发/兜底共同使用6000ms预算，切换不重置；只有交付token显示能停止该计时，观察首发的迟到token不能解除用户截止；到期温馨提示重试并记超时。1%目标和全局上限不随型号阈值改变。（R7）
- AC8：受影响既有测试、跨包 typecheck、适用 build、迁移与权限验证完成；无法运行的真实环境检查明确记录。（全部）
