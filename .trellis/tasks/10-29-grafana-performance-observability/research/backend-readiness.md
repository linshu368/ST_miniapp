## 2. Critical: current request/attempt storage is business state

`GenerationObservationRepository` is not merely an analytics sink:

- `begin()` freezes request identity and may persist the authoritative billing snapshot before upstream dispatch (`features/conversations/generate.ts:293,395`).
- `selectDelivery()` persists the winning attempt/generation identity; `execute.ts` returns/uses `deliveryPersisted`.
- `checkpoint()` calls `record_chat_delivery_preview`, saving a bounded first-token preview for recovery. Migration `20261027_recoverable_chat_delivery.sql:24` explicitly describes it as recovery state, not an analytics payload.
- `report()` calls `report_chat_first_token`; migration `20261028_client_committed_first_token.sql` records the one terminal receipt and releases a genuine failed-delivery free-round reservation in the same transaction.
- `billing.chat_delivery_billing_gate` (`20261027_recoverable_chat_delivery.sql:114`) reads `chat_generation_requests`, client delivery failure, deadline, winner identity and durable reply to return `pending/waived/visible/user_stopped`.
- `settle.ts:192` and `sync-job.ts:419` enrich provider metadata, with business finish reason and cancellation rules remaining independent.

Therefore migration MUST NOT stop writes to, delete, or repurpose `experience.chat_generation_requests`, `experience.chat_generation_attempts`, first-token preview/receipt fields, or related RPCs. A nonblocking telemetry copy is allowed; financial/recovery authority stays in Supabase. Any future database-write reduction is a separate business-state decoupling task with billing/recovery regressions, not an observability cleanup.

Do not forward `AttemptObservation` wholesale: it includes `discarded_response.content/reasoning` diagnostic fragments. Explicitly project only safe identity classes, timings, statuses and bounded provider fields.

## 3. Minimal Grafana path

1. Keep existing Sentry capture sites as the single measurement sites. Add a small no-throw measurement/export boundary for backend Metrics; do not instrument every route individually.
2. Low-cardinality histograms/counters: server response duration/count by normalized route + method + status class + request kind; Prisma operation duration/outcome by bounded model/operation; runtime RSS/event-loop; in-flight requests and exporter drop/queue health.
3. Attempt logs: one dispatch and one terminal event (or a terminal event plus start counter), with request/attempt IDs only as log fields, platform, requested/resolved model, known provider, role, reason, HTTP class, monotonic durations, release and environment. Provider missing remains unknown; provider-internal hidden retries cannot be invented.
4. Logical request terminal counts remain distinct from actual dispatch counts. User cancellation, losing a hedged race, policy filtering, timeout and provider transport failure stay distinct; a cancelled hedge is not automatically a broken supplier.
5. Metrics/Logs export must be asynchronous, bounded, disabled by default until endpoint/credentials are provisioned, and fail open for chat. Shutdown has a short bounded flush and cannot wait indefinitely.
6. One private Alloy/Collector endpoint can receive batches. Do NOT assume a separate Railway service can tail another service's stdout filesystem. Explicitly choose supported platform log draining or an allowlisted bounded log transport into the private collector; raw stdout remains the existing Railway diagnostic path.
7. Traces can follow later after proving Sentry/OpenTelemetry compatibility; do not add a second complete instrumentation stack merely to draw the first engineering dashboard.

## 4. Ownership and acceptance semantics

- Engineering-owned response duration: non-generation server route duration; app-side preparation duration; DB operation wait; client render/ready duration. Each retains its own clock/boundary.
- Upstream-owned observation: dispatch to upstream headers/first valid token/completion, split by provider/model. Provider selection, retries and fallback are engineering policy, so retain user end-to-end experience alongside upstream timings.
- SSE `onResponse` may include the stream lifecycle; it must remain in the generation class and cannot be ranked together with ordinary JSON endpoints. A 200 SSE response does not prove strict successful reply.
- Never subtract independently aggregated p95 values to infer a phase. Use paired per-request stage durations or spans; concurrent primary/fallback durations do not sum into user latency.
- Per route/model table must include sample count, success/error/timeout/cancellation rates and p50/p95; compare same environment/release/request kind and context cohort. Lower p95 achieved by dropping slow requests or shortening output is not an accepted performance improvement.
- Operational quality needs monitoring coverage/drop counters. Source calls to Sentry metrics on every request are not proof that every event arrives at Sentry/Grafana under quotas/network loss.

## 5. Required verification before cutover

- Existing `lib/perf-metrics.test.ts` covers generation classification, status bucketing, P2024 and metric-failure no-throw; extend only after approved acceptance scope.
- Verify route normalization/unmatched paths, duplicate initialization/shutdown, aborted/disconnected SSE, explicit user stop, primary win/fallback win/hedge loser, pre-dispatch balance rejection, absent provider, missing cost and reported zero.
- Exporter endpoint down/queue full/timeout/invalid credential must not change chat latency, response, wallet, free quota, recovery or throw unhandled rejections. Failed telemetry must be observable without recursive logging.
- Run backend/shared tests and affected consumer typechecks/build; retain existing first-token billing/recovery local scenarios.
- No database polling, extra database timer, per-event config SQL, or telemetry schema/table migration is required for the new generic service metrics/logs path.
