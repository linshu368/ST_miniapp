# 30 部剧各取一个首播原片，两组同期比较

## 复用边界

按已获取的远端 dev 6935f927、main c804055b 核对，以下是 dev 源码事实，不代表已部署。主工作区含旧代码与无关修改，实施应从届时最新 dev 隔离开展。

- routes/drama.ts 的 /api/dramas/:id/play 已负责 Telegram 鉴权、选定归属该剧的可播单集、生成私有地址，并禁止中间缓存。保留详情、DramaRepository、原私有桶和封面。仅为默认推荐单独提供确定的置顶顺序；前端复用列表时，不让置顶改变搜索/最新等独立视图的原顺序。
- features/drama/delivery.ts 有固定账号 HMAC；目前阈值和返回值是 Bunny 专用。复用分桶算法，不覆盖旧实验 ID/key 或用原 20% 作为 B。日志去重与 /play 响应都要绑定**新**实验，不能将旧分桶补入新事件。
- shared 的 DramaDeliverySchema 和 frontend/lib/perf/grafana.ts 都只接受现有来源。先扩展有限枚举，再贯通实际取址、Faro 输入白名单、查询和恢复事件；不从 URL 猜分组。无归属仍是 unknown。
- 当前 DramaPlayer 设置 video.src，drama-media.ts、drama-seek.ts 又按 currentSrc 等于播放地址判断观察归属。hls.js 会让元素持有 blob 地址，仅替换 URL 会导致丢帧或漏报。复用同一 DOM 播放器、既有计时与生命周期；媒体所有权绑定本次装载代际和实际元素资源，切源时解绑旧实例/帧回调，网络细节不可见则标缺失。
- 既有 @drama、drama-play-error、固定播放器及快进观测用例可扩展；不另搭模拟后端或建监控平台。既有 compare-drama-cdn 中 5000ms 判断不直接用于本实验。

## 流程与故障处理

1. 运营侧一次导入同一批 TEST 原片，保存视频 ID 与 Stream UID 对应关系。对照原片来源记录/校验值、时长、音轨、构图；检查多档清单和私有访问。Stream 重编码，不能拿分片哈希与原片作等值校验。只有全档就绪、权限与真机抽查通过的映射才进入白名单，以已核验清单作为唯一就绪来源。
2. 服务端 runtime-config 读取限定环境的短片单和独立开关；使用同一份有序的 30 条 (drama_id, video_id, UID) 清单，同时派生默认推荐顺序和 video_id → UID 索引，拒绝重复/无效/环境不符。无需迁移、双写或数据库事务。开窗前按当前首个可播 ID、封面、全部资产就绪核对 30/30；片目变更/失效先暂停该版本的实验、排查，不在任一臂悄悄换片。坏配置禁止 Stream 曝光，不影响原 MP4。生产 Bunny 仍启用或恢复未经验证时禁止开流。
3. /play 校验权限和可播资格后才选择媒体。新版客户端随同一次请求声明协议能力；老端或不支持的端在分组前排除，两组使用相同准入条件。按环境、独立实验 ID、稳定账号做确定性分组；入组比例与 A/B 比例分离，固定分配键。TEST 由受控账号/预先核对的桶覆盖两臂，不给线上公开强制选组参数。
4. A 走原签名；B 在后端用 Stream key ID 和私钥为选中 UID 本地签短期 token，返回直接访问 Stream 的 HLS URL；响应保留 expires_at，增加兼容的媒体格式和有限 delivery 元信息。/play 不查 Stream 管理 API、不代理清单/片段。短时凭证需覆盖这些原片的合理观看/快进时间；到期沿用重取址恢复位置。旧客户端、无标记及片外保持 MP4；不发永久 URL。Supabase 签名缓存不与 Stream 混用。
5. 同一 video 元素优先使用真机验证过的原生 HLS；需 MSE 的客户端只在 B 路径动态加载 hls.js，验证 CSP 的 media/connect/worker 对所需 host/blob 的精确许可。A 不加载 HLS 库。ABR 使用完整清单；不锁初始档、不改分片、不增加 B 专属预热。计时从用户行为起，加载 HLS 库/签名耗时均计入。
6. 区分不可恢复的媒体错误、自动播放限制、后台和慢网。致命不可播或签名失败允许每个播放意图至多一次回到原 Supabase 签名路径，经同一鉴权和资源校验；播放器维持当前集/秒数/暂停状态。原 B 终态先留存，恢复记录关联原意图，不重算总等待，不把恢复算成 Stream 成功。3 秒是测量线，不触发切源；新请求/库重试采用明确超时与有限次数。双路均失败回现有重试界面；关闭实验后新取址直接 MP4，旧异步回调不能抢回播放。
7. 导入是配置阶段的有限操作。保存导入回执，超时先查已有 UID/状态，避免重复创建付费资产；单个错误不纳入片单。无播放时写库、定时同步、队列或 webhook。两套环境各有映射、资产和凭证，实际播放 URL（尤其 token 位于路径）、私钥、源临时链接不得出现在 Pino/Faro/Sentry/自动 HTTP 追踪明细中。

## 两项指标与启动/停止门槛

- 起播：同一入口的已接受播放意图到真实首帧与 playing 均成立。主比较先选点击封面，同期同片；自动首页、换集、直接进入、重试分别看，不混入分母。另看设置源 → metadata 供诊断；MP4/HLS 元数据事件不可替代端到端结果。
- 未缓冲快进：复用 drama_seek_resume_v1，提交前正在播放、向前、目标 buffered=no；提交到目标附近新帧且播放恢复。buffered=yes/unknown、暂停定位、后台及不可验证的降级单列，不能以 seeked 即判成功。TEST 可在开播后跳到未缓存远端并现场读缓冲区验证。
- 主报告按**原实验分组**，另看实际 provider、回退原因、平台、入口、片目分布/网络条件。用全量终态计算可测成功 P95 和有效 N，3 秒内成功率同时保留可判定失败分母，退出、缺终态、不可测另列。已有 5 秒内起播指标、仅慢日志、按比例采样的明细均不是本轮全量 3 秒结果。分组必须实际进入两种终态和耗时流，不能仅修改仪表盘筛选。首帧代理能力单列。
- TEST 顺序交错 A/B 与 B/A，含首次和重复播放、Wi-Fi 和蜂窝；两个系统都要验证。线上先确认 Bunny 关流、旧地址不再下发、新版客户端和埋点覆盖。建议仅安全灰度时纳入 10% 合格账号、组内各半。灰度健康后，正式窗口建议纳入观看白名单的全部合格账号，以同一分配键固定 50:50；范围不是全站所有视频。开流和比例须另批。灰度不合并进正式样本。
- 开始前核对真实片单曝光与未缓冲快进量，约定观察窗口、有效用户/样本门槛和预算。分别给出 P95 与不确定性（可按用户聚类估计）、3 秒成功率、失败/回退/缺报、卡顿和字幕画质。只有两项各自有充分证据低于 3 秒且护栏可接受，才讨论扩量；小样本或只有缓冲命中则结论待定。此比较是两套完整播放方案的差异，置顶片库不代表全目录或原推荐策略；同时看各位置/片目曝光、点击和观看集中度，两臂的未缓冲占比及所有向前拖动的 3 秒成功率。
- 出现鉴权绕过、不可播、错误或回退异常、归属/分母串组、严重画质问题或超预算时停止发新 B 地址；不强制中止已在播放的媒体，保留历史。回滚无数据库变更。
