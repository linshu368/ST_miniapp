# 短剧 Stream 小片库 A/B（规划稿）

目标：验证同一批短剧在同期真实观看中，Cloudflare Stream 自适应播放相对当前 Supabase 原版 MP4 是否改善体验，起播与未缓冲快进 P95 是否分别低于 3 秒。区分“优于 A”和“达成 3 秒目标”。

- 既有 TEST 低规格试验每组仅 3 次起播，顺序固定；B 的 6 次快进全部已缓冲。它说明方向值得试，不是 Stream 的性能基线。
- 首轮用 30 部不同剧各自的第一个可播竖屏原片（高大于宽），含 AB1103 对应的三个历史慢样本，同一环境内每条内容只有一个用户入口；不把固定 650 kbps 的低规格版本作为输入或第三组。
- 目录、封面、鉴权和原片归档保持既有权威来源；普通播放、选集、快进、重试、续看使用同一界面。两组默认推荐列表固定相同的前 30 部、相同顺序，后续沿用原排序；不改最新、搜索、历史、续看语义。只有所选单集才算实验曝光，其他播放保持现状。
- A/B 在已鉴权、兼容客户端和已验证片单的共同范围内按用户固定、同期比较；切换和重试不换组。保留每次首次失败、实际来源和恢复结果。
- TEST 验收：Telegram iOS/Android 真机走通原片、Stream、片库内外换集、确定未缓冲的向前拖动、错误与恢复；同次操作两端能看到一致归属及计时。TEST 验证能力，不宣称生产 P95。
- 线上另案授权后：分别报告两项 P95、有效样本、3 秒内成功率与分母、失败/退出/回退，以及卡顿和可接受画质。证据不足写“不确定”，结论范围仅及本片单/观察人群。
- 本轮交付为规划和 Cloudflare 准备清单。Bunny 关流属于另一个窗口；未取得该窗口的关流及恢复证据不得打开生产 Stream 实验。不开通付费服务、不导入素材、不部署、不改生产。

待评审：首轮使用环境隔离、按位置排序的 30 条就绪映射，扩库才建管理流程。正式线上流量、费用上限和观察窗口待 TEST 验收及片单曝光量明确后冻结。
