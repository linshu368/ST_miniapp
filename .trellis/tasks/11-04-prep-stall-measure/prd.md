# 聊天派发前卡顿诊断埋点

## 目标与约束

为首字 5 秒预算内、供应商派发前的等待补充可定位证据。只改测量，不改鉴权、请求/响应正文、超时、重试、SSE、模型路由、计费与数据库。

## 已核实的测量缺口

- Prisma `measureDbOperation` 已包含池等待；不能用它排除经 Supabase REST 的历史、开轮、运行配置读写。
- `generation.pre_dispatch` 只在走到派发门禁时输出；不能以各阶段 P95 相加归因于某个失败请求。
- `dispatch_offset_ms=NULL` 只说明没有记录实际派发，不能独立证明请求从未进入任何上游路径。
- 成功首字样本中 ≥5 秒为零不代表超时失败为零，也不能推断延长 0.5 秒无收益。

## 验收

- Fastify 聊天发送/重生成记录 onRequest→preParsing、preParsing→preValidation、preValidation→preHandler、preHandler→handler 的互不重叠阶段；拒绝/失败请求也有收口。
- Supabase REST 记录安全的表/RPC 名、HTTP 方法、等响应头耗时及超过 1 秒仍在等待的事件；不读取/复制正文，不改变 signal、重试和响应对象。
- 计时必须标明只到响应头，不能冒充完整 SQL、连接池等待或完整正文耗时。
- 遥测异常不能改变业务结果；仅慢/失败请求输出结构化 Pino 事件，不输出 URL、查询条件、请求头、用户/会话 ID、正文或错误正文。
- 回归测试锁定正常/拒绝/挂起/取消、敏感信息脱敏与遥测失败隔离。运行 Backend typecheck、相关/完整单测和复杂度检查。

## 性能

无前端代码或资源变更；计时用单调时钟，REST 每在途请求最多一个单次计时器，结束清理，不轮询、不额外发请求。双端无新版本可观测样本，基线不补零。发布后同版本比较首字 P95、超时失败率及遥测负担。
