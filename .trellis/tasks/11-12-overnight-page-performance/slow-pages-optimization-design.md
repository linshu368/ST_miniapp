# 超过2秒及有失败的页面清单与优化设计

状态：**待评审的优化设计，尚未实施**。本次只基于既有报告筛选、分析和核对本地代码，不重新采样、不改产品或生产配置。

数据来源：[本次生产性能报告](./report.md)、[原始脱敏聚合与查询](./evidence.json)。窗口为**北京时间2026-11-11 19:00:00—11-12 10:09:24**。本地代码核对版本为`fix_request_speed / 5a05ffc0`，报告中的生产Backend最新部署为`9716d8a1`；**本地实现不等同线上实现，代码发现必须先与实际部署SHA核对**。

## 一、筛选结果与边界

- 主筛选：Grafana页面P95 **严格大于2000ms**，Android/iOS任一平台满足即收录；分别保留站内导航、文档冷启动、挂载到可用三种口径，不相加、不取平均。
- 失败筛选：Grafana页面终态`outcome=error`次数大于0。卡住、提前离页、API timeout及Sentry AbortError均不直接当页面失败。
- **站内导航超标11个页面，冷启动超标4个，挂载超标4个；去重共13个页面、23个超标“页面×平台×口径”分组。**
- **有失败的页面2个，共4次：大厅1次、聊天3次。**这两个页面已在13页中，不再重复相加；没有“只失败但三种P95均未超标”的额外页面。
- 表格单元格为“P95秒 / 成功样本N”，**粗体为该平台超标**；—为无样本。N<100一律为低样本，不能据此判定稳态或优化收益。本窗口导航仅Android个人中心达到100个样本。
- 以下页面筛选不使用API P95。例：会话列表页面导航未超过2秒，不能因为`conversations GET`为2.32秒就把它列成页面超标；接口问题另作定位证据。
- Sentry挂载指标只交叉验证，不混入主表：其报告中超过2秒的聊天、短剧详情、创作数据都已被上述规则覆盖。

## 五、分项优化设计

### A. 大厅：同时处理“打不开”和冷启动

**路径：HTML/公共脚本 → Telegram/Providers → 首屏数据 → 核心内容可用；浏览器同源大厅请求 → Next代理 → Backend目录读取。**

1. 使用既有`startup.stage.duration`及慢启动事件，区分壳展示、初始化、首屏数据和关键头像，不把shell_ready提前等同业务ready。首屏头像可见沿用critical_visual的独立验收。
2. 按实际release验证缓存和首屏策略是否生效。优先复用已存、契约校验通过且当前允许展示的公开列表；失败刷新保留可用内容并呈现更新失败。无有效数据时明确错误和重试，不能把骨架记成ready。
3. 核对Android4秒外层deadline与代理5秒上游等待的关系：外层截止后signal必须到代理及上游；有限只读重试只能在原总预算内，不能每层各重试一遍或重新计时。**2秒P95目标不等于将所有请求强制截成2秒超时。**
4. 先用代理现有`Server-Timing`与`lobby.proxy.duration`确定代理/后端等待。如果慢在启动公共脚本，再按实际依赖图延迟非关键模块；现有动态加载和监控延后保持原owner。
5. 对26次OPTIONS 403只核验正式Origin、允许方法/头、对应release；仅修正确认误拒的精确来源。不能放开通配来源，也不能按vercel.app后缀排除正式用户。
6. 个性推荐、身份状态、权限不进入全站共享缓存；公开latest的缓存策略不得直接复制给推荐接口。

预期：页面错误有明确归因与可恢复入口；大厅导航已有的快速路径不退化，Android冷启动先验证可缩短阶段，再向2秒内容目标推进。

### B. 聊天：把进入会话和生成回复分开

1. 分别验“已有session直接进入”“无session创建后读取”“恢复中会话”“深页历史”。沿用`useChatSession`与已有query，不增第二套会话身份状态。
2. 路由代码和只读角色资料可在用户明确意图时有限预热；进入后已有会话详情优先使用critical槽位。模型目录、图片/语音配置已有分阶段控制，先核验实际是否参与争抢，不能简单重复增加延迟。
3. 复用已经过权限与字段完整性校验的创建/详情缓存，避免已取得足够首屏数据后再次串行读取同一结果；是否可跳过请求须依据真实响应完整性，不伪造聊天ready。
4. 对14次详情timeout拆解客户端排队、headers/body、后端身份/设置/恢复/历史页读取。后端优先使用现有有界展示投影和游标读取；生产迁移、回填覆盖及writer兼容未核验前，不默认切换读路径。
5. 创建是写入：保留同步防双击及不自动retry；超时后显示结果待确认并走已有权威查询/恢复路径。若现有协议无法确认已创建身份，先评审shared最小契约，不能猜测“超时就是未创建”。
6. 离页取消只终止允许取消的读取；不把它等同生成取消。消息正文、公开思考、分页、草稿、活动轮次恢复、计费资格均保持；不通过减少历史内容或改首字计费改善页面数字。

预期：减少可以证明冗余的入场等待；页面3次error逐类闭环。首字、完整回复和进入页面分别验收，不能互相替代。

### C. 个人中心：优先优化路由提交前等待

本地`/profile`已经在真实可交互入口提交后标ready，余额独立loading/fresh；已动态加载部分VIP/服务组件。**不能再把“余额不阻塞ready”当新方案，也不能再提前ready。**

1. 复现Android从大厅、放映、剧场进入个人中心，分别记录首次/再次进入、预热命中/未命中与弱网条件。
2. 复用BottomNav的受限路由预热，检查/profile是否实际被选中、在点击前完成，预热是否因当前导航安静窗口中止。若无足够提前量，在原调度内安排一个目标，不开启全路由并发下载。
3. 只在资源/执行证据证明必要时继续拆重模块，保持交互入口、头像和编辑可用；不为减少bundle把原本点击可用的功能改成二次等待。
4. 保持wallet、签到、VIP的真实数据状态；检查后台请求是否在关键提交前争抢，沿用现有优先级与放行，不把相关读取全部禁用。

主要验收分组：Android站内导航4.57秒/N107 → **建议目标≤2.00秒**；iOS现有0.17秒作为守护分组。余额fresh、操作可用和失败恢复同时检查。

### D. 短剧详情、放映和剧场：按内容与媒体两条链验证

1. 复用既有目录、/play、metadata/data、first_frame、playing诊断。首次启动、切集、重试与播放后rebuffer分开；避免仅看成功分位数漏掉自动播放被拦、退出和错误。
2. 若/播放地址已返回而首帧慢，再定位清单、首段、解码或autoplay；若/播放地址本身慢，先查鉴权/数据库/签名。不能从两组P95之差直接决定换CDN。
3. 同一视频只复用已确认安全、有效的缓存/在途读取；manifest是否已非阻塞、缓存TTL是否已调整，必须核对生产SHA及观测，不照本地旧值重复改。换源/新播放意图仍需鉴权与签名，不预建所有视频播放请求。
4. 短剧详情ready继续需要真实首帧且playing；放映通用页面ready与视频startup保持两条指标。海报和壳不是播放成功。
5. 剧场列表只延续现有首屏封面、可见项优先和分批渲染，确保首行两张封面critical_visual不退化；2.07秒/N52先积累样本。

### E. 消息列表/详情：核对缓存新鲜度与串行写入

1. 本地已有消息路由/query预取，但列表staleTime=0、挂载总刷新，先测真正的网络次数与cache行为；保留运营下架所需新鲜度，不直接改成长期缓存或全局stale展示。
2. 列表/详情内容请求复用同一query key与进行中请求，核验是否值得使用critical优先级；轮询与未读刷新保持现有owner，避免在目标页首包前齐射。
3. 已读写入是单独审查点：列表点击消息时当前先等markRead再跳详情。该逻辑**不能解释本报告“消息列表进入慢”**，但可能影响列表到详情的真实点击体验。若后续改为先展示、异步已读，必须先确定“打开即已读”的产品语义，并保留失败补偿、未读数一致性，不能在本次隐式改变。
4. 消息详情17.98秒仅1个冷开样本；先复现直达深链、无缓存、Telegram初始化及详情响应，再决定代码拆分。VIP附加信息只有对应通知需要时再评估延后，不能替代正文/权限校验。

### F. 其余低样本页面：小范围验证后再动代码

## 六、可靠性、容量与最小充分方案

| 风险项       | 本方案要求                                                                                                            |
| ------------ | --------------------------------------------------------------------------------------------------------------------- |
| 超时         | 保留显式deadline及signal传播；诊断queue、headers、body；不得用延长超时或更早失败伪装提速                              |
| 重试         | 只对明确可安全重试的读取有限退避，并受原总预算约束；401/403/404和已取消请求不重试；写入结果未知不自动重放             |
| 并发/容量    | 复用3槽优先队列、受限预热和single-flight；核验inflight/waiting与首屏字节/CPU，禁止无界预热或无限队列                  |
| 幂等/事务    | 不改现有创建、已读、客服发送及生成计费事务；涉及写路径时按原身份/幂等键与权威结果确认                                 |
| 降级/补偿    | 只展示仍允许使用的缓存；无有效数据显示错误与手动重试；后台刷新失败不抹掉成功内容；过期权限/已下架内容仍按权威结果处理 |
| 隔离/限流    | 身份相关query/cache按现有身份边界；限流不自动绕过；保留客服代理、签名、鉴权与CORS精确来源限制                         |
| 可观测性     | 继续使用现有Sentry/Faro/Pino；请求上下文只留允许字段，错误记录`{ err }`；不把用户ID/完整URL/正文加进聚合标签          |
| 数据库       | 首批不新增表/视图/函数/migration；只有定位到真实查询问题后再按数据库规范单独设计，不读取生产业务行做本次分析          |
| 新框架       | 不新增全局缓存层、调度状态机、统一启动框架或性能测试平台；首批改动集中在原owner及已有测试/fixture                     |
| 注释与复杂度 | 仅解释deadline、取消/恢复、缓存隔离等非显然约束；未来实施遵守500行/120行预算，修改基线超长代码时先拆分                |

如确需补充导航阶段，先扩展原tracker和shared白名单中的有限枚举，消费者先校验兼容；不新开一条遥测出口，也不要求把所有跨源样本强行按身份配对。

1. 第一批优先Frontend原owner内的小改动，保持现有DTO和ready定义。先核对实际生产版本，已部署修复只复验，不重复实施。

必须覆盖的失败/恢复场景：

- 无缓存冷开、缓存有效但刷新失败、body挂起、队列等待时取消、快速连点/返回、切后台再恢复、离线重试；原deadline不被每层重试重置。
- 聊天已有/新建/失效session、创建已提交但响应丢失、无权限、长历史分页、离页后活动轮次恢复；不重复创建、丢草稿或误触发生成/计费。
- 消息下架、预取后挂载刷新、已读失败与未读恢复；客服发送响应丢失、重复点击及图片重试保持幂等。
- 播放地址失败、manifest miss、autoplay拒绝、首帧未到、切集/换源、重试与后台恢复；原始失败不被随后成功覆盖。
- 创作数据跨身份/筛选、过期缓存和统计错误；角色编辑私有草稿与保存/发布结果未知。
- 真实Android/iOS Telegram、iOS受限媒体计时、系统键盘、弱网和真实供应商另验；固定虚构fixture不能替代真实性能或账务验证。

这些改动涉及跨页面联动和失败恢复，**建议纳入现有本地验收系统**：复用上述分组和fixture，补充慢导航、取消/timeout、缓存失效及恢复场景。新测试文件是否必要须在具体实施批次风险评审中确认；本次不新增测试文件，也不强制接入暂停中的固定样本性能测试机制。
