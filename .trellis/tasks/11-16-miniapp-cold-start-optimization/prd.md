# MiniApp 冷启动专项优化

用户在周末故障分析后明确要求“进行优化处理”，并要求参考 GitHub/论坛实践。本任务实施该整改方案中的冷启动部分。

## 需求与约束

- 缩短 `/` 打开到 `/chats` 或 `/characters` 内容可用的完整链路，优先消除多余文档请求和首屏排队。
- 保留原分流、Telegram 签名身份、邀请、支付回跳、深链、返回、列表/分组和失败重试语义。
- 不持久化凭据、不缓存私人响应、不调整鉴权、计费、重试上限或后端容量。
- 复用原有 HTML shell、ready、请求调度、日志与本地验收系统。报告和方案可追溯到真实数据与一手资料。

## 验收

1. 无 cookie、合法 chats cookie、无效 cookie 打开 `/`，首次文档为 200，无重定向链；HTML 分别显示大厅/会话框架。
2. 启动 JS 阻塞时框架和原生 ready 可用；恢复 JS 后业务正常、无 hydration 错误。参数先捕获再清理；规范路径更新不产生第二个 document/RSC 请求。
3. 新旧用户分流、query/hash、深链、支付回跳、前进后退、刷新和主导航均正确；不将 root 冷启动错记为 SPA 或重置时钟。
4. 只有可见列表第一页使用 critical 槽；分页普通优先级、AbortSignal、总预算与有限重试继续有效。
5. groups API 的观测分类独立于详情，历史口径差异明确说明；日志不暴露凭据。
6. 运行既有 frontend tests/typecheck/lint/build、复杂度、适用 UI 检查；记录生产样本限制。Android/iOS 内容就绪阶段目标 P95≤4 秒，API 目标≤2 秒，不能以本地结果宣称生产已达标。
