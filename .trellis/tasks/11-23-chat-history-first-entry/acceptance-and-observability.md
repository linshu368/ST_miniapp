# 功能一致性、日志与聚合读取边界

日期：2026-11-23。根据补充要求修订规划，以下是实施及上线门槛，不是已完成的代码或测试结果。

## 1. 决策：限制聚合范围，以结果决定是否保留

聚合只服务“显示当前会话的最近历史”。**正确性、可定位性和数据库负载优先于减少RPC数量**。一个RPC只是候选实现，不能成为强制架构目标。

| 可以纳入首屏读取                                      | 必须独立或延后                                      |
| ----------------------------------------------------- | --------------------------------------------------- |
| 已认证身份对应的会话归属/未删除检查                   | 付费生成、报价、扣费/退款、额度收口                 |
| 当前会话必要字段、角色可用性和版本检查                | 模型目录、用户全部设置、钱包、VIP、语音资源         |
| 最近10轮及该页需要的编辑/删除/点赞/分支投影           | 完整角色卡、system prompt、raw_card、大型运行快照   |
| 展示确需的名字字段；到历史起点/空会话才取必要开场内容 | 剧情记忆读取/压缩、过期状态修复、全量历史、列表统计 |

角色授权和版本校验始终执行；只有“开场内容读取”可按需，不能连同权限一起省略。如果现有helper虽然返回少量字段、内部却读取大型runtime，先验证成本，再由所属模块提供最小安全投影；不从旁路直接绕开权限。

聚合函数不根据include参数逐渐长成通用接口，不接入外部HTTP，不做DML/行锁式修复，不返回整行JSON。复用拥有方的安全规则和历史投影，避免一份复制的SQL形成第二套真相。单个运行文件≤500行、单函数≤120行，按现有仓库规则拆分职责。

### 查询与数据量边界

- 先定位受权会话，再索引选有限轮次，最后关联展示投影；禁止先JOIN/聚合整个历史再LIMIT。
- 当前用户名字、角色版本只做固定数量的键查询；不得对20条消息逐条查角色/设置，不产生N+1。
- 首屏10轮+1轮哨兵判断has_more，不执行全历史COUNT、全局排序、全表角色查询或无界jsonb_agg。`session.message_count`复用原事实，不现场重算。
- 分页游标沿用turn_index，不使用OFFSET深翻页；旧客户端默认50消息与既有最大200消息不扩大。
- 不强制将轮询、向上分页、首次进入绑定到同一个数据库执行计划。数据DTO与React Query状态源保持一致，Backend内部可按有限用途选择更合适的读路径；每条都执行必要授权与一致性规则。
- 普通首屏暂以未压缩响应≤256KiB作为**容量观察目标**，不是截断或拒绝长消息的硬限制。超出标记payload_large，仍保留完整轮次和正文；必要时另评审按字节分页，不临时丢消息。现有消息长度约束保持。

### 聚合是否采用的对照门槛

在隔离TEST中，同一批固定数据对照“现有读取/最小必要并行读取/聚合候选”，不在每个生产请求里同时调用新旧链，也不创建永久两套复杂实现。测试复用既有合法fixtures，覆盖短/长会话、200轮、分支、多revision、编辑删除、长文本和streaming。

比较端到端读完成、SQL计划/缓冲区读取/返回行数、响应字节、CPU及内存、连接/锁等待和错误结果；逐级增加受控并发，记录与生产基线相当的测试条件。缓存冷/热分组，不把一次预热结果当P95。

采用聚合的必要条件：功能一致；同条件Backend读取P95不劣于现有链；应用请求次数或往返减少；DB查询计划、负载、锁等待和错误没有恶化。不能仅凭“HTTP请求变少”认定成功。DB内部关键查询无法解释或候选更慢时，缩小聚合范围或保留最小并行读取，T2首屏减量仍可独立实施。

暂定工程目标：Backend入口至DTO就绪P95≤800ms，RPC完整读取/反序列化P95≤600ms，映射和序列化各P95≤50ms。当前没有这几项同口径生产基线，标记为目标；实施先取基线，再据真实条件确认。它们不相加证明端到端P95达标。

保留原有兼容路径以支持应用回滚；不为每次失败自动执行“聚合失败→旧链全量重读”，避免加倍负载、重复修复和隐藏异常。

## 2. 超时、重试与恢复不会造成请求放大

- Backend一次详情请求总读预算≤8秒；聚合RPC单次≤5秒，**聚合分支最多发起一次RPC，不再内部重试**。旧独立分页helper的原有限重试只作用其原路径，不能无条件包住聚合分支。
- Frontend GET仅对既有允许的暂态传输故障最多重试一次，逻辑请求共用≤10秒截止，包括调度、尝试和退避；不得每次重置10秒。调用方离页取消、404/权限、SQL超时、shape错误、PT409均不重试。
- RPC客户端超时不证明SQL已经终止。先在真实PostgREST测试目标验证取消与statement timeout效果；不擅自修改全库/全role的timeout。不能保证取消时，记录执行未知并验证连接容量，不用SDK abort作数据库容量保护的唯一证据。
- 名字/权限/版本这些必要读取失败，返回既有明确错误；不以默认“你”、空历史或当前公开角色代替成功。头像/工具等可选信息失败只影响自身。
- 状态恢复/结算失败走原幂等同步流程。GET不修账、不重复生成，交付身份未确认仍不结算；后台恢复容量不过关时不移除旧同步恢复路径。

## 3. 日志按层解释，不用一条总耗时猜原因

复用现有HTTP根终态、DB transport、生成attempt和业务终态；补字段及固定中文展示，不新增日志存储或逐消息打印。

| 层/事件                                      | 必须能够区分                                                                                                                | 时长含义                                                              |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| HTTP `operation.terminal` / http.request     | 环境、release、固定路由、方法、状态、request/trace、结果是否确定                                                            | 服务端整个请求/连接生命周期；SSE200不等于生成成功                     |
| `conversation.detail.read`（新增业务读摘要） | entry/older/poll/refresh/unknown、aggregate/legacy、身份映射缓存状态（可得时）、消息数/页大小、attempt、failed_stage/reason | Backend读取与映射边界，不能代替浏览器真实可见时间或浏览器缓存命中情况 |
| DB `operation.terminal` / db.supabase        | 固定RPC/resource、attempt、响应状态/超时/取消来源                                                                           | 到响应头的transport耗时；不冒充SQL或body读取耗时                      |
| 同一读摘要中的 `rpc_read_ms`                 | 从发起RPC至SDK返回并完成内部结果校验                                                                                        | 包括网络、body/反序列化和校验；不等于纯SQL执行                        |
| generation attempt / conversation.stream     | 准备、主/备、首字截止、交付选择、持久化、结算、真正取消                                                                     | attempt与最终应用结果分开；按请求去重                                 |
| 现有worker根/终态                            | 扫描/恢复/失败/跳过数量、有限批次、最老候选年龄、结果是否确定                                                               | 与HTTP独立的恢复工作，避免将HTTP结束误当恢复完成                      |

### 受控字段

- 关联：沿用request_id、trace_id、span_id、parent_span_id及既有环境/release；不新增高基数业务ID到Sentry/Faro标签。
- 用途：`history_page_kind=entry|older|poll|refresh|unknown`，`read_path=aggregate|legacy`；若新增用途传输，先定义shared可选有限字段，旧客户端缺失归unknown，不信任它做授权/限流/业务分支。
- 阶段：`failed_stage=identity|authorize|entry_rpc|history_map|serialize|recovery|generation_prepare|first_token|delivery_select|history_finalize|billing|unknown`。
- 原因：`failure_kind=not_found|permission_denied|client_disconnected|user_stop|first_token_timeout|dependency_timeout|network_failure|db_read_failed|db_write_failed|delivery_conflict|invalid_result|unknown`；无法证明就用unknown，禁止从原始消息猜私有内容。
- 耗时：`identity_ms`、`rpc_read_ms`、`history_map_ms`、`serialize_ms`、`read_total_ms`。只记录实际测量到的值；未知字段省略，不补0。只有明确未执行的阶段才可记录0并附执行状态。
- 规模：`requested_turns`、`returned_turns`、`message_count`、`response_bytes`、`has_more`、`attempt`；response_bytes说明未压缩/线上传输口径，不混算。
- 终态：原有outcome/outcome_known、public_error_code、受控cause code；`cancel_source=client_close|user_stop|deadline|dependency|unknown`、`delivery_conflict_reason=already_terminal|winner_conflict|identity_mismatch|unknown`仅在权威状态或明确守卫可证明时赋值。

聚合后在Backend只能测到RPC整体，不能再打印虚假的owner_ms/settings_ms/opening_ms等“内部阶段耗时”。SQL内部用隔离测试EXPLAIN与可用的数据库聚合观测核查；若必须新增同请求内部诊断，应独立评审只含固定阶段/时间的诊断机制及开销，不把持久化日志、逐阶段写表或额外查库塞入读RPC。缺少内部原因证据时不批准扩大聚合范围。

`serialize_ms/response_bytes`从已有Fastify序列化/发送边界取值，只观察现有payload，不二次JSON.stringify、不读流、不为日志做SQL。无法直接取得时省略并在验证记录说明；传输字节缺失不能冒充0。

### 实际打印与等级

已确认 `safe-log.ts` 会删除嵌套 `phases`，`phase`也未在TEXT_FIELDS；数字`*_ms`可能通过旧Pino出口，但EventFields.safeFields仍有独立白名单。新增字段必须同时覆盖producer → EventFields/safeFields → safeLogRecord → formatter/serializer → 中文presentation → stdout → Railway，不能仅在调用点加参数。

- HTTP/DB既有基础日志保持原覆盖，保留成功分母；不以抽样日志计算全部错误率。
- 新业务读摘要每个请求最多一条：正常首次读取成功固定采样10%；正常poll不额外打印；慢读、失败、重试和未知结果全量打印。已有slow/failed事件与新摘要复用同一完成守卫，避免再复制一套详细日志。采样需固定、记录sample_rate，并验证没有按耗时选择正常样本。
- 新业务摘要与HTTP根终态属于不同语义边界，后续统计以event+operation+request_id去重；不能直接累加。HTTP层与业务层断开各保持一次终态。
- 预计404/业务拒绝、确认用户停止按info/rejected或cancelled；慢读/依赖超时用warn，真实DB写入/交付确认/结算失败保留error。不能将所有AbortError、409或HTTP200自动降级。
- 每次尝试、每个请求、每个后台批次均有明确根上下文，poll与原生成请求使用各自request，不能伪造同一个trace；业务关联沿用已有受控方式，不额外查库。
- 并行读取发生多个失败时，主失败阶段与捕获异常一起冻结；迟到的其它失败或离页取消不能覆盖首个真实失败。记录已完成阶段，未完成的不补耗时；不额外等待所有慢依赖才返回失败。
- 原始异常以`{err}`安全投影；新增固定中文原因和枚举，不开放Error.message/SDK detail/SQL/URL/token/initData/正文/昵称。未知错误保留code/cause和源码位置。

## 4. 功能一致性是上线前提

“功能不出错”按以下可执行验收落地；不能用文档门禁或性能数字承诺零故障。

| 验收组       | 必须通过的场景                                                                  | 失败处理                                                     |
| ------------ | ------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 权限与版本   | 跨用户、删除会话、角色权限收回、固定创作者版本、空会话开场、官方角色            | 不返回任何未授权历史；保持既有404/错误语义                   |
| 历史完整     | 0/1/10/11/200轮、最新revision、编辑删除、点赞、分支继承、长正文、开场只出现一次 | 新旧读路径在固定快照下DTO一致；10轮只是分页大小差异          |
| 前端操作     | 向上翻页/滚动/草稿、切会话、迟到响应、取消定位、新建免重复GET、发送后刷新       | 不清空旧页、不串消息、不重复创建或重发                       |
| 并发与恢复   | streaming中进入、主备竞争、用户停止竞态、worker重启/跨副本、24小时前孤儿        | 不抢占活跃生成，保留CAS及额度先收口后解锁                    |
| 钱与未知结果 | 交付PT409、DB终态写失败、扣费响应丢失、重复恢复/结算                            | 不因读取变更多扣/少扣，未知只按原charge_id核对               |
| 超时与隔离   | 名字/权限/DB慢、SQL timeout、网络断开、用户离页、工具/模型慢                    | 必要数据不伪造，可选失败不挡历史，取消不吞真故障             |
| 日志可信度   | 每阶段失败、正常停止、SSE200内失败、并发trace、字段脱敏、采样/输出失败          | 真实stdout有字段，原因与权威状态一致；日志异常不改变业务结果 |

优先扩展既有回归文件和@chat/@chat-history虚构场景；共享契约运行shared测试和全consumer typecheck。功能一致、负载对照及日志stdout三组证据齐全才能发布；性能达标不能抵销功能失败。缺少真实Telegram/并发/生产样本的部分明确未验证，不能写“全部正常”。

发布按小变更拆开：先日志与错误分类，再有对照收益的读取方案和首屏减量，恢复覆盖通过后最后移除同步恢复。每项独立回滚；不叠加上线后才寻找根因。生产发现历史缺失/越权/结算不一致立即停止，普通性能退化按原design门槛核查。
