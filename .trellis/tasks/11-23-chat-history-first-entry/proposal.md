# 聊天会话历史优先优化方案

日期：2026-11-23。当前状态：方案完成，尚未修改产品代码、执行数据库迁移或部署。

## 主要结论

建议把进入聊天的主链收敛为：**身份与权限校验 → 有界的必要数据读取 → 显示最近历史**。优先验证小范围聚合，效果不佳时采用最小必要并行读取。模型、设置、钱包、语音等随后加载；异常生成状态交给经过验证的现有恢复任务处理。

目前后端是“多个读取组串行、组内并行”，历史仍然要等昵称、过期消息检查和角色开场读取。单纯增加Promise.all或修改加载动画，不能解决整条链路。

## 当前基线与目标

数据窗口：北京时间2026-11-21 00:00至11-23 00:00，左闭右开，与前面的周末报告一致。

| 指标                | Android 当前P95 / 样本数 | iOS 当前P95 / 样本数 | 第一轮目标                 |
| ------------------- | ------------------------ | -------------------- | -------------------------- |
| 实际聊天页导航      | 4481ms / 741             | 3154ms / 138         | Android≤2500ms、iOS≤2200ms |
| GET聊天详情逻辑请求 | 2331ms / 10681           | 1913ms / 1667        | Android≤1500ms、iOS≤1300ms |

目标尚待实施和线上验证，不是时延保证。接口数据包含刷新和轮询，发布后要单独区分首屏；不同P95不能相加、相减。合并“聊天与会话”模块的3.3秒不能代替真实聊天页数据。

## 四项优化任务

### T1：减少数据库往返

保留现有聊天详情接口，将会话归属、必要昵称、角色访问与会话版本、历史第一页作为小范围聚合候选。先验证功能等价及性能/DB负载，不能为了减少RPC数量做业务大接口。保留现有历史分页规则、编辑/删除覆盖、分支和点赞处理。

权限不作为可延后内容；昵称替换、固定角色版本和开场白也保持正确。一次RPC减少的是Backend与Supabase之间的网络往返，不意味着数据库内部没有查询成本。

### T2：首屏先显示最近10轮

当前通常首次取25轮、约50条消息，建议改为10轮、通常约20条。向上滚动继续读取更早内容，不裁剪完整历史，也不改变模型上下文。

复用现有内存缓存与创建会话响应，避免重复GET；不增加私人聊天持久缓存。已经加载的更早记录不能被刷新清空，必须保留滚动位置、草稿、编辑状态及当前回复。

历史真实渲染后即可阅读；头像、模型目录、偏好、钱包、语音与教程随后补齐。涉及发送时仍由服务端按真实权限、配置和报价校验。

### T3：恢复逻辑退出首屏等待链

现有过期消息恢复会涉及免费额度与生成终态，不能简单改成后台void调用。

复用已有30秒同步任务和发送前恢复门禁。先修补现有任务只覆盖最近24小时的缺口，验证更早孤儿、失败退避、有限批量、跨副本和重启后的恢复，再让历史GET成为纯读取。

恢复覆盖或容量验证未通过时，T3停止上线，T1/T2可保留原恢复路径独立交付。不能为了首屏变快而留下永久“生成中”或未释放额度。

### T4：结合Railway修复对话故障

同窗口按4个12小时切片读取生产聊天error，返回258、246、99、493条，均未达到每片500上限；去重后共1096条可见错误日志。**这不等于1096次用户失败**，同请求会产生多个事件。

| 问题                | 可见数量                                   | 方案中的处理                                                                                                 |
| ------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| 首字超时            | 165个不同请求：发送90、重生成75            | 拆分准备耗时、主备尝试、首字选择和总截止；不靠盲目延长超时或重试掩盖                                         |
| 交付身份确认冲突    | 5个请求，均见PT409                         | 核对取消与主备交付竞争，补准确原因；保留CAS，未确认交付不结算，永久冲突不重试                                |
| 历史终态写入失败    | 2个请求                                    | 抽查DB PATCH约5秒超时，被统一显示为upstream_error；应单独分类，保留部分正文并可靠收口                        |

| 账务/元数据落库异常 | 各1条                                      | 结果未知走原幂等对账，不重发付费生成，不推断“已扣/未扣”                                                      |

## 实施顺序与验收

### 本轮补充：功能、聚合边界与日志

**功能正确是上线前提。** 权限/固定角色版本、200轮完整历史、分页/编辑/删除/点赞/分支/重生成/取消、流中返回与迟到响应、跨副本恢复和额度幂等都要回归；固定快照下新旧读取的内容与状态应一致，只允许第一页大小不同。任何一项失败不得用性能提升抵销，不以方案文档承诺零故障。

**聚合接口只做首屏必需读取。** 不接模型、钱包、完整设置/角色runtime、记忆、恢复或计费，不做全历史COUNT/先全量JOIN再分页。先索引选10轮再取投影，禁止逐消息N+1。开场内容按需读，角色权限仍始终校验。对照相同数据、冷/热缓存和并发，比较读取P95、SQL计划、返回字节及数据库负载；聚合更慢或内部成本无法解释，就缩小范围或保留必要并行读取。

**日志增加可区分的固定字段，验证实际打印。**

| 记录内容   | 主要字段/规则                                                                                        |
| ---------- | ---------------------------------------------------------------------------------------------------- |
| 入口与关联 | 环境/release、固定路由、request_id/trace_id；entry/older/poll/refresh/unknown、aggregate/legacy      |
| 耗时与规模 | 身份、RPC完整读取、映射、序列化、总读取耗时，页大小/消息数/响应字节/重试次数；未知省略，不补0        |
| 失败原因   | 会话缺失、主动停止、首字超时、网络、DB读/写、交付冲突分别分类；保留error_code、cause及源码位置       |
| 结果与等级 | 正常停止info、慢读/依赖超时warn、真实持久化/交付/结算失败error；不能凭AbortError/409/HTTP200自动判断 |
| 输出与开销 | 字段贯通白名单、中文展示和真实stdout；不打印正文/昵称/token/URL，不为日志查库、读流或二次JSON序列化  |

聚合后的RPC总时间不能伪装成SQL内部各阶段时间；SQL内部另用受控查询计划和数据库观测核查。正常entry的额外业务摘要采样10%，正常poll不重复打印，慢/失败/重试/未知全量，单请求最多一条业务摘要；HTTP基础终态保留完整成功分母，按请求去重。

聚合RPC在Backend最多一次，不叠加内部重试；Frontend仅一次允许的传输重试并共享10秒总截止，避免多层重试放大。数据库是否真正取消需在PostgREST验证。

### 发布检查

1. 先补清晰的日志阶段和故障分类，锁定交付/终态写入失败的恢复行为。
2. 在TEST验证聚合读取RPC，保留旧客户端与应用兼容，再发布Backend和首屏减量。
3. 恢复任务覆盖验证通过后，单独移除GET同步恢复。
4. 发布稳定后重新观察完整48小时，分别报告Android/iOS的P95、样本、错误、离页、stall及恢复积压。每端至少100次同类导航，不足则延长窗口。

需纳入现有本地验收系统：最近10轮首屏、200轮完整翻页、慢设置不挡历史、编辑/点赞/分支、快速切会话、生成中退出与恢复。继续复用`@chat`和`@chat-history`；真实Telegram双端、系统键盘、供应商与账务另行验证。

不新增Redis、队列或通用缓存框架；不改聊天正文、模型上下文、权限和计费规则。出现串号、历史缺失、重复扣费或交付未确认仍结算，立即停止发布并回退兼容应用。
