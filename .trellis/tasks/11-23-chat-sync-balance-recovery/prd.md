# 聊天扫描与余额保护修复

## 当前需求（用户2026-11-23最终修正）

- 过期streaming扫描增加索引，以真实查询2秒内返回验收。
- 余额不足统一 insufficient_balance / HTTP402 / 星尘余额不足；不得当普通故障重试。
- 余额预检必须覆盖并发抢占：供应商请求前原子预留冻结报价。
- 数据库确认余额不足后，账单直接永久失败，实扣0；不要待结算，不得在充值后突然扣费。

## 约束

保留正常交付、用户停止计费资格和流水幂等；未知错误仍报错。失败账单不重开、不改价、不清除账务。只给新开轮预留，不回填旧账。生产迁移先TEST、按仓库workflow执行，不自动commit/push。不能用2秒超时冒充2秒成功。

## 验收

- 原查询/游标查询匹配部分索引；真实生产查询窗口内P95和最大值均记录，目标<2000ms。
- 用户钱包行锁下预留；并发另一会话、统一扣款及直接钱包消费均不能透支预留。
- 重放不多占，实扣一次；免费/失败/超时恢复释放，用户停止保持原计费规则；未知结果不强制过期放款。
- 余额不足的永久失败与RPC返回在同一事务提交；充值/重放/旧结果回写不能恢复收费。
- 余额拒绝info/rejected，后台独立计数不进入退避；未知P0001仍error。
- 财务并发/契约高风险，明确需要回归测试；既有相关测试、typecheck、静态检查必跑。

## 余额扣款日志呈现补充

用户明确要求余额不足显示“扣款失败”，不呈现为普通失败且不进入循环重试。两个既有balance_rejected事件维持info/rejected/INSUFFICIENT_BALANCE；通过注入的事件结果映射将result固定为扣款失败，原因显示星尘余额不足。普通未知数据库错误仍为失败/error。后台汇总单独标出balanceRejectedCount，失败账单永久终结语义不变；真实logger测试覆盖两个事件、普通错误不被误分类及不登记退避。
