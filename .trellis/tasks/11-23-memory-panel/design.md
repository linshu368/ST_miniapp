# 记忆栏拆出正文模型：独立生成、放进右侧面板

2026-11-23。用户已定方向：记忆栏和状态栏一样由独立模型生成，放在右侧面板状态栏下面；格式由我们内定，不开放给用户调；状态栏的提示词和格式不动。

## 1. 为什么拆

近 3 天 DeepSeek 应写记忆的成功回复约 8160 条，只有约 49% 写了记忆栏。和用户设置、剧情模式、轮次、篇幅都无关；漏一次后下一轮只有 22% 会写。不是正则漏抓（没出记忆栏的回复里有记忆内容的不到 3%）。每轮都带着约 1750 字的记忆规则也只有这个水平，加严格式没有用；历史回复里记忆区还占约四分之一篇幅，白白占上下文。

## 2. 用户看到的样子

- 右侧面板：状态栏下面加「记忆」区：**近期事件**、**历史档案**（含前情概要）、**里程碑**。样式见对比稿（A 三段折叠 / B 时间线，待选）。
- **不显示轮次**，只写故事里的时间和发生了什么。
- 面板入口：状态栏或记忆栏有一个开着就显示；卡没有状态栏、或玩家关了状态栏时，面板里只有记忆。
- 回复末尾不再出记忆栏；老回复里的记忆区直接隐藏（和旧状态栏的处理一致）。
- 「记忆栏」开关（`pref_show_memory`）保留：关了就不生成、不显示记忆区。
- 记忆内容只读，玩家不能改格式或内容。

## 3. 什么时候检查、用什么模型

- 和状态栏**同一时机检查**：每 3 轮自动看一次；VIP 点「立即更新」时立刻看一次。不扣星尘。
- 检查 ≠ 一定记：**有进展才记，没进展就不动**（见第 4 节）。点「立即更新」时如果没进展，记忆不变，提示「这几轮没有新进展」。
- 和状态栏**分开调用、同时发出**：状态栏提示词一字不动；记忆有自己的提示词和校验。两个调用并行，不多等；一个失败不拖累另一个。
- 模型同状态栏：Surplus Gemini 3 Flash 首发（首字 4 秒），失败或没过校验立刻 DeepSeek 兜底。

## 4. 按事件记，不按轮次记（核心）

用户定（11-23）：角色关系不是看轮次的，轮次不是好单位；应该由剧情、情节、事件驱动。聊 100 轮没进展就是没进展，不需要强行记录；提示词也要贯彻这个精神，不为了输出记忆而输出记忆。

- **算进展的**：感情变化（升温、降温、表白、争执、和解、心结、关系阶段改变）；第一次发生的亲密行为、尺度或玩法升级；做出承诺、约定，或旧悬念有了结果；重要剧情事件（相遇、离开、秘密揭开、身份改变、受伤、怀孕之类）；持续生效的状态变化（关系规则、穿戴、身体变化）。
- **不算进展的**：闲聊、日常、重复上次做过的亲密、气氛描写、原地打转。
- **一件事一条**，每次检查最多新记 2 件（两件互不相干的大事才分开）；没有进展就 0 件，这是常态。
- **看的范围从上一件记下的事之后算起**：中间几次判断「没进展」不挪起点，零碎的小变化会攒到真正有进展时一起记；一直没进展，最多看最近 40 轮（最近 10 轮完整，更早的截短），再早的不用再看。
- **已有内容只读**：模型只写新增；历史档案、里程碑平时只增不减，只有被挤出上限时才并进前情概要。
- **长度封顶，越久远越粗**（防止越聊越膨胀）：

  | 部分     | 上限  | 单条                             | 超出时                                                     |
  | -------- | ----- | -------------------------------- | ---------------------------------------------------------- |
  | 近期事件 | 10 件 | 事件一句话 ≤24 字，四项各 ≤40 字 | 快满时最早 5 件合并成 1 条历史档案                         |
  | 历史档案 | 6 条  | 四项各 ≤50 字                    | 最早 1 条并进前情概要                                      |
  | 里程碑   | 20 条 | 一句话 ≤30 字                    | 最早 5 条并进前情概要                                      |
  | 前情概要 | 1 段  | ≤400 字                          | **可改写**：每次有内容并进来时由模型重写整段，仍不超过上限 |

  整份记忆封顶约 5000 字，不随对话轮数增长。哪些内容要合并、并进概要，由代码按上限判断后放进本次任务；模型只负责写合并后的文字。

- **输入**：角色名 + 已有记忆（只读，不带轮次）+ 上一件事之前 2 轮（标【已记过】）+ 之后的对话 + 本次任务。不喂正文模型的 system prompt。
- **输出**：固定 JSON（`events[] / milestones[] / archive / summary`），代码校验各项齐全、字数上限、件数上限、合并任务有没有完成，不合格转兜底并附问题清单。

草稿代码（本地分支，未提交远端）：`packages/shared/src/memory-bar/`（schema / plan / prompt / apply），单测 `__tests__/memory-bar.test.ts`（9 条通过）。

## 5. 老会话怎么接上

某会话第一次检查时，如果当前路径上还没有新记忆：取当前路径上最近一条带 `[memory]` 的回复，把它的记忆区原文作为「旧记忆」并进前情概要，起点从那条回复之后算；没有就从空开始。一次性。

## 6. 存储、分支、撤销

- 新表 `experience.chat_memory_snapshots`（数据性质 D：由对话派生）：每次**有变化**的检查落一行（会话、锚点轮次、结构化记忆 jsonb `memory_detail`、触发方式、替换的那条）；沿用状态栏同一套规则——锚定到当时最新一轮的那一版回复，**只认当前路径上的记录**：重新生成、切分支看到的是那条路径上的记忆。落位卡与 registry 登记在 PRD 里补齐（CONTRACT §2.2）。
- 「多久检查一次」另记一个检查点（最后一次检查到第几轮，没变化也更新），避免没进展时每轮都去检查。
- 面板的「撤销这次更新」：状态和记忆一起撤回上一次。
- 迁移只加表和读写函数，走 GitHub Actions 迁移流程（TEST → 生产）。

## 7. 正文模型这边

- 提示词：`{{MEMORY_RULES}}` 填空（同 `{{STATUS_RULES}}`），协议常量去掉记忆部分；主体模板里提到记忆区的文字由运营改（只改文字，不动占位）。
- 历史：旧回复里的记忆区从入模历史里剥掉（省约四分之一的历史回复篇幅）；选项照旧保留。
- **新记忆不喂给正文模型**（用户定）：正文的连贯性由已经进入消息序列的「长期记忆压缩」负责；记忆栏是给用户看的，让用户心里有底。
- 选项不动。

## 8. 成本

- 正文：每轮少写记忆区（平均约 350 字），少带约 1750 字规则，历史少约四分之一回复篇幅；每轮输入预计下降一到两成。
- 新增：每 3 轮一次检查，输入约 1–2 万字对话 + 已有记忆（≤5000 字），没进展时输出只有几十个字符。

## 9. 上线步骤

1. Trellis 规划门禁补齐（prd / implement / task.json 的移动端性能与日志接入声明、落位卡）→ 用户审过后开工。
2. 共享层（草稿已有）→ 后端检查任务、存储、接口。
3. 用真实会话离线试跑一批看质量（需用户同意：只读生产对话、用生产模型 key）。
4. 面板对比稿选定 → 前端。
5. 迁移（新表）TEST → 生产。
6. 一次发布切换：正文去掉记忆规则、历史剥记忆区、老回复隐藏记忆区、面板显示记忆。

## 10. 用户已定（11-23）

1. 按事件记，不按轮次记；没进展不更新，提示词不为了记而记。点「立即更新」立刻检查一次，有进展才记。
2. 老回复里的记忆区直接隐藏。
3. 新记忆不喂正文模型（长期记忆压缩已在消息序列里）；记忆栏是给用户看的。
4. 要有长度限制：久远的记忆要能舍弃或被改写，不能越聊越膨胀。
