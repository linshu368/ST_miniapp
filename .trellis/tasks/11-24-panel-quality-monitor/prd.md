# 状态栏与记忆栏质量漏斗监控

## 背景

聊天页右侧面板的状态栏、记忆栏由独立模型每 3 轮生成。玩家最终在面板里看到的内容是否"按预期呈现"直接影响体验（P0 级关注），但目前只有零散的 Railway pino 日志：状态栏只记最终采用那次尝试的命中数，首发错误码被脱敏吞掉，最终显示层完全没有检查，Grafana 上没有任何数据。

## 目标

在 Grafana 上按天看到状态栏、记忆栏的**整体成功率**和**每一层的成功率**，并能下钻到失败原因，作为后续优化、修 bug 的锚点。

## 已拍板口径（2026-11-24 用户确认）

- 状态栏的项"沿用上次的值"算失败；另外单列沿用率作对照。
- 不做比率告警，只在 Grafana 记录数据。
- 用生产数据补算上线以来的基线（只读）。
- 记忆栏本轮一起接入。

## 需求

1. 状态栏按层统计：模型调用 → 格式解析 → 模板对账 → 落库 → 最终显示。
2. 状态栏按项、按样式统计最终显示结果：本次写对 / 写了"暂无" / 显示组件与样式不符 / 沿用旧值。
3. 记忆栏按层统计：模型调用 → JSON 解析 → 内容检查 → 落库（记下 / 没进展 / 冲突）。
4. 首发、兜底分开统计；首发失败原因（首字超时、截断/被拦、HTTP 错误等）可分类。
5. 新增一张 Grafana 看板，源 JSON 放仓库 `docs/grafana/`。
6. 一次性只读补算基线，结果写进本任务文档。

## 验收标准

- 发布后 24 小时内，看板能显示状态栏、记忆栏的整体成功率与各层成功率，样本量和 Railway `status_bar.update` / `memory_bar.update` 日志条数量级一致。
- 状态栏按样式的项级结果可查，能看出哪种样式最常沿用或显示错位。
- 首发失败按错误码分布可查，Railway `*.primary.failed` 日志带 `error_code`。
- 业务行为不变：更新结果、落库内容、接口返回与改动前一致。
- 基线数字记录在 `design.md` 的「基线」一节。

## 不做

- 比率告警、飞书通知。
- 修复已知格式问题（如长段落被吞）——由监控量化后另开任务。
- 前端真实渲染上报（面板打开率、样式错位）。
- "该更新而没触发"的触发层统计。
