# 聊天｜03 每次调用成本看板

## 背景

Grafana 现在只有稳定性看板：01 成功率与首发失败、02 兜底成功率与失败原因。成本侧缺一个看板。

供应商后台只能看到单次模型调用的价格，看不到业务口径。我们上了首字兜底、首发并发、超时竞速、出字后重写这些策略，一次用户调用背后可能有好几次模型调用。

用户要的循环是：不断上模型 → 看稳定性（01/02）→ 看每次调用成本（03）→ 决定上不上。

## 需求（用户 2026-11-27 原话要点）

1. **以用户调用为单位**，不以模型调用次数为单位。一次调用 = 用户发一次消息或点一次重新生成，即一条回复。
2. **成本 = 这次调用所有上游模型调用之和**：首发、并发的其余几路、竞速落败或被取消的、首字兜底、出字后重写。
   - 例：DeepSeek 首发走了兜底，算首发加兜底，不能只算兜底。
3. **时间维度**：能直观看到价格随时间的变化。OpenRouter 价格基本不变，Surplus 波动大，要能看出来。
4. **看板位置与命名**：作为「聊天」第三个视图，与 01、02 同组命名、互相链接。
5. **金额一律美元**。来源是人民币或额度的，换算成美元后再展示；没有可信换算的不硬算，标为未知。

## 范围

- **纳入**：聊天两条线，付费（lane chat）和免费畅聊（lane free_zone）。
- **不纳入**：状态栏 / 记忆栏（已在 st-panel-quality 的「成本与收入」）；建卡 AI 帮写、长期记忆压缩（不进 ops.llm_calls）。
- **模型维度**：按用户选的模型，付费按目录模型，畅聊按候选。不按实际干活的上游模型。
- **上游单价走势**：按上游模型 × 供应商，单独看价格本身。

## 验收

- **看板**：「聊天｜03 每次调用成本」（uid `st-chat-cost`）。默认最近 7 天，按小时。可按平台（付费 / 畅聊）和模型筛选。内容：
  - 调用次数、总成本、每千次调用成本、成本已知占比；
  - 模型明细：次数、每千次成本、单次 p50/p90、成本结构（首发交付 / 首发落败与取消 / 兜底 / 重写）、成本未知次数；
  - 每千次调用成本走势：付费、畅聊分开；
  - 上游每百万 token 单价走势：Surplus 与 OpenRouter / Venice 分开；
  - 成本结构走势、口径说明、数据刷新时间。
- **01、02 与 03 互相链接**。
- **数字可核对**：任选一天一个模型，看板总成本与 `analytics.llm_turn_costs` 当天同口径加总一致。
- **重写的 Surplus 成本能补到**：修复后新的 Surplus 重写行 `cost_source` 不再全是 unavailable。
- **日志字段**：`llm.recovery.completed` 的 `added_chars`、`reasoning_chars`、`reset`、`fallback_model` 在 Railway 日志里可见。
- **性能**：看板每个面板查询在只读数据源 15 秒语句上限内完成，目标 < 2 秒。
