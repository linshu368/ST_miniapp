# 大厅角色卡列表返回位置保持规划

## 1. 目标

用户从大厅角色卡列表打开角色详情并进入聊天游玩后，通过聊天页顶部返回、Telegram 返回键或系统返回手势退出时，恢复进入前的大厅浏览现场，而不是回到“推荐”列表顶部。

## 2. 范围与需求

### 2.1 必须实现

- 仅恢复“本次从大厅进入角色后返回大厅”的最近一次浏览现场。
- 恢复当前排序标签（推荐 / 最新）、搜索词、已加载的角色卡集合与顺序、滚动位置、目标角色卡在视口中的相对位置，以及大厅底部导航选中状态。
- 返回定位优先以进入的角色卡为锚点；像素偏移无法完全复现时，至少保证该卡及其上下文立即可见。
- 恢复前不得把大厅首屏作为可见最终状态，也不得明显先闪顶部再跳回目标区域。
- 详情内收藏状态变化继续以现有 React Query 收藏缓存为准，不能为了位置恢复回滚成旧收藏状态。
- 快速连续进入/退出时以最近一次进入聊天前的现场为准。
- 当前实现虽然一次返回完整角色列表，恢复机制必须保存“已加载集合/锚点”语义并依赖现有查询缓存，不得假设目标卡只会出现在首屏；未来或分支中列表采用分页/无限滚动时，需先保证已加载页可渲染，再执行同一锚点定位。

### 2.2 返回路径

- 聊天页顶部返回按钮。
- Telegram MiniApp 返回按钮。
- 浏览器或系统返回手势（history 返回）。
- 上述路径必须收敛到同一返回语义；不得一个路径恢复、另一个路径重置。

### 2.3 边界

- 主动切换推荐/最新或修改搜索词属于新条件，按用户操作更新列表，不应被旧快照反向覆盖。
- 用户从底部导航、收藏/会话列表或其他入口主动进入大厅，不恢复旧位置。
- 刷新页面、结束 MiniApp 会话、切换账号、列表整体重置不要求恢复。
- 锚点角色被下架或不在当前返回数据中时，优先定位其保存的相邻角色；相邻角色也不存在时回退到最近有效滚动位置，不白屏、不死循环加载。
- 不改变角色列表内容来源、排序算法、卡片样式、详情/聊天业务能力或后端接口。

## 3. 非目标

- 不做跨设备、跨账号、跨会话的长期浏览记忆。
- 不新增“返回顶部”“上次看到这里”或浏览历史入口。
- 不为当前一次性完整列表强行改造后端分页，也不引入新的全局状态框架。
- 不把完整角色列表再复制到 Zustand/localStorage/sessionStorage 形成第二份服务器数据真相。

## 4. 验收标准

- [ ] 在推荐列表下滑至少两屏，打开可见角色并进入聊天，游玩后从顶部返回；返回后目标卡处于进入前相近视口位置，可继续向下浏览。
- [ ] 在“最新”和带搜索词的列表分别执行上述路径；返回后标签、搜索词、卡片顺序与位置均保持。
- [ ] 顶部返回、Telegram 返回键、浏览器/系统返回手势结果一致。
- [ ] 深度浏览（包含未来分页/无限滚动已加载多页的情形）后进入并返回，不丢已加载卡片，不重新从首屏逐页开始。
- [ ] 聊天/详情内变更收藏后返回，位置保持且收藏展示为最新状态。
- [ ] 返回期间没有可感知的“先显示搜索框与首屏，再跳到目标卡”闪动。
- [ ] 锚点卡删除/下架时可落到保存的邻近卡或最近有效位置；页面保持可滚动。
- [ ] 用户主动切换列表条件、刷新或从其他主导航入口进入大厅时，不错误恢复旧位置。
- [ ] 快速连续打开不同角色时，只恢复最近一次进入前的现场。
- [ ] 弱网或后台刷新失败不阻断恢复；无快照、快照损坏或浏览器存储不可用时安全降级为现有大厅行为。

## 5. 约束

- TypeScript strict，不新增 `any`。
- 服务器状态仍由 React Query 持有；列表条件和恢复意图属于短生命周期客户端 UI 状态。
- 采用最小、前端单包改动；没有契约、后端和数据库变更。
- 默认不新建测试文件；本任务风险评估以现有检查加真机人工矩阵为主。如实施评审决定用回归测试锁定纯恢复算法，再单独确认测试文件范围。
