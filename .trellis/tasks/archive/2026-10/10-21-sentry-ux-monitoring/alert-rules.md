# 体验告警规则：什么信号值得把工程叫醒

> 2026-10-22 制定。视角是 C 端用户，不是服务器指标。
> 落地方式：Sentry Alert Rule → webhook `POST /api/alerts/sentry` → 现有 outbox → 飞书卡片。

## 一、只回答一个问题

用户会不会在这条规则触发的时候，说"这破 APP 打不开 / 点了没反应 / 转圈转半天 / 白屏"？

答"会"，才建规则。答不上来，或者只说明"服务器某个指标不好看"，就不建——那是看板的事，不是告警的事。

所有规则都落在四个用户感知动作上：

| 用户说的话          | 背后的技术事实                               | 对应信号                                                |
| ------------------- | -------------------------------------------- | ------------------------------------------------------- |
| 打不开 / 白屏       | 首屏资源没下来、chunk 加载失败、入口请求 5xx | `asset_load_failed`、pageload 失败率、入口接口 5xx      |
| 点了没反应          | 按钮触发的请求失败或长时间无响应             | `action_stall`、按钮对应接口的 5xx/超时                 |
| 转圈半天            | 慢，但最终会出来                             | `page.ready.duration`、`api.request.duration`、后端 p95 |
| 数据没了 / 内容不对 | 写成功但读不到、生成结果为空                 | 支付/生成成功率的绝对值断言                             |

## 二、级别与"要不要叫醒人"

| 级别   | 判据                                               | 响应要求                | 飞书                     |
| ------ | -------------------------------------------------- | ----------------------- | ------------------------ |
| **P0** | 大比例用户完全用不了，或涉及钱和账号               | 立刻（10 分钟内有人看） | @全员 + 电话式催办       |
| **P1** | 某个核心链路对一部分用户坏了，或核心页面大面积变慢 | 当天处理，不超过 4 小时 | 正常推送                 |
| **P2** | 体验在退化，没到"坏了"，但要防它悄悄恶化成 P1      | 排期处理                | 正常推送，可设免打扰时段 |
| **P3** | 单个用户的偶发问题，说明不了系统状态               | 不推动任何人，只记录    | **不推送**，只进 Sentry  |

P3 的价值是"用户来投诉时能查到"，不是打扰人。任何 P3 类信号如果在 1 小时内累计到 10 个不同用户，自动升级为 P1——偶发变成普遍，这就是"一阵一阵"那种情况。

## 三、规则表

阈值全部以**当前真实基线**为锚点。基线见第五节，都不是拍的。

### P0

**P0-1 核心接口大面积 5xx**

- 条件：5 分钟窗口内，`http.response.status_code >= 500` 的请求占比 > 20%，且失败数 ≥ 20
- 为什么是 20%：近 7 天全站 5xx 占比约 9%，20% 是两倍以上，不是正常抖动
- 为什么加绝对数 ≥ 20：低峰期 5 分钟只有 3 个请求，2 个失败就是 66%，不能因此报警
- 覆盖：所有 `/api/*`，排除对话生成两个长连接接口（它们本来就慢、偶发失败高）

**P0-2 流量断崖**

- 条件：过去 10 分钟 `http.server` 请求量 < 上周同小时均值的 30%，且绝对值 ≥ 10 才算一次
- 为什么必需：入口挂了、鉴权挂了、DNS/证书挂了，往往**一条错误都不产生**，只有请求量掉下去。这是唯一能覆盖"整个 APP 直接打不开"这类事故的信号

**P0-3 支付链路**

- 条件：15 分钟内 ≥ 2 个用户出现 `recharge_create_order` / `vip_create_order` 失败，或支付告警队列连续 30 分钟投递失败
- 涉及钱，不看比例，出现即处理

### P1

**P1-1 单个核心接口坏掉**

- 条件：15 分钟内某个 `transaction` 的 5xx > 50 且占比 > 30%
- 场景：一个接口挂了但总量里占比不高。今天 `/api/characters` 连续 7 天大量 5xx，就是这类——占比淹没在全站里，只有按接口看才看得见

**P1-2 页面打不开**

- 条件：15 分钟内 `asset_load_failed` 覆盖 ≥ 20 个用户，或占比 > 1% 的会话
- 典型成因：发版后 chunk 找不到。这类事故用户看到的就是**白屏**，而且刷新也不一定好
- 附：任何发版后 30 分钟内，这条规则的绝对数门槛降到 5

**P1-3 页面卡住（用户说的"卡在那不动"）**

- 条件：15 分钟内 `page_stall`（4 秒未就绪）覆盖 ≥ 20 个用户，或占 pageload 的 8% 以上
- 单条 `page_stall` 只记录不推送——网络差、低端机都会触发。要的是"有一批人在卡"

**P1-4 按钮没反应**

- 条件：15 分钟内 `action_stall`（2.5 秒无反馈）覆盖 ≥ 15 个用户，且集中在同一个 action
- 只对决定性动作报：`send_message`、`select_character`、`daily_checkin`、`support_send_message`
- 生成类动作（`image_generate`、`voice_generate`）本来就慢，**不按 2.5 秒判**

**P1-5 连接池耗尽**

- 条件：5 分钟内 `db.client.operation.duration` 中 `outcome:pool_timeout` 的计数 ≥ 10
- 这是 15 秒 500 和偶发卡顿的直接证据链，见 `research/slow-500-findings.md`

### P2

| 编号 | 条件                                                               | 含义                                                   |
| ---- | ------------------------------------------------------------------ | ------------------------------------------------------ |
| P2-1 | 15 分钟内 `http.server` p95 > 5s（排除对话生成），占比 > 5% 的请求 | 后端整体变慢，还没坏                                   |
| P2-2 | 30 分钟内 `page.ready.duration` p75 > 6s，按 route 分组            | "能打开但很慢"，用户体感最差的一类                     |
| P2-3 | 1 小时内 `runtime.event_loop_delay_p99` > 200ms 持续               | 进程被阻塞，后面必然出问题                             |
| P2-4 | 任何 release 上线后 2 小时内，新出现 `perf.instrument_error` > 0   | **监控自己失效了**，必须马上修，否则后面所有规则都失明 |
| P2-5 | 生成类接口成功率 < 95%（`POST .../messages` 5xx + 超时占比）       | AI 供应商或队列在退化                                  |

### 不报警，只看板

- 单条 `page_stall` / `action_stall` / `slow_request`
- 图片、字体、第三方资源加载慢（只要没失败）
- 任一新出现的 JS 异常 issue，除非它同时伴随 5xx 或卡住信号
- 冷启动慢本身（这是已知的结构性问题，单独排期，见 dashboard-setup.md 第 6 图）
- 对话生成耗时长（p50 16 秒是设计使然）

## 四、怎么保证飞书不被刷屏

四个机制，缺一不可：

1. **按事故合并，不按事件**：fingerprint 固定为 `类型 + route/action`，同一类问题永远是同一条事故，Sentry 侧和 outbox 侧都去重。387 个 5xx 是**一条**告警，不是 387 条
2. **同一条事故 30 分钟内只推一次**：既有的 `min_delivery_interval_ms` + 状态机。只有级别升高（P2→P1→P0）会再推
3. **恢复也推，但只推一条**：`resolved` 转 healthy 时发"已恢复"，让人知道不用再看了
4. **P3 纯静默**：不进入投递队列

## 五、基线（2026-10-22 实测，用于校准，不作为长期承诺）

| 指标                       | 现值                               | 说明                               |
| -------------------------- | ---------------------------------- | ---------------------------------- |
| pageload 请求/天（采样后） | 150–330                            | 峰值 10-18 有 326                  |
| `http.server` 请求/小时    | 170–2,360                          | 峰值 10-21 15:00 有 2,252          |
| 全站 5xx 占比（近 7 天）   | ≈ 9%                               | 33,426 / 约 380,000                |
| 5xx 占比（近 1 小时）      | ≈ 47%                              | 1,240 / 约 2,600，**当前正处高位** |
| 单接口 5xx（近 7 天）      | `GET /api/characters/:id` 6,409 次 | p50 370ms                          |
| 首屏 LCP p75               | `/` 4,401ms                        | Google "良好"线是 2,500ms          |
| pageload p95               | `/` 20,028ms                       | 这就是用户说的"打不开"             |

**关键事实：近 7 天 33,426 个 5xx 请求，没有产生任何一条 Sentry error event。** 所以：

- 基于"新异常"的告警在这套系统上基本无效
- 5xx 必须从 **span 的 `http.response.status_code`** 属性上取，不能用 issue 计数
- 现有 `/api/characters/:id` 的 5xx 已经持续一周，用户侧表现大概就是"有时候角色页打不开，重进又好了"

**计数会高估影响**：一个用户重试 3 次就是 3 条失败 span。所以所有规则都是"比例 + 绝对数下限 + 覆盖用户数"三件套，不用裸计数。

## 六、新功能上线的配套动作（非常建议，不强制）

新功能如果新增了会触发请求的关键按钮/交互（参照本文开头"只回答一个问题"的标准：用户点了会不会觉得"没反应"），非常建议顺手做两件事：

1. 在 `packages/frontend/src/lib/perf/action-tracker.ts` 的 `TrackedAction` 里补一条埋点；
2. 评估这个动作是否重要到要进第三节 P1-4 的白名单（目前只有 `send_message`、`select_character`、`daily_checkin`、`support_send_message`）。

不做不会报错、不会被测试拦住——纯前端交互本来就不用埋。但新按钮卡住了没人会知道，只能等用户来投诉，这正是这套监控本来想避免的事。

## 七、落地清单

1. 每条规则对应一条 Sentry Alert Rule（Dataset 按第五节：5xx 用 Spans，卡住用 Issues/Metrics）
2. Alert Rule 的 webhook 指向 `POST https://<backend>/api/alerts/sentry`，Header `x-alert-secret`
3. Railway 后端环境变量 `SENTRY_ALERT_WEBHOOK_SECRET` 设为同一个值
4. `runtime_config.alerting.notifications_enabled` 置 `true`（当前默认 false，为 false 时全部静默）
5. `FEISHU_ALERT_WEBHOOK_URL` 指向现有群机器人
6. 投递由 `stminiapp-payment-alert-monitor` 服务每 60 秒 drain 一次，所以**告警到达飞书有最多 60 秒延迟**，P0 规则的时间窗口（5 分钟）比这个延迟大得多，不受影响
