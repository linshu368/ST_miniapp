# 自研引擎替换 ST：阶段与模块划分

> 状态：总体思路与关键决策已确认（12 项，见 §二）。MVP 阶段的可执行方案见 **`docs/ST_remove-MVP实施方案.md`**（2026-08-10）
> **进度（2026-08-14）**：M1 / M2 / M3a / M3b / M5 已交付；测试与生产已切到自研引擎。ST 旧路径按「归档到 `legacy/st-removed/`、不硬删」执行：整包见 **`docs/ST_remove-整包清理清单.md`**，散文件与接线见 **`docs/ST_remove-混用清理清单.md`**（两份均已执行）。仍暂缓：`chat_engine_mode`、`st_handle`、nginx `/tavern` 分档、Railway `st-bundle`、历史 SQL。
> ⚠️ 读到旧 bot 代码后，**决策 3（预设格式）已二次修正为"MVP 不消费预设，后续自建格式"**，连带影响 M2 的性质与 M4 的排期，正文均已同步。
> 前置文档：`docs/ARCHITECTURE.md`（⚠️ 数据层描述停留在 migration 030，实际已到 068，参考时以实测代码为准）
>
> 背景：用户首次点卡进对话的耗时不达标（P50 4.9s / P95 22.4s，目标 P50 ≤2s / P95 ≤5s）。
> P95 长尾的根因是 ST iframe 冷启动（网络下载 + 手机解析）叠加点卡路径，ST 瘦身无法根治。
> 解法：自研 prompt 引擎替换 ST，让 boot 从点卡路径上彻底消失。

## 一、总原则

1. **平行开发 + 一次性切换**
   - 新引擎作为一条平行链路从零长出来，**不改变 ST 链路的运行时行为**。
     （原措辞为"不碰 ST 现有链路一行代码"。实测发现计费、免费额度、SSE 透传、chat_history 落库全部内联在 `routes/llm-proxy.ts` 的单个 handler 里，新引擎要复用这些能力必须先把它们抽成服务；这是行为保持的纯重构，故放宽为"不改变运行时行为"。）
   - **不做按用户灰度分流**。两条链路在生产代码里长期共存的成本（双数据源列表、两套渲染路径、按用户增量迁移、登录 provision 分支）远高于收益；且 ST 链路本身就是待解决的问题（P95 22.4s），作为回退目标价值有限。
   - 退路改为**全局开关 + 回滚窗口**：`runtime_config` 单一布尔值整站切换，切换后 48~72h 内 ST 保留但不路由，可一次性全体回切；窗口关闭后只向前修复，随即执行删除清单。
   - 上线前的质量验证靠**环境隔离**（staging 用生产数据快照跑完整链路 + 迁移演练），不在生产里做分流。

2. **MVP 优先，复现旧 bot 基本功能**
   - 引擎的对齐目标是**旧 bot**（prompt 组成、平台规则模板），不是复刻 ST 行为。
   - 跑通为主不搞复杂；一阶段不做世界书、正则、酒馆助手。

3. **上线速度 > 老用户体验**
   - 可以接受用户体验受到一定程度/范围的影响（如存量记录迁移只保证可见、不追求完美还原）。
   - 据此接受两处已知代价：**切换后老用户的存量对话历史不再对用户可见**（留档但不呈现，见决策 1）；回滚窗口内若真回切，切换后新产生的会话在 ST 侧不可见。

4. **删除判据：只删"ST 专用且后续无用"的东西**
   - 要抛弃的是"只有 ST 能消费、别的用不上/没必要接着用"的部分。
   - 与 ST 相关但替换后仍能用、维护成本低的，继续用（见 §四）。

## 二、已确认的关键决策

| #   | 决策点                   | 结论                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| --- | ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 存量聊天记录             | **不迁移**。`miniapp.chat_history` 只有 user_id + character_id 两维、无 session 概念，无法还原历史会话；而合并成单会话不只是展示失真——该会话会成为新引擎的 prompt 上下文，把多段无关对话喂进窗口截断会直接劣化输出。存量数据留档供运营/审计，不对用户呈现                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| 2   | 会话管理                 | 后端新增会话管理逻辑 + 新增会话表；`chat_history` 补 `session_id` 字段（存量行为 NULL，切换后新写入带上），使其从两维升为三维                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| 3   | 预设格式                 | **新引擎不消费预设**。实测旧 bot（`SimplePromptEngine`）没有任何一处读预设，其 prompt 由角色卡 `system_prompt` + 会话历史 + 平台规则包装的用户输入构成；而 `platform_presets.preset_payload` 是 ST 的 OpenAI 预设格式（`prompts[]` + marker + `prompt_order` + 深度注入），只有 ST 的 PromptManager 能消费。两者唯一同源的是**内容**：预设里 `platformRules` 那条 prompt 的正文，是 bot 侧 `system_instructions` 模板渲染后固化的一份快照（占位符已被写死）。平台规则改由 `miniapp.runtime_config` 承载模板与三个 `pref_*` 占位符。**后续会自建一套预设格式**（明确不沿用 ST 的），届时在格式定稿后一次性适配 payload 与消费方，因此不存在返工——MVP 阶段先只看"复现 bot 对话功能后 miniapp 上的表现"。（结论演进：自定义新格式 → 沿用 bot 预设格式 → MVP 不消费预设 + 后续自建格式，2026-08-10 二次修正） |
| 4   | 角色卡格式               | **不换格式、不重新设计字段**。引擎不适配酒馆运行时语义（宏、卡内嵌世界书/正则等），只从现有卡数据取需要的基础字段组 prompt                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| 5   | 正则 / 世界书 / 酒馆助手 | 都不需要。表现质量由 prompt 组装逻辑 + system prompt 质量承担，接受语义降级；**"下架酒馆卡"不构成切换的前置条件**，内容侧治理与本方案解耦排期                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| 6   | 重生成                   | 自研 UI 重新设计，**不保留 ST 的 swipe 多候选语义**                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 7   | 上线策略                 | **全量一次性切换，不做按用户灰度**。退路 = `runtime_config` 全局开关 + 48~72h 回滚窗口（窗口内 ST 保留不路由）。切换后全体用户（含存量）统一走新链路，登录不建 ST 账号、不跑 provision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| 8   | simulation 测卡链路      | **不属于 miniapp 项目本身，替换方案不考虑它**；删除清单中与其共用的部分（st-bundle / sync-engine 等）按 simulation 自身归属另行处理                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 9   | 会话模型                 | **支持同一用户 × 同一角色多会话**，保留今天的产品形态（侧边栏＝会话列表、保留新建会话入口）。会话是新链路的一等概念，也是决策 1 判定存量无法还原的原因                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| 10  | 生成配置归属             | 模型档位属于**用户配置层**（后续扩展字数、文风等同层），对该用户所有会话生效、不做会话级覆盖；**消息行须记录生成时的配置快照**（至少模型），否则改配置后历史输出无法解释                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| 11  | 历史会话列表             | 直读 DB（新会话表），不再反代 ST `POST /api/chats/recent`，连带下线 ST cookie 的 Redis 缓存与 avatar→角色元数据映射                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 12  | 切换方式                 | 因决策 1 取消了数据迁移，切换退化为**翻一个开关**，无需停机维护窗口。选低峰期执行即可（代价仅为切换瞬间正在 ST 里对话的用户下次加载会落到新的空会话页）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

## 三、阶段划分

### 阶段一：自研引擎后端 MVP（不碰前端，不碰 ST）

做的事：

- 新数据模型：会话表（用户×角色多会话）+ 消息表（内置新版重生成语义 + 生成配置快照）+ 用户生成配置存储。
- 引擎 v1：移植旧 bot 的 prompt 组装；输入 = 角色卡 `system_prompt` + 会话历史 + 本轮用户输入 + 用户生成配置 + `runtime_config` 的平台规则模板，输出 = messages 数组。**不做上下文长度管理**——bot 侧的"水位线泄洪式"机制后续需在 miniapp 复现，但不进 MVP。
- 对话 REST + SSE 接口：发消息、流式回复、重生成、会话 CRUD。LLM 调用复用现有网关的上游转发 / 计费 / 免费额度 / chat_history 落库逻辑（先把这些能力从 `llm-proxy` handler 抽成服务，引擎内部直调，不再走 st-extension 的 JWT + header 旁路）。

**核心产出：一条端到端可验证的对话链路**（建会话 → 发消息 → SSE 流式回复 → 落库计费），旧 bot 基本功能在新链路上跑通。

### 阶段二：自研聊天 UI + 切换就绪（代码可上线，但不接生产流量）

做的事：

- 消息区 UI 新写：气泡列表、markdown 渲染、输入框、流式打字、重生成（新设计）；复用现有壳组件（header / 侧边栏 / 模型切换 / 工具菜单）的交互框架，数据源从 bridge / 反代切到新 REST。
- 全局切换开关接线：`runtime_config` 布尔值同时控制 `/tavern/[characterId]` 的渲染分支与登录路径分支。**默认关闭**，代码合并上线后生产行为完全不变。
- 登录去 provision 化：开关打开后登录路径为纯平台鉴权，不建 ST 账号、不写 ST 文件系统。
- staging 全链路验收：内部账号在 staging 打开开关跑完整对话体验（建会话 / 发消息 / 流式 / 重生成 / 切会话 / 改配置）。
- **压测定容**：今天 SSE 长连接由 ST 进程承担，切换后全部压到 backend（Fastify / Railway），叠加新增的会话与消息表写入。全量切换没有灰度爬坡，容量必须在切换前压出来。
- 埋点对齐：新链路复用现有"点卡 → 呈现"耗时口径，切换后可直接对比 P50 / P95。

**核心产出：切换就绪**——新链路在 staging 达到生产质量、容量有底，生产流量一行未动。

> 注意：全量切换意味着新链路核心路径（发消息 / 流式 / 重生成）在切换当天就要面对 100% 流量，不存在"小流量试错"的缓冲，质量门槛全部前移到本阶段。

### 阶段三：生产全量切换 + 观察窗口 + ST 下线删除

做的事：

- 低峰期打开全局开关（无数据迁移、无停机窗口）。
- 48~72h 观察窗口：ST 链路保留但不路由，出严重问题可一次性全体回切（接受窗口内新会话在 ST 侧不可见）。
- 窗口关闭后执行删除清单（见 §四），部署收敛：Railway 从"nginx + backend + st-bundle 三进程单容器"收敛为以 backend 为主的简化拓扑。

**核心产出：ST 从 miniapp 生产链路和代码库中消失**，冷启动问题从根上不存在。

## 四、删与留（按"ST 专用且后续无用"判据）

### 删（只有 ST 能消费）

> 执行时点：**回滚窗口关闭之后**。窗口期内以下内容全部保留在仓库与生产环境中，只是不被路由。

- `vendor/sillytavern/` 本体（含受控补丁）
- `packages/st-extension`（bridge 服务端 + handlers + forwarders + 15 patches）
- `packages/bridge-protocol`
- frontend 整个 bridge 体系：`lib/bridge/`（BridgeClient / 看门狗 / 重连）、`components/bridge/`（STIframe）、`stores/st-mirror`、ChatSplash 及停摆遥测
- backend 桥接层：`routes/bridge.ts`（st-session 鉴权桥 / 单卡懒下发）、`middleware/stProxy.ts`、`routes/chats.ts`（ST recent 反代 + cookie Redis 缓存）
- `packages/sync-engine` 中 miniapp 相关部分（provision 下行 + watcher settings 回流）
- 部署侧：st-bundle 容器、nginx `/tavern/*` 分发与 ST 静态资源缓存分档、`ops/st-extensions/`、`ops/sillytavern/`
- ST 侧镜像表按需归档：`st_users.user_st_settings` / `user_st_chats`（占位从未接线）

> 与 simulation 共用的部分（st-bundle、sync-engine 的 simulation worker 等）不在 miniapp 删除范围内，按 simulation 系统自身规划处理。

### 留（与 ST 相关但替换后仍有用、维护成本低）

- `miniapp.chat_history` 及落库逻辑（运营监控/审计继续用；新增 `session_id` 字段后由新引擎继续写入）
- LLM 网关（`routes/llm-proxy.ts`）的上游转发 / 计费 / 模型目录 / 免费额度能力（引擎复用同一出口，切换前后计费口径不变）
- `miniapp.characters` 表及全部现有字段（含 `raw_card`，引擎只读取需要的基础字段）
- `st_platform.platform_presets` 表与 admin 管理通路（MVP 阶段新引擎不消费；待自建预设格式确定后，payload 与消费方一次性适配到位，见决策 3）
- `miniapp.runtime_config`（模型目录、计费配置续用；另新增平台规则模板 / 选项模式块 / 字数档位三个 key 供新引擎消费）
- 用户身份体系（`miniapp.users`，`st_handle` 等字段留着不碍事）
- 前端壳与交互设计（大厅、`/tavern/[id]` 壳页、chat-sidebar、模型切换器、工具菜单）

## 五、分模块划分（6 个模块）与阶段对应

| 模块                          | 内容                                                                                                                                                                                           | 所属阶段                  |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| **M1 对话数据模型与会话管理** | 会话表（支持用户×角色多会话）+ 消息表（内置新版重生成语义 + 生成配置快照）+ 用户生成配置存储（模型档位等）+ `chat_history` 补 `session_id` + 会话管理逻辑与读写仓库层                          | 阶段一                    |
| **M2 Prompt 引擎核心**        | 移植旧 bot 的 prompt 组装（角色卡 `system_prompt` + 历史 + 平台规则包装的用户输入）、平台规则模板渲染（三个 `pref_*` 占位符）；MVP 不消费预设、不做酒馆语义适配、不做上下文长度管理            | 阶段一                    |
| **M3 对话服务 API**           | 拆两步：**M3a** 把生成执行与计费出口从 `llm-proxy` handler 抽成服务（行为零变化）；**M3b** 发消息 / SSE 流式 / 重生成 / 会话 CRUD / 会话列表（直读 DB，替代 ST recent 反代）/ 用户生成配置读写 | 阶段一                    |
| **M4 预设供给**               | 按修正后的决策 3，MVP 阶段新引擎不消费预设。本模块改为**自建预设格式 + 引擎侧消费适配**，在格式定稿后一次性做到位                                                                              | 后置（不在 MVP 关键路径） |
| **M5 自研聊天 UI**            | 消息区本体新写（气泡 / markdown / 流式 / 重生成），复用壳的交互框架，数据源接 M3                                                                                                               | 阶段二                    |
| **M6 切换与账号链路**         | `runtime_config` 全局切换开关、登录去 provision 化、切换预案与回滚窗口、切换前压测定容（无迁移脚本，见决策 1）                                                                                 | 阶段二建设 → 阶段三执行   |

阶段三不设新模块：执行 M6 的切换预案，工作内容是全量切换 + 观察窗口 + 执行 §四删除清单。

### 模块依赖关系

```
M1（数据模型）────┐
M2（引擎核心）────┼─► M3b（对话 REST + SSE）─► M5（聊天 UI）─► M6（切换与账号链路）
M3a（生成出口服务化）─┘

M4：后置，不在关键路径（自建预设格式定稿后一次性适配）
```

M1 / M2 / M3a 三者互不依赖，可完全并行。关键路径：**三者并行 → M3b → M5 → M6**。
详细批次与执行方案见 `docs/ST_remove-MVP实施方案.md`。
