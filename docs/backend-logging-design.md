## 目标与边界

让工程师从一次前端请求、支付订单、生成轮次或后台任务出发，定位关联的业务阶段、依赖调用和最终结果。统一生产日志事件入口、错误归类和输出策略。覆盖 Fastify 的所有路由及鉴权、业务服务、DB 和第三方边界、进程内任务及生产独立脚本。经营流水、结算、告警 outbox、现有 Sentry Metrics 和 Grafana 指标继续按各自语义工作，事件字段和计时口径随迁移验证。无数据库对象、权限、连接池或交易逻辑改动。

## 结构与公共接口

在 backend 的 platform 下组织可观测性模块。可移植核心只定义事件、上下文、执行计时、采样规则与输出接口，依赖注入时钟、ID、策略和输出。Fastify、Pino、Sentry、业务错误目录和运行时配置属于宿主接线。先在一个工作区实现，并用最小独立应用验证可插拔性。等有真实第二个消费者再发布独立 workspace/npm 包。

- `emit(event, fields)` 记录注册事件，适用于状态转换、分支和降级。
- `observe(operation, execute, summarize)` 围绕一次明确调用收集耗时、异常或返回失败。成功原值和异常对象原样交给调用方，execute 只运行一次。支持同步和异步入口，SSE/作业交付由实际终态所有者结束。
- `withContext(context, execute)` 和 `childContext(operation)` 用于 HTTP、worker、脚本及并发子操作。AsyncLocalStorage 用 run 建立隔离作用域，跨 worker/队列只显式传递受控标识。
- 输出接口接收已校验的事件，根据策略输出到 Pino、Sentry Logs、Sentry Issues 或后续插件。生产至少有一个承接全量链路基础记录的可查询出口，配置校验拒绝关闭全部基础记录出口。现有 requestLogger 等入口逐批成为兼容桥，最终禁止业务模块直接写 Pino/Sentry Logs/异常出口。

## 低侵入扩展约束

- 请求关联、公共字段、耗时、终态归一、脱敏、选路、采样、缓冲和输出故障处理全部由基础设施负责。业务方法通过异步上下文自动取得 trace，业务调用签名无需逐层增加 logger、traceId 或输出参数。跨进程边界在基础设施适配器传递受控上下文。
- Fastify 全局插件覆盖新注册路由，Supabase/Prisma/pg 既有工厂覆盖数据调用，统一第三方调用适配器覆盖网络尝试。新增第三方只需在对应客户端接线一次，沿用调用者的 timeout、AbortSignal、重试和响应流语义。禁止全局替换 fetch 或隐式改变 SDK 链式对象的执行时机。
- 服务/repository 的公开业务方法可在已有工厂或装配点用显式类型化包装一次登记。包装保持 this、参数、同步/异步返回类型、异常 cause 与原有生命周期。模块函数没有装配点时允许函数边界调用 observe；包装语法以真实调用者验证后确定。避免为日志把整个 backend 迁移到新的依赖注入或装饰器框架。
- 新业务操作只登记稳定的操作名、允许摘要及错误映射。内部状态转换需要业务代码调用 emit 的明确语义，例如支付已确认、结算等待恢复、生成赢家已确定。自动切面根据可观测返回值判断技术结果，状态机所有者提供业务结果。
- 扩展点限定为上下文补充、安全事件投影、路由策略、输出适配器和生命周期。按固定顺序完成字段收集、归一、脱敏、选路和投递。插件只获得已脱敏的有界事件，输出异常在日志系统隔离；插件不得修改 HTTP 响应、业务参数或执行交易。
- 新出口实现适配器并在启动装配处注册，运行时配置沿用 platform/runtime-config.ts，安全的启动凭据沿用已有配置中心。新增日志字段在统一上下文或对应事件 schema/projection 中声明，扩展字段不能覆盖关联 ID、状态和版本。事件 schema 采用增量兼容，重放旧事件时按版本解析。
- 业务失败使用统一领域错误及注册映射。各方法直接传递异常或返回原业务结果，由负责该操作终态的边界记录一次；业务处理需要恢复或补偿时记录其自身事件。SSE、回调、作业和异步任务生命周期采用专用一次性结束入口，归属明确。

可验证的扩展验收包括新增一个内存测试输出适配器并完成多路选择与故障隔离，业务模块改动数为零；调整全局公共字段和输出策略时业务模块改动数为零；新增普通路由和使用现有客户端的 DB/第三方调用自动具备基础日志；新增业务操作只需一次边界登记与必要的业务事件。特殊协议或全新客户端需要适配器接线，CI 要能发现绕过受控入口的调用。所有扩展仍满足全量基础记录和性能门禁。

## 采集与关联

- HTTP 切面在根级路由注册前建立上下文。onRequest 记录时间与安全来源，鉴权完成后补调用类型，按路由提取允许的参数，普通响应通过生命周期记录真实 HTTP 状态、业务码、耗时与大小摘要。用 onError 收集原因，统一终态负责输出。验证未知路由、解析失败、CORS、鉴权拒绝、early abort、超时、redirect 和媒体上传。404 响应使用共享 envelope 之前要核对现有消费者。
- SSE、代理流和 webhook 由协议出口记录终态并与 HTTP 终态去重。区分 header 状态、首字时间、应用终态、断连和实际响应是否发送。SSE 开流后保留 HTTP 200 与独立业务错误字段，沿用现有 SSE 帧和客户端消费逻辑。
- Supabase transport 记录一次 HTTP attempt 的允许域/schema、固定资源名、操作类型、状态和 headers 耗时。repository 识别 SDK 的 `{ data, error }`、RPC 业务拒绝、结果数量和最终耗时。只读取业务本来会读取的结果，保持 thenable、abortSignal、响应流及 SDK 行为。Prisma 扩展记录逻辑 query，事务/pg 只在既有边界补摘要，记录回滚与结果不明，不重复输出 SQL 和参数。
- 服务方法按入口、嵌套业务调用、状态转换、IO、重试/降级和异常归属建清单。每次业务边界调用都有独立操作标识和全量终态。纯转换、循环热路径、逐 token/chunk/行按父操作记录计数、耗时与异常位置，具体方法覆盖方式在覆盖清单中逐项评审。批量任务的各独立业务项通过操作标识关联，批次另输出扫描/推进/失败数量，额外诊断详情有上限。
- `trace_id`、`span_id`、`parent_span_id` 构成调用图，`request_id` 标识本服务一次 HTTP 请求，`event_id` 标识单次事件。兼容期保留 reqId / request_id 的已有查询字段，验证合法入站 X-Request-Id 的前端联查，另有服务端独立实例标识防碰撞。多层重试每次新 span，并发分支共用父 span。统一选择有效的现有 Sentry trace 或受信 W3C 上下文，具体优先级和 SDK span ID 对齐由 P0 探针验证。无上下文时自行生成，Sentry 关闭仍可在 Pino 关联。响应头回传相关 ID，CORS 暴露范围随现有配置验证。
- 仅受信服务允许透传明确列出的追踪头，外部商户/模型/DB 默认本地关联，记录厂商允许的 request ID。Railway 平台请求 ID 单独验证是否能从可信入口获取。回调、轮询、脱离 HTTP 生命周期的任务各自生成根 trace，通过现有订单、生成轮次、attempt、作业键的允许摘要关联。跨进程保留父子关系需要协议原本支持透传，否则记录关联链接。追踪字段不参与鉴权、幂等或业务判定。

## 事件字段与安全

全局错误码、默认日志等级和操作结果以 [全局错误码评审清单](backend-error-code-review.md) 为设计依据，契约与迁移见 [错误码技术设计](backend-error-code-design.md)。采用清单的 outcome 枚举并独立记录 outcome_known；状态/等级的场景例外按清单处理，不能由 HTTP 状态推断结果。ERROR/FATAL 的异常捕获与告警动作独立，清单中的通知建议仍受 LOG_ALERTING_ENABLED 默认 false 约束。

固定字段包括版本、事件名、级别、模块、kind、时间、部署版本/环境、关联 ID、操作名、终态、耗时。HTTP 包含路由模板、方法、来源类别、认证类别、安全 Origin/客户端平台枚举、实际状态和响应类别。请求与响应扩展字段按事件定义类型和提取函数，例如分页大小、是否流式、结果数量、响应大小、错误码、provider 和 attempt；默认不取整包。敏感字段包括完整 initData、token、Cookie、签名、支付密钥、用户 IP/私密资料、对话和 prompt、完整 URL/query、签名链接、SQL/绑定值、二进制。业务标识需单独白名单或使用带密钥的稳定摘要，动态值不得成为指标标签。

错误调用方传原始 `{ err }`。各输出仅写经清洗的错误类型、受控消息和有界 stack/cause，未知 Error.message、供应商响应、DB detail/hint 不直接序列化。限制字符串、递归深度、列表与事件字节数。验证 Pino 子 logger、Sentry 默认集成、Logs/Issues/Spans 和诊断字段均通过各自安全出口。

## 状态码、日志等级与策略处理

2026-11-12 补充需求：状态码、日志等级及相关观测内容必须能作为后续策略输入，支持告警等动作。本节为待审批的设计契约，不表示现有系统已具备这些能力。首期同时建立受控策略入口、模拟动作与告警适配边界；具体生产规则、阈值、通知对象和启用范围随整体设计审批，不默认开启通知。

### 事件事实与策略决策

- 流程固定为事件收集 → 归一与脱敏 → 全量基础记录投递，同时将同一安全事件交给异步策略消费者 → 条件匹配/窗口评估 → 动作适配器。策略失败或抑制动作不影响原始基础记录，不允许把日志采样后的数据作为全量告警分母。
- 统一字段区分 `http_status`（实际发送的响应，未发送为 null）、`upstream_status`（依赖响应）、`error_code`（规范内部码）、`public_error_code`（兼容公开码）、`level`、`outcome`、`stage`、`operation`、`provider`、`attempt`、环境和事件版本。后台操作无 HTTP 状态，旧事件缺字段保持 unknown；不得补成 200、0 或成功。字段最终命名在核心契约定稿时统一。
- `level` 表示事件诊断严重程度，错误目录提供默认等级，受控分类规则可在归一阶段调整；不得由告警动作反向改写已记录事件。告警优先级独立存于策略决策，Sentry Issue 捕获、通知开关和日志输出级别各自独立。提高 LOG_LEVEL、关闭 Sentry 或诊断采样为零不能关闭基础记录和策略所需事实。
- 事件中的实际状态与业务结果不可相互替代。例如 SSE HTTP 200 后失败按业务终态评估；上游 401/403 可能是服务端依赖凭据故障；用户余额不足、主动取消和竞态败方通常只记录；一次 attempt 失败但最终兜底成功进入依赖健康/降级规则，不计为两次用户请求失败。支付建单超时保留结果未知，告警不能将其解释为订单失败或触发补单。

### 最小策略契约与组合规则

- 策略配置包含 `policy_id`、`version`、`enabled`、`mode=observe|active`、`priority`、适用环境/模块/操作、事件作用域（请求终态、业务终态或依赖 attempt）、条件和动作引用。条件仅允许白名单字段的等值、集合、范围和显式 all/any 组合，可组合状态码/状态码段、最低等级、错误码、outcome 与耗时；不支持任意脚本、动态代码或自由文本匹配错误消息。
- 单事件规则只处理指定作用域的一次事实。窗口规则另声明窗口、分组维度、计数或比例阈值、最小样本数、持续触发和恢复条件。比例分子/分母必须来自同口径的完整终态或已有权威指标，缺报、延迟和无流量保持 unknown，不能据此报告恢复。窗口长度、阈值和迟到容忍均须定稿，不能只写“错误较多时告警”。
- 多条规则可独立命中，按 priority 和 policy_id 稳定评估；每条规则每个动作一次，去重键包含策略版本、事件或窗口身份及动作。抑制与静默只作用于明确的规则/动作/时间段，不中止其他规则、删除基础记录或掩盖日志投递故障。配置拒绝重复 ID、非法等级/状态范围、未知字段/动作、无界分组、缺失窗口口径和不可用的必需依赖。
- `evaluate(event|window, policySnapshot)` 产生有界决策，包含策略 ID/版本、命中原因枚举、评估身份、事件/窗口引用、分组指纹、告警优先级和动作引用；`dispatch(decision, signal)` 只执行已注册的观测动作。首期使用类型化配置和固定动作注册表，不新增通用规则语言、工作流引擎或运营配置页面。新增公共策略或动作在核心及装配处接线，业务模块零修改。

### 告警状态、投递与故障模型

- 告警适配优先复用现有 [AlertPublisher](../packages/backend/src/features/alerting/publisher.ts) 和 shared AlertEvaluation/outbox，复用事故去重、升级与恢复，禁止业务代码直接发送通知。现有支付探测有专用规则及投递过滤，新规则需逐项核对 schema、domain、指纹和投递允许范围，不能假定注册动作即能送达，也不能放宽原支付过滤。若现有契约不足，另行评审 shared 扩展及消费者兼容。
- 区分策略评估命中、Publisher accepted（状态/outbox 已持久化）和渠道 delivered。指纹由环境、稳定规则身份及有界业务维度组成，不使用 request_id、用户/订单 ID 或错误消息生成独立事故。版本留在决策与幂等身份中；规则升级须明确沿用、关闭或迁移旧事故，不能制造无法恢复的孤立事故。通知有冷却、静默到期、升级和恢复规则，静默期仍更新事故状态。
- 同一事件经多个日志出口或持久化重放时按 event_id 去重。窗口评估必须确定唯一权威执行方，跨实例窗口与事故状态不能只存在进程 Map；优先复用现有聚合/告警设施，选择应用消费者或 Grafana 等平台执行时，一条规则只有一个通知所有者。权威设施、检查点、迟到/乱序、水位、去重保留期及重启恢复未确认前，窗口策略保持 observe，不能承诺准确计数或生产通知。
- 策略消费者与动作各有有界队列、并发、超时/取消和容量预算；持久化失败不得记为 accepted。仅对安全、幂等的评估/通知做有限退避重试，沿用 outbox 投递恢复，不重执行业务。重放默认 observe；主动补通知须明确重放范围、过期限制与幂等键。动作范围限于通知、受控诊断选路及观测指标，不执行交易、自动重试请求或修改业务配置。
- 策略异常、队列积压、去重失败与投递故障记录独立健康指标和限频自诊断；标记为策略内部事件，默认不再进入同一告警策略，防止日志→告警→日志递归。独立健康检查监测该故障，不能只依赖已故障的策略链路自报。策略消费不可用时保留基础记录，告警覆盖明确标记 unknown/degraded。

### 配置演进与验收

日志告警使用环境变量 `LOG_ALERTING_ENABLED` 作为总开关，默认 `false`；只有显式配置为 `true` 才启用日志告警评估和通知发布，未配置为关闭，非法值按既有配置校验拒绝，不得因非空字符串而开启。变量在 platform/config.ts 集中解析，经现有 platform/runtime-config.ts 入口统一暴露，不新增同名运营配置覆盖它，业务模块不得直接读取 process.env。该开关独立于全量日志采集、Sentry Issue 捕获和现有支付等业务告警，不改变它们原有开关与行为。

关闭时不初始化日志告警消费者，不执行该来源的影子/窗口评估、不发布新告警或恢复通知；基础记录、日志查询及其他非告警观测策略继续工作。启用后仍按规则的 enabled 与 observe/active 模式控制，observe 不发布通知。环境变量变更随服务/worker 重启生效，需核对全部生产实例，不能宣称运行时即时停止。关停后已有日志告警 outbox 项也不得继续外发：消费者须识别该来源，在关闭时暂停其待投递/重试项，保留供恢复或明确处置；不影响既有业务告警项。若现有 outbox 无法安全区分来源，必须先补齐兼容设计与验证，不能启用生产日志告警。已在途的通知可能完成，不承诺撤回；重启后保留事故状态，再按有效窗口评估，不因关闭自动报告恢复或盲目补发过期通知。

策略规则配置经 platform/runtime-config.ts 读取，按版本整体验证后原子替换快照；一次评估固定版本。坏更新保留上一有效版本并报告拒绝，启动无有效版本时保持基础记录、关闭策略动作并显式报告策略不可用。总开关关闭优先于上一有效规则版本，不得通过配置回退重新开启。支持 observe 影子评估、按环境/规则灰度、独立停止动作及回滚上一版本，不回滚真实 HTTP 状态或删除历史事件。通知凭据由现有安全配置管理，策略只存渠道引用。

开关验收覆盖未配置、false、true、非法值，以及 true 下 observe/active；默认/关闭时日志告警评估与 Publisher 调用均为零，全量基础记录及既有业务告警不受影响。另验证重启后全部服务/worker 关闭、待投递/重试项暂停、在途边界和重新开启后的状态恢复。实施时同步安全的 .env.example、README、架构与部署/运维手册，明确默认 false 和各实例重启要求；本次仅确认设计，不修改实际环境。

验收需用固定事件与窗口输入复现：404/预期拒绝、500、SSE 200 后失败、上游鉴权故障、429、正常取消、失败后兜底成功、支付结果未知；验证等级阈值与组合条件、规则并存/静默、跨实例重复/重放、窗口迟到/无流量、触发/升级/恢复、坏配置回退，以及动作超时/拒绝/积压和自诊断防递归。新增规则/模拟动作应无需修改业务模块；策略关闭或故障时基础记录与业务响应保持正确。真实通知在 TEST 独立核对 accepted、delivered 和恢复各阶段。执行方、窗口状态持久化、容量与生产阈值列入规划待完成项；如需数据库对象，先按八域归属和迁移规范另行评审，本设计不直接授权建表。

## 默认策略与可靠性

- HTTP、作业、内部业务操作、DB、第三方每次 attempt 均全量记录安全基础字段与实际终态，成功、失败、拒绝、超时、取消、降级和结果未知都覆盖。全量基础记录不参与成功采样、普通日志级别过滤或跨请求合并。每次请求/作业另有开始记录，长任务记录低频存活信息，支持发现已开始但缺失终态的链路。请求结束后仍运行的子任务用关联链接记录独立终态。
- Sentry Issues 仅捕获有处理价值的异常，预期 4xx、正常竞态、取消和已恢复 attempt 在全量基础日志中保留。Sentry Logs、详细 span、调试字段和堆栈补充允许按策略选路或采样。基础记录的覆盖率独立于 Sentry tracing 的采样决定。一个事件一次生成，跨输出和重放共用 event_id，查询按 ID 去重。
- 允许按环境、模块、操作、结果和错误码选择输出，基础记录策略固定全量。额外诊断配置采样档位、有效期、速率与容量。Pino 承担 Railway JSON 可读出口，Sentry 有效配置才启用。优先验证 level、message 及字段检索并保留已有查询字段。Railway 官方当前单副本上限 500 行/秒，容量按峰值请求/作业数、每链路操作数、每条字节数和开始/终态条数计算，所有基础记录计入预算。
- 热路径同步工作只做有界提取、计时和内存投递，无阻塞式远端等待或 flush。基础记录使用独立容量与高优先级投递，诊断详情先降级。远端插件独立有界队列、并发、超时和故障隔离。各层记录接受、投递、重试、丢弃数量及队列最老年龄，通过独立指标和限频自诊断暴露故障。接受进程内事件、写 stdout、被平台收录与可检索分别验收。
- 仅内存队列和 stdout 在进程崩溃、持续背压及平台限流下有丢失窗口。全量覆盖验收要求所有基础记录在约定负载和故障窗口内可检索；发现缺失即失败。容量不足时，设计需要补充独立全量日志出口或带持久化缓冲的采集端，承接全量基础记录，Railway 保留请求终态及排障摘要。推荐将此可靠投递方案纳入整体审批，明确存储位置、磁盘配额、故障缓冲时长、确认/重放、保留期和可检索延迟；当前尚未核对部署能力与成本。任意时长故障下的零丢失、有限存储及业务始终无阻塞无法同时承诺，故障上限必须写进最终验收。
- 不从观测层重试业务操作或改变 deadline、AbortSignal、数据库连接、幂等、事务提交点和补偿。支付超时/网络中断需保留结果未知及原对账关联。Shutdown 在停止接收、drain 后有界 flush，沿用退出码并确保超时仍退出。SDK/插件异常测试覆盖同步 throw、异步拒绝、挂起、队列溢出和坏配置。
- 排查先按 request_id 找 HTTP 终态，按 trace_id 和父子 span 查询全量基础调用记录，按安全业务键串起后续任务，最后查看 Sentry Issue 与发布版本。全量 P95、错误率用现有指标作分母，Sentry 采样 trace 提供补充详情。Railway 平台 HTTP 状态与应用日志分别核对。

## 全链路完整性验收

- 每个 HTTP/作业入口均能定位开始和唯一逻辑终态。每个业务、DB、第三方操作和重试 attempt 均有可关联的终态记录，基础字段包含操作标识、父标识、时间、耗时、结果和安全错误摘要。
- 用独立测试计数和受控调用图核对基础记录，校验成功/失败请求、并发分支、重试、回调、后台补偿、SSE、断连、鉴权与解析早退。覆盖率以实际执行数为分母，不能只统计已输出日志。
- 区分运行中、正常结束和缺失终态。进程崩溃后只能将尚未完成的链路标为中断或未知，恢复事件保留独立类型和原关联，不能伪造业务成功/失败。
- 验证关闭 Sentry、采样率为零、诊断降级和生产日志级别提高时，基础记录仍可查。针对允许的生产配置执行同一套完整性测试。
- 峰值吞吐、插件超时、断网、采集端重启、缓冲耗尽与服务关闭分别验证。必须记录故障期间的可检索率、遗漏、重放去重、恢复耗时和业务 P95；基础记录缺失触发停止发布。最终容量与持久化选择批准前，整体方案保持待评审。

## 实施顺序与验收

1. **基线与契约**。逐路由建立失败分支矩阵与旧消费者核对表，逐出站点盘点并登记责任人。抽样统计现有每请求日志量、Railway 格式、丢弃和重复率；核对实际部署版本、Sentry SDK 自动捕获、代理状态及 Sentry/Grafana 基线。形成可执行 P95 声明和模块影响清单后提交 Trellis 评审。
2. **核心与 HTTP 切面**。接入日志 facade、Pino/Sentry 适配器和异常出口。先在 TEST 以健康、鉴权、可控 404/500 与一条普通路由验证；新旧终态按路由组互斥。逐批迁移 HTTP 错误和老日志入口，校验共享契约及所有消费者。
3. **数据库与出站**。复用 Supabase 和 Prisma 注入点，迁移代理、Storage、pg、第三方和脚本。在隔离环境验证返回失败、超时、异常、取消、事务回滚、连接归还和故障下响应一致；对照现有 DB 指标和慢查询诊断。
4. **高风险链路**。独立批次迁移生成/SSE/图片/语音、支付 webhook/建单/查单/对账、后台任务。核对首字、断流、并发、兜底、重复回调、验签、金额冲突、未知建单和单次结算。原状态机、协议与授权边界作为回归基准。
5. **收口与门禁**。接入 CI Quality Gate。使用静态检查禁止新增裸 console、Pino/Sentry 业务直写、未登记对外错误码和绕过现有观测入口的客户端。以路由、repository、provider、job 覆盖清单与现有例外基线审查增量；临时例外需理由与移除条件。契约测试断言 status/code/日志/协议一致，动态验证关插件、并发隔离、脱敏、限流和单终态。同步 AGENTS、Backend spec、README、架构、Railway 排障手册和示例配置。

每批部署先 TEST，随后按模块逐步启用，兼容现有消费者后才清理旧码与旧字段。观察真实状态错配、响应/计费/回调异常、重复或泄漏、掉日志、CPU、内存、队列和 P95，发现回退时停批，优先关闭远端与详细采样，必要时回滚独立发布单元。日志观测本身无需数据回填，已写入的业务记录仍按既有恢复流程处理。

## 性能门禁

覆盖 Backend 全部 API 与消费它们的 Android/iOS 页面，优先大厅/角色、聊天、钱包/充值、图片/语音、短剧、创作者。Android/iOS 分开记录 page-ready P95，API 按路由组与 release 记录 P95，普通 JSON 全响应、SSE 首字/完整终态和媒体分开。当前任务未获得同版本、同口径生产样本，三类基线均为 null（无可见样本）。提议沿用既有工程基准，普通 page-ready/API 看 2 秒预算与相对回退，聊天看首字/完整回复既有指标。建议同路由、平台及负载下 P95 回退不超过 5%，连续两个完整 24 小时窗口，每组 N<100 延长观察。使用现有 Grafana/Faro、Sentry Metrics 与同构 TEST 对照；阈值随用户评审和基线定稿写入 task.json meta.mobile_performance，样本不足不得记通过。

执行 `pnpm --filter @miniapp/backend typecheck`、backend/shared 相关测试、全消费者 `pnpm -r typecheck`、适用 lint/build、`pnpm lint:complexity` 和 Quality Gate。建议纳入本地重复验收，复用 ui-tests 的 @chat、@profile、@image、@drama 与现有 creator 流程，补 404/依赖失败/断流恢复/重复订单提示。真实商户回调、供应商首字、Railway/Sentry 检索及 Android/iOS 真机另在目标环境验证。
