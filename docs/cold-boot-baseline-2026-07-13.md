# ST 冷启动耗时 Baseline（2026-07-13）

> 本文是**冷启动耗时专项优化的基准线**，为后续排查/优化提供统一对照口径。
> 数据来自 pro 真实用户流量（非开发机自测），采样窗口覆盖 Tier-1 并行化上线之后。
> 后续每轮优化复测，均以本文的分位数为 before 基线，按相同口径（干净冷启动、分平台、看中位数+P75/P80）对比。

> `iframe-boot-firstloadinit-parallelization.md`（Tier-1/2 方案与核验）、

**"干净冷启动"定义**：`bridge_start→st_ready` 相位完整，且无停摆重载标记（无 `click_stall_reload`、`iframe_onload` 尝试次数 ≤1）。

**分段定义**（三大相位，绝对时钟相减）：

| 相位                 | 起点→终点                      | 含义                                                        |
| -------------------- | ------------------------------ | ----------------------------------------------------------- |
| ① iframe_load(网络)  | `bridge_start → iframe_onload` | /tavern 文档 + 同步静态资源(已缓存) + 跨洲首连              |
| ② st_script+ext_init | `iframe_onload → st_handshake` | 手机解析执行 lib.js+~200 模块(CPU) + firstLoadInit 前段网络 |
| ③ st_app_boot        | `st_handshake → APP_READY`     | boot 后段：扩展窗口 + 角色列表 + settings + 尾段            |

**重要口径提醒**：

1. 真实用户群（以中低端 Android 为主）比开发机基线慢。此前文档里"干净冷启动 ~13s"是开发机实测；pro 真实流量 P50 就有 15.9s，重尾更明显。**后续目标值以本文分位数为新基线，不要再拿 ~13s 做对照**。
2. 冷启动指标**必须报中位数 + P75/P80**，只看均值或单样本会被重尾误导。
3. Tier-1 前样本量太小（49 条，且含开发自测），不具备可比性，本文不做 Tier-1 前后对比；Tier-1 生效证据见 §四瀑布数据（92% 样本三请求起点重叠）。

## 三、平台对比与瓶颈定位

### 整体对比

|              | Android P50 | iOS P50 | 差异与解读                                                                  |
| ------------ | ----------- | ------- | --------------------------------------------------------------------------- |
| 全长         | 16.5s       | 13.9s   | Android 慢 ~2.6s，且重尾更陡（P90 34.4s vs 26.4s）                          |
| ① 网络       | 2.9s        | 3.6s    | iOS 略慢但**尾部更稳**（P90 5.5s vs 8.2s）；Android 网络重尾是慢网/弱网设备 |
| ② script+ext | 5.7s        | 5.1s    | 接近；这段是手机 CPU 解析成本，Android 机型离散度更大（max 23s vs 11.3s）   |
| ③ boot       | 7.2s        | 5.4s    | **Android 与 iOS 的主要差距在这里（+1.8s）**，集中在扩展窗口                |

### 各平台瓶颈

- **Android（主力，决定整体体感）**
  - 头号瓶颈：**③ boot P50 7.2s**，其中**扩展窗口 3.8s** 是最大单块；重尾极陡（③ P90 15.8s、max 47.8s）。
  - 次瓶颈：**② script+ext 5.7s**，纯 CPU 解析，机型离散度大。
  - ① 网络 P50 仅 2.9s 但尾部到 8.2s/最高 47s，是弱网设备贡献，属长尾而非中位问题。
  - **结论：Android 优化优先级 = 扩展窗口 > 解析段 > 网络长尾。**

- **iOS（次要人群，但设备性能更均匀）**
  - 三段更均衡：② 5.1s ≈ ③ 5.4s > ① 3.6s；重尾明显轻于 Android（全长 P90 26.4s）。
  - 头号瓶颈仍是 **② 解析段 + ③ 扩展窗口**，但绝对值和离散度都更小。
  - ① 网络虽 P50 最高(3.6s)，但 P90 只有 5.5s，稳定，非攻击点。
  - **结论：iOS 已相对健康，优化收益不如 Android 显著；扩展窗口并行化同样受益。**

### 全局优化靶点（承接 `iframe-cold-boot-progress.md` §三）

1. **扩展窗口并行化**（`activateExtensions` 去循环内 `await`）——全平台 boot 后段最大单块（Android 3.8s / 全平台 3.4s，P80 7.5s），是**当前最大且未动的靶点**，量级远超 Tier-2。风险：改扩展执行顺序（loading_order 语义、握手时机），需谨慎。
2. **boot 尾段跳过"恢复上次聊天"**（merger 强制清空 `active_character`，零 vendor）——压 settings→APP_READY 尾段。
3. **② 解析段**：手机 CPU 物理成本，只能减少解析总量（禁扩展已做）或就近部署间接改善，不可精简 bundle（ST 锁 commit）。
4. **① 网络长尾**：中位可接受，长尾靠就近/多区域部署（中期立项）。

## 四、Tier-2 收益量化（后段并行组瀑布，233 样本）

来自 `[iframe-timing-wf]` 瀑布行，后段并行组 `avatars`/`characters`/`backgrounds` 三请求：

- **Tier-1 生效证据**：214/233（92%）样本三请求起点重叠在 500ms 内（改前为依次错开）。
- 各请求耗时：

| 请求                     | P50     | P75     | P80     | P90     |
| ------------------------ | ------- | ------- | ------- | ------- |
| /api/avatars/get         | 0.5     | 0.7     | 0.7     | 0.9     |
| /api/characters/all      | 0.6     | 1.0     | 1.1     | 1.4     |
| **/api/backgrounds/all** | **0.6** | **2.0** | **2.3** | **2.7** |

- **Tier-2（跳过 getBackgrounds）实测节省**（backgrounds 结束点超出另两者最晚结束点的部分）：

|      | P50 | P75 | P80 | P90 |
| ---- | --- | --- | --- | --- |
| 节省 | 0.0 | 0.7 | 1.1 | 1.6 |

- backgrounds 是并行组尾巴（>100ms）的样本占 36%；47% 样本删了不省。
- **性质：尾部收益，非中位数收益**。正好压 Android 重尾，验证 Tier-2 应看 P75/P80 而非中位数。
- Tier-2 已落地：commit `d88639e`（分支 `test`），代码 + NOTICE.md 登记齐全。

## 五、复测口径（后续每轮遵循）

1. 采样：`railway logs -s stminiapp -e production` 按部署 ID 回捞 `--filter "iframe-timing"`，累计 ≥100 个干净冷启动再下结论。
2. 报告：分平台（至少 Android/iOS）分别报 P50/P75/P80，全平台汇总一份。
3. 归因：停摆/重载样本单列，不混入基线。
4. 直接证据：并行类优化看 `[iframe-timing-wf]` 瀑布行起点是否重叠；跳过类优化看 nginx 是否不再出现对应请求。
5. 对照：以本文 §一/§二 分位数为 before。

> 分析脚本：`analyze.py`（分位数）、`analyze2.py`（平台+瀑布）、`analyze3.py`（分平台节点），
> 会话期间存于 `/tmp/st_timing/`，需长期保留可迁入 `ops/`。
