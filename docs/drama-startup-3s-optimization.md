## 1. 要解决什么

1. 播放与缓存播放要快（含二次进入、往回滑）
2. 进详情 / 放映要快（勿长时间黑屏）
3. 边看边下流畅（少卡顿；换集 / 换剧也快）

硬指标（`docs/drama-playback-timing.md`）：首帧且 `playing`；**含放弃** 3s 达标；**双端**都要 ≤3s。

## 2. 瓶颈（在 #932 之后如何读）

### 2.1 文档基线（#932 **前**窗口，仍作对照，不能当「现状终值」）

| 维度               | Android         | iOS             |
| ------------------ | --------------- | --------------- |
| 全入口 3s 达标     | 83.1%           | 64.5%           |
| 全入口含放弃 P95   | ≥ **3820ms**    | ≥ **7860ms**    |
| cover 3s / P95     | 70.8% / ≥4520ms | 48.8% / ≥8870ms |
| `/play` 客户端 P95 | ~1140ms         | ~1576ms         |

慢样本构成（Android 会话首播，清单预取前）：取址 24% · 主+子清单 18% · 首片 TTFB 14% · 首片下载+入缓冲 **40%**。

### 2.2 #932 之后应如何看数

- 清单预取命中时，**主+子清单 18%** 应接近抹掉；取址在 cover 命中时也常变为 cache/inflight。
- **剩余主因仍是首片（约半壁）+ 未命中预取时的 `/play` 跨境 RTT + iOS 原生不可控预取。**
- **修订要求：** 开工 Batch 1 前，用 Faro 按 `app_version`（含 #932 后代）重算「清单预取后」基线，并按 `diagnostics.hls.prefetch` 分层 hit/miss。11-19 门禁对比窗用**新基线**，避免与 #932 效果混算。

### 2.3 已保留的能力（勿推倒）

Stream 多码率 HLS · 主清单内联 · #932 播放资源缓存 · `startLevel:0` · 续播对齐 · preconnect · 固定 `POST /api/dramas/play` · 封面 intent 并行。

        ▼

附加项 **A–G** 的设计细节见任务 `design.md` §3.5；清单与取舍见下文 §9。

### 3.1 为何仍要三支柱（#932 不够）

| 支柱                    | #932 之后仍缺什么                                                                            |
| ----------------------- | -------------------------------------------------------------------------------------------- |
| iOS 默认 hls.js         | 未开 env 时**几乎吃不到**子清单预取（`prefersHlsJs()` 才拉子清单）；首块 loader 也落不到原生 |

| #   | 优化点                                    | 证据                                                                                                | 打哪一段      | 影响                       | 成本                                                      |
