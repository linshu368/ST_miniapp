# 短剧双端起播 ≤3 秒优化说明

> 状态：规划已立项（`.trellis/tasks/11-19-drama-startup-3s-edge/`）  
> 硬门禁：Android / iOS **含放弃**起播 P95 ≤ **3000ms**（3s 达标率 ≥ 95%）  
> 日期：2026-11-19

本文把「为什么要做、做什么、预期到多少、怎么验收」写在一处，便于产品与工程对齐。详细需求见任务 `prd.md`，技术设计见 `design.md`，执行顺序见 `implement.md`。

---

## 1. 要解决什么

用户侧三条体验目标：

1. **视频播放和缓存播放要快**（含二次进入、往回滑）
2. **进入详情/放映页要快**（不要长时间黑屏）
3. **边看边下要够快、整体流畅**（少卡顿、换集/换剧也快）

工程硬指标与现有看板一致（`docs/drama-playback-timing.md`）：

- 成功 = **首帧且 `playing`**
- 主门禁 = **含放弃**的 3 秒达标（等价含放弃 P95 ≤ 3s）
- 平台 = Telegram 内 Android + iOS 都要达标

## 2. 现在卡在哪（证据）

### 2.1 基线（Faro，与 `11-18-drama-playback-prefetch` 同窗口口径）

| 维度               | Android      | iOS          |
| ------------------ | ------------ | ------------ |
| 全入口 3s 达标     | 83.1%        | 64.5%        |
| 全入口含放弃 P95   | ≥ **3820ms** | ≥ **7860ms** |
| cover 3s 达标      | 70.8%        | 48.8%        |
| cover 含放弃 P95   | ≥ **4520ms** | ≥ **8870ms** |
| `/play` 客户端 P95 | ~1140ms      | ~1576ms      |

### 2.2 慢样本构成（Android 会话首播）

| 阶段              | 占比 | 含义                                                     |
| ----------------- | ---- | -------------------------------------------------------- |
| 取址 `/play`      | 24%  | 大部分是浏览器到 Railway（新加坡）的 RTT，不是业务逻辑慢 |
| 主清单 + 子清单   | 18%  | 已有内联主清单 + 封面清单预取，仍有冷 miss               |
| 首片 TTFB         | 14%  | CDN/PoP 冷或距离远                                       |
| 首片下载 + 入缓冲 | 40%  | **最大头**；约 280KB/最低档首片                          |

结论（与 11-18 任务一致）：**只做清单预取到不了 95%**；要双端都 ≤3s，必须同时打「取址跨境 RTT」和「首片」，并且 **iOS 必须走可控的 hls.js**，否则预取/缓冲策略落不到原生播放器上。

### 2.3 已经做过、仍然保留的优化

- Cloudflare Stream 多码率 HLS
- 后端主清单内联 + 进程预热
- 片库可见封面 / 按下 / intent 预取 `/play` + 子清单
- `startLevel: 0`、续播分片对齐、Stream preconnect
- 点击与取址并行（固定 `POST /api/dramas/play`）

这些继续保留，本方案是在其上叠加，而不是推倒重来。

## 3. 业界对照（我们怎么借鉴）

| 来源          | 做法                                        | 落到本项目                                    |
| ------------- | ------------------------------------------- | --------------------------------------------- |
| YouTube       | 低档起播 → 预取 init + 首片 → 再 ABR        | hls.js `startLevel:0` + 首块预取 + 稳播升档   |
| 抖音 / TikTok | 下 N 部只预下约 1MB 首块；过期取消          | 可见封面/下一部「撒点」只预取首片级，有界并发 |
| 抖音短剧插件  | `preloadResourceVideo` 限制大小与任务数     | 单块字节上限 + background/critical 优先级     |
| hls.js        | `startFragPrefetch`、起播压低 buffer 再抬高 | 写入统一装载层配置                            |

不照搬：完整离线下载、默认双播放器预解码（内存贵，作达标后增强）、自建转码替代 Stream。

## 4. 总体方案：三支柱

```text
                    ┌─────────────────────────┐
                    │  ① 双端统一 hls.js       │
                    │  iOS 默认 MMS + hls.js   │
                    └───────────┬─────────────┘
                                │ 同一套 loader / 缓冲 / 预取
          ┌─────────────────────┼─────────────────────┐
          ▼                     ▼                     ▼
 ┌────────────────┐   ┌──────────────────┐   ┌────────────────────┐
 │ ② /play 边缘签 │   │ ③ 首片边缘预热   │   │ 客户端首块预取     │
 │ CF Worker JWT  │   │ 暖 PoP / 可选 R2 │   │ 视频+音轨+init     │
 └────────────────┘   └──────────────────┘   └────────────────────┘
          │                     │                     │
          └─────────────────────┴─────────────────────┘
                                ▼
              进页不挡播 + episode 提前取址 + 边下边播水位
                                ▼
                     双端含放弃 P95 ≤ 3000ms
```

### 4.1 支柱 ①：双端统一 hls.js

- **Android**：已是 hls.js（MSE）。
- **iOS**：生产默认改为 hls.js（Managed Media Source），与 Android 共用预取、首块缓存、缓冲水位。
- 原生 HLS 仅作无 MMS 时的降级，**不作为门禁承诺路径**。

没有这一步，iOS 侧「首片预取 / 自定义 loader」基本落空，双端 ≤3s 无法成立。

### 4.2 支柱 ②：`/play` 边缘化

- 现状：客户端 → Railway（新加坡）签 Stream JWT，P95 ~1.1s，约 90% 是网络。
- 目标：Cloudflare Worker 靠近用户，用 Backend 短时 **`edge_ticket`** 鉴权后本地 RS256 签 Stream JWT，返回兼容的 `DramaPlayback`。
- **已定鉴权**：Telegram / 会话校验只在 Backend；进剧场后由 Backend 发 TTL 5–10 分钟的 `edge_ticket`（可与目录捎带，可刷新）。Worker **不验 `initData`、不持 bot token**，只验 ticket 后查 KV 并签名。
- KV 保存有界的 `dramaId+videoId → stream_uid` 快照（Backend 同步），Worker **不查业务主库**。
- ticket 无效/过期或 KV miss → 回退原 `POST /api/dramas/play`，可灰度、可关。

预期：边缘命中时取址客户端 P95 ≤ **500ms**。

### 4.3 支柱 ③：首片边缘预热 + 客户端首块预取

**边缘预热（暖 CDN）**

- 定时对热门 uid：拉「最低档视频首片 + 默认音轨首片 + fMP4 init」
- 让 Stream 边缘节点先有对象，压用户首片 TTFB
- 可选增强：首块进 R2，仅极端冷区辅助（非默认带宽中枢）

**客户端预取（对齐点击）**

- 在现有「/play + 子清单」缓存上，再预取起播那一片（+ 音轨 + init）
- 触发：可见封面（background）、按下/intent（critical）、播放中下一部撒点
- hls.js loader 命中则起播不再等首片网络
- 单块约视频 ≤512KB、音轨/init 更小；总内存有硬顶

这是对慢样本里 **54% 首片时间** 的直接打击。

### 4.4 配套（进页与流畅）

| 项          | 做法                                                       |
| ----------- | ---------------------------------------------------------- |
| 进详情/放映 | library hydrate 不挡住播放器首 paint；封面占位到首帧       |
| 选集/续集   | 与封面一样，点击当下提前 `/play`                           |
| 边看边下    | 起播短缓冲（约 4–8s）→ 稳播 20–30s；弱网/rebuffer 锁最低档 |
| 换剧        | 当前缓冲足够后，只预取下一部「清单 + 首块」                |

## 5. 预期效果（规划数字，发布后实测为准）

> 口径均为**含放弃**。不得用「只算成功」的 P95 代替门禁。

| 阶段                                      | Android 全入口 P95          | iOS 全入口 P95              | 说明           |
| ----------------------------------------- | --------------------------- | --------------------------- | -------------- |
| 基线                                      | ≥3820ms                     | ≥7860ms                     | 现网           |
| 仅客户端（hls.js 默认 + 首块预取 + 进页） | ~2700–3200                  | ~4500–5500                  | iOS 仍难稳 ≤3s |
| + 边缘签 + 首片预热（本方案完整）         | **≤3000**（预期 2400–2800） | **≤3000**（预期 2800–3000） | 硬门禁         |
| 二次进入同集（缓存命中）                  | 常见 &lt;1s                 | 常见 &lt;1s                 | 体验目标       |

分层对照（非替代门禁）：

- cover 达标率：Android 71% → **≥92%**；iOS 49% → **≥92%**（分母单独报）
- `/play` 边缘命中 P95：1140ms → **≤500ms**

若完整三支柱上线后仍差一线，优先加「预热名单 / R2 首块」，**不**把门禁改回单端。

## 6. 明确不做

| 不做                    | 原因                                        |
| ----------------------- | ------------------------------------------- |
| 完整离线整集下载        | 签名 TTL、存储与审核成本高，Mini App 收益差 |
| 自建转码替代 Stream     | 已有多码率 HLS，重复建设                    |
| 全量 SW 劫持媒体        | WebView 兼容与排障成本高                    |
| 同步阻塞 `/play` 等清单 | 历史已证明伤害冷视频                        |
| 首期上双播放器预解码    | 内存/解码争用大；达标后再作体验增强         |

## 7. 发布与回滚

建议切片：

1. **PR-A** 诊断 + iOS 默认 hls.js + 客户端首块预取 + 进页/episode（先走 Railway）
2. **PR-B** 边缘 Worker 签发 + 前端优先边缘 + 灰度
3. **PR-C** 首片边缘预热 Cron
4. **验收窗** ≥7 天 Faro；不足样本延长，不补零

回滚开关（互相独立）：

- 关边缘路由 → 全部回 Railway `/play`
- 关首块预取 → 回清单预取行为
- iOS 回退原生 HLS flag（仅应急；门禁声明路径会失效，需同步沟通）

## 8. 验收清单（发布后）

- [ ] Android 全入口含放弃 P95 ≤ 3000ms，达标率 ≥ 95%
- [ ] iOS 全入口含放弃 P95 ≤ 3000ms，达标率 ≥ 95%
- [ ] cover 双端达标率 ≥ 92%（分层报）
- [ ] 边缘 `/play` 命中时客户端取址 P95 ≤ 500ms
- [ ] iOS 默认 engine 为 hls.js（MMS）
- [ ] 首块命中组 3s 达标显著高于未命中组
- [ ] 失败率 / 快进恢复 / 剔除占比护栏通过
- [ ] 预取 discarded 流量可估算，弱网不拖垮剧场首屏

查询入口：Grafana `st-engineering-drama` + Loki `drama.startup_diagnostic`（字段含 prefetch segment / delivery path；禁止日志 URL/token）。
