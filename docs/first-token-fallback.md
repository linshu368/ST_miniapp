# 首 token 兜底与人工观察

本文以客户端首字交付 v4 为观测标准，首发与兜底竞争交付为当前生成策略。实际部署状态以本任务发布核对为准；历史 v1-v3 数据不重算、不混入 v4，竞争策略上线前后按实际发布时间分窗。尚未实现 AI 自动调参。

## 运行与计时

| 配置               | 初始值                                         | 管理位置                       |
| ------------------ | ---------------------------------------------- | ------------------------------ |
| 兜底型号           | OpenRouter `deepseek/deepseek-v4.1-flash-1017` | 运营配置 → 兜底配置            |
| 每型号启动兜底阈值 | 4000ms                                         | 同页，各型号分别编辑           |
| 兜底预留时间       | 2000ms                                         | 同页，人工调整                 |
| 全局首 token 上限  | 10000ms                                        | 同页，人工调整                 |
| 超时率目标         | 1%                                             | 观测目标，不是可直接控制的结果 |

配置沿用模型目录草稿，先保存再发布；本轮冻结型号、版本、时限和报价。新增模型默认4000ms；不足150个有效请求不适合自动调整。本期只支持人工观察与发布。

首发从实际派发 POST 计时，到该型号阈值仍无有效首 token 就启动一次兜底，首发继续竞争。所有可用尝试共享原来的绝对总截止；首发超过4秒、兜底超过2秒仍可获胜，只要未过共同截止。最先产生有效正文或已开启公开思考首 token 的一方负责交付，另一方立即 abort/cancel，不能把两路混进一条回复。

`fallback_timeout_ms` 保留字段名与2000ms默认值，现表示前置处理过慢时的兜底启动预留：启动时刻取“首发派发时刻＋型号阈值”与“总截止－预留时间”的较早者。若已经过了启动时刻，就立即启动；前置耗尽预算时不能承诺仍有完整2秒。它不再限制兜底自身运行时长。用户总时间仍包括前置、模型请求、网络和客户端更新，并发尝试的耗时不能相加。

首字前明确 HTTP/连接/流错误、refusal、空结束直接启用一次兜底；已有有效正文/公开思考后不再启动另一模型。同型号静默等待不并发重发，继续至总截止；明确失败允许一次顺序重试。两路都失败时立即收口，不空等总截止；显式停止与总截止终止全部未获胜尝试，已获胜回复仍可正常生成完毕。

深度思考使用每轮冻结的开关。开启后可读思考首 token 与正文等效；关闭只算正文。空白、headers、role、等待标题、加密内容不算。

## 客户端首字交付 v4（2026-10-28）

新客户端用 `client_committed_v4` 替换屏幕可见检测：提交动作 → 本轮正文或已开启的公开思考首次提交到 React 消息界面状态。它是业务侧交付口径，不是像素/阅读证明。滚动位置、气泡是否在视口、思考是否折叠均不参与；received 仅供分段排查，不能取消截止。提交时间达到当轮 deadline 即归超时，计时器延迟不能变成超时后的成功。

send/regenerate 携带可选 `first_token_measurement`；后端通过既有 begin RPC 的同一次 INSERT 写入现有 measurement_method，缺报请求仍属于 v4。每轮首次结果不可改写；离页/后台独立终态，生成仍可继续并在返回时恢复。迟到回复可展示但不改写已超时记录。旧 v1-v3 保留兼容，历史独立筛选。

统计复用现有 first_token_visible_ms 列承载按版本定义的时长，不增加表、cron、轮询或逐 token 写入。主指标为前台已知结果的无字时间截断率；成功分布只取截止前已交付样本，离页/缺报及覆盖率同时显示。后台和缺报不能当成功，不用服务端或供应商 latency 填补客户端数据。竞争策略保留4秒触发阈值、2秒预留、10秒总预算与1%目标，v4观测起止点不变。

系统超时免费、免费预留释放；主动停止沿原报价/权益一次结算。计费继续用一次交付结果和服务端持久化终态保障正确性，不依赖滚动/阅读。已结算记录只补调用元数据，不重进计费；归档明细依永久去重返回显式 archived 终态，不重扣、不伪造账单；failed 进入已有有界退避。缺报沿用原预算+15秒保守收口，不增加新计费任务。

v4观测与归档计费迁移为 `20261028_client_committed_first_token.sql`、`20261028_llm_archived_charge_result.sql`。本次竞争策略在其后前向扩展既有 attempt 与单赢家选择，发布证据见任务 `.trellis/tasks/10-28-first-token-race/`；1%是否达成须由上线后的 v4 样本判断。

## 数据口径与解释

`experience.chat_generation_requests` 每个请求/revision 一行；`chat_generation_attempts` 只记录首发与兜底。保持原表、身份、快照及有界写入。败方只保存停止前已经收到的有界展示文本/公开思考片段，合入原 attempt 终态观察；不为排查继续生成、不逐 token 落库、不阻塞获胜首字。片段不进入用户消息、恢复、prompt 或计费，Grafana只读指标列不能读取片段。旧列 `first_token_visible_ms` 在 v4 中表示客户端消息提交耗时；必须连同 measurement_method 解释。

| 指标               | 起止点                                   | 用途                                        |
| ------------------ | ---------------------------------------- | ------------------------------------------- |
| 客户端首字交付耗时 | 点击提交 → 有效 token 提交到消息界面状态 | 用户等待主分布，包含首发/兜底全过程         |
| 客户端接收耗时     | 同一次点击 → 首个有效内容被解析          | 诊断接收与提交差距，不作为成功标准          |
| 首发/兜底实际首字  | 各自实际派发 → 后端获得有效 token        | 排查调用阶段，失败/未等到不填阈值作真实耗时 |
| 服务端写出         | 路由入口 → 首个内容写入 SSE              | 排查后端，不能证明客户端收到                |
| 供应商 latency     | 供应商自身定义                           | 仅供对照，缺失不填零，不代替业务耗时        |

各端只用自己的单调时钟；客户端与服务器差值包括网络、客户端准备与更新，不应全部归因于网络。浏览器暂停/忙碌时不能承诺提示精确在第10000毫秒出现；恢复后的绝对时长校验仍判超时，绝不改成慢成功。

请求身份需同时匹配用户、会话、history、request_id、revision。晚绑定身份不延长原计时；一次终态上报可沿已有有限重试重发相同结果，数据库重复回报不 UPDATE。旧客户端在兼容期继续旧规则。

## 看板与人工判断

[业务看板](https://ea3213527545.grafana.net/d/chat-first-token-manual) 默认 v4，最近24小时、北京时间、5分钟刷新，按所选型号筛选。复用现有最小只读账号、事实视图及有界时间窗；不增加统计刷新任务。

- **无字时间截断率**：前台已知结果里，未交付首 token 且因模型阶段/服务端总限/客户端总限结束的请求比例。其他上游失败列入已知结果分母并单列，不能冒充时间截断。
- **首字分布及P50/P90/P95**：只取 v4 前台已交付且小于该轮上限的真实客户端时长。成功分布必须和失败率、缺报数一起读，不能只看成功者。
- **兜底触发率**：触发兜底的请求/全部有效请求；触发后首发获胜或两路都失败也算。两次尝试只计一个请求。
- **已交付样本中兜底占比**：实际由兜底交付的前台成功样本/全部前台成功样本，与触发率分开看，不能把启动兜底当作已经替代首发。
- **离页/后台、缺报和覆盖率**：单列。没有回报不能推断成功；指标不能覆盖未到服务器、鉴权/开轮失败的所有点击。缺报多时不能宣称整体达成1%。

v3历史出现过已收到后等待视口几十秒、以及超时后重新改成 observed；这批数据不能直接与 v4 比较，也不会做历史回填来“改善”结果。竞争策略保持v4观测口径；看板“首发等待”旧列名在新策略下表示启动兜底阈值，“兜底预留时间”在上线前的历史记录仍表示旧兜底硬时限。以实际生产上线时刻分窗，不能只按相同4/2/10数值把前后策略合为一个参数组。

每24小时看过去24小时。调参只比较同一型号、相同口径及参数组，不跨型号排名；150是样本门槛，不是所有小参数组都可靠的保证。未来损失函数可考虑3秒内无惩罚、兜底率20%以内无惩罚、超时率1%以内无惩罚，但系数/判断/自动发布本期留空。

## 计费与恢复

每轮同一个 charge_id、同一份原型号报价/VIP/免费权益，只对获胜回复结算一次，败方不另扣用户星尘。供应商可能已产生输入或在途 token 成本，立即停止败方减少后续生成，不能承诺上游零费用。系统无首字超时免扣星尘、不消费免费次数；主动停止已报价轮按原权益结算，不增加扣费提示。只有思考而没有自然完成正文不自动收费。超时使用轻提示“这次回应稍慢，再试一次吧”。

离页不取消服务端生成；返回从原消息身份恢复，不重新生成。离页后完整保存的正常回复可按原价结算。真正缺报继续 pending，原总预算+15秒后保守免收；宽限只供结算，不延长用户等待。已完成/免单的账务不被晚到回报或供应商 stop 改写。

旧明细保留最近100条的清理策略下，永久 dedup 是已结算证据。新收费函数先只读确认已完成明细/去重，再处理未完成的交付资格；已归档返回明确状态/金额，不重建账单。未知唯一冲突保留错误。供应商元数据不足与账务未完成分开，已settled不重进收费；失败进入原任务退避，避免每30秒反复调用。

## 验证、发布与恢复

本地 `bash scripts/test-first-token-fallback-local.sh` 在一次性 PostgreSQL17/PostgREST 验证兼容、身份/权限、重复报告、迟到免扣、用户停止、免费额度和账单归档；不读取应用凭证、不连远端。前后端单测与 `pnpm test:ui --grep @chat` 验证真实页面状态及滚动不影响交付。模拟UI不能替代真实钱包、供应商与Telegram宿主。

竞争策略迁移先TEST后生产，保留5秒锁/30秒语句上限；不做历史回填、不新增cron。在既有 attempt 添加有界诊断列时，将Grafana整表读取收窄为旧指标列授权，片段不进分析视图。先合dev验证，再生产迁移 → Backend/Admin → 看板文案；配置数值未变，无需重新发布运营配置。回退应用保留新增列、函数兼容能力及已结算事实，不删除账务或统计历史。
