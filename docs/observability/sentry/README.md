维护日期：2026-11-19。适用项目：`wangqiao / st-miniapp`。本次交付流程与模板，按用户确认采用北京时间每周二、周五15:00汇报，暂不启用自动定时任务。

## 一、连接与取数边界

1. 使用现有Sentry连接；组织 `wangqiao`，项目 `st-miniapp`，区域 `https://de.sentry.io`。本次只读能力已核验，不表示已检查全部项目、全部后端错误、告警配置或SDK覆盖。
2. 先使用 `find_organizations`、`find_projects` 确认目标。拿到具体Issue或事件链接后先用 `get_sentry_resource`，不重复猜测组织。
3. 组织或权限变化时重新确认。认证失败时修复连接授权，不向对话、Markdown或源码粘贴密钥。
4. 主统计使用Errors数据集的 `error/fatal`；Logs中的error日志、HTTP失败、性能问题和warning另列，不与Errors相加。一条业务故障可能在多个数据集中出现。
5. 先以 `environment:production` 取数，再核对真实服务、正式origin和release。正式前端origin已知为 `https://app.themijing.com`；该域名只用于前端来源核验，不限制后端事件。后端以服务与部署证据确认，证据不足列入“来源未核实”。
6. 聚合只返回计数、Issue、平台与release等允许字段。必要的脱敏事件摘要可包含时间、错误类型、路由模板和安全的栈帧位置；不保存用户身份、消息正文、请求参数、签名URL、token、完整initData或原始局部变量。链路信息沿用现有脱敏出口，不扩展采集字段，见[现有可观测性约定](../../backend-observability-runtime.md)。

## 二、时间范围与周二、周五节奏

全部窗口采用北京时间 `Asia/Shanghai`，内部同时记录UTC，并使用左闭右开区间 `[开始, 结束)`。以事件发生时间为准，补报可能使历史计数变化。

| 时间                      | 工作                                                       | 输出                   |
| ------------------------- | ---------------------------------------------------------- | ---------------------- |
| 每个工作日上午，建议09:30 | 人工触发增量排查，处理新增、回归及待复验问题               | 更新问题清单与任务     |
| 每周一                    | 对周末问题和上期积压排序，确认本周负责人及目标             | 本周修复清单           |
| 每周二15:00               | 汇报自上周五15:00至本周二15:00的错误及修复状态，通常96小时 | 错误报告、修复情况说明 |
| 每周五15:00               | 汇报自本周二15:00至本周五15:00的错误及修复状态，通常72小时 | 错误报告、修复情况说明 |
| 发现P0或持续P1            | 立即排查和升级，不等固定汇报日                             | 故障记录、处置进展     |

第一次汇报如无上期截止点，使用明确的初始化起点并说明；后续接续上期截止点，避免空档。两次周报窗口长短不同，不能直接比较事件总数宣称改善。任意“前48小时”查询仍支持独立输出，但不替代连续周期报告。

15:00为报告截止点和初版出具时间；如果尚未完成采集，注明临时结果、抓取时间和采集延迟，待完成后用修订版补发。连接故障也按时出具“数据不可用”的状态说明，不填零。首次未来节点为2026-11-20周五、2026-11-24周二；本次仅约定节奏，实际运行由人工触发。

## 三、指定范围取数步骤

1. 输入：开始、结束、时区、项目、环境、正式来源核验条件、可选release、输出目录。拒绝开始不早于结束或未来结束点；若用户明确要进行中窗口，标记“尚未结束”。
2. 转UTC。例如 `2026-11-17 15:00 +08:00` 至 `2026-11-19 15:00 +08:00` 对应 `2026-11-17T07:00:00Z` 至 `2026-11-19T07:00:00Z`。
3. `search_errors` 查询示例：`environment:production level:[error,fatal] timestamp:>=2026-11-17T07:00:00Z timestamp:<2026-11-19T07:00:00Z`。本次连接已验证可将绝对范围转换为实际起止时间；每次仍必须检查返回的 `executedSearch.timeRange`，不能只看请求文案。不得另加相冲突的相对时间筛选。
4. 总览字段：`count()`、`count_unique(issue)`、`count_unique(user)`；另查按 `issue` 的事件数，按 `os.name`、`release` 的分布，必要时拆分维度。字段不存在则记录缺口，不假设所有事件都有平台、用户或release标签。
5. 用 `search_issues` 或具体资源补充标题、当前状态、全生命周期首次/最后出现时间和归属；它们是问题元数据，不能替代Errors里的窗口内计数。报告主统计不使用 `is:unresolved`，避免漏掉本期已解决、归档或重新出现的问题。
6. 每次查询保存数据集、实际查询、实际起止范围、字段、限制、抓取时间、Sentry链接和截断提示。详情查询再核对事件时间落入目标窗口；“最近一条事件”可能在窗口外。
7. 校验分组事件合计与总数。若分组达到返回上限或有截断提示，继续分页或按互斥时间/维度拆分。已拆分的事件数可按无重叠区间相加，去重Issue、用户数不能相加；Issue须合并去重，用户去重需整窗查询。查不全时标注“部分数据”和覆盖范围，Top列表不得冒充全量。
8. Errors中的OS取值标准化成iOS、Android、其他/未知，原值保留在查询说明。用户标识缺失时去重用户数为0不能解释为无人受影响；报告写“未识别，无法估算完整人数”。
9. 用[错误报告模板](templates/error-report.md)生成文档；没有数据也保留模板结论，并区分“查询成功但无可见事件”和“查询失败/已超保留期/采集异常”。

## 四、分级、排查与实施

| 等级 | 判定依据                                                        | 处理目标                       |
| ---- | --------------------------------------------------------------- | ------------------------------ |
| P0   | 已证实的资金、安全、隐私或核心业务大面积不可用                  | 立即升级、止损并持续跟踪       |
| P1   | 冷启动、会话/聊天、角色创作或影像创作关键流程持续失败；明显回归 | 当日明确负责人和复现，优先修复 |
| P2   | 局部失败、可绕行或非核心功能异常                                | 纳入本周，说明预计时间         |
| P3   | 低影响、已证明的预期取消或观测分类问题                          | 单列并记录证据，安排治理       |

严重度不能只按次数决定。持续失败即使低频也可能高优先级；离页取消必须证明来自当前请求，不能靠错误名字一概过滤。供应商故障、旧release残留和已退役入口单列，不能直接当作新代码回归。

每项问题先记录：Issue链接、时间范围、平台、版本、业务影响、可复现步骤、脱敏样本、根因证据和置信度。无法定位时写“根因未确认”及下一步，不编造结论。

确认需要修复后，复用已有Trellis任务或新建问题任务，按仓库规划门禁补齐复用调研、性能与日志方案、风险、回滚、验收及人工审核。一个根因可对应多个Issue，但保留完整映射；不按每个事件创建任务。

实施须运行受影响包的typecheck、既有相关测试和适用静态检查；跨包契约、部署等按根规则扩大验证。是否新增测试按审核后的规划和风险决定。已有UI场景优先复用，复杂流程建议纳入本地验收；真实系统键盘、计费、上游与发布验证不能被模拟场景代替。

## 五、修复状态与关闭条件

报告状态与Sentry当前状态分别记录，避免两套状态互相冒充。

| 报告状态                                  | 必须提供的证据                                                   |
| ----------------------------------------- | ---------------------------------------------------------------- |
| 待分析 / 已定位 / 修复中                  | 影响、负责人、根因置信度、下一动作                               |
| 本地已修复                                | 改动与本地检查；尚未commit就写未提交                             |
| 已提交待上线                              | 完整commit、PR及检查结果                                         |
| 已上线待观察                              | 实际部署成功时间、Sentry release及commit映射、正确环境           |
| 线上验证通过                              | 指定新版本窗口、有效业务曝光、采集健康、目标错误和回归检查均满足 |
| 验证不足 / 修复无效 / 再次回归 / 外部阻塞 | 明确证据缺口或失败原因、恢复动作和下次检查时间                   |

默认从实际生效时间后观察至少48小时；低曝光延长至72小时或继续观察。具体阈值在修复任务里事先确定，不能只因过了48小时就自动通过。周一修复尚不足48小时，周二应如实报告“待观察”。

前后比较采用同环境、正式来源、平台、release可辨认且等长的窗口；排除部署过渡段，记录旧版本仍在上报的情况。优先比较同一业务暴露分母的错误率，同时列事件数与业务量。分母不可得时只报告观测次数及限制；有埋点变化、采样变化或SDK停报时不认定收益。

P95附有效样本数、指标定义、来源和窗口；无样本写“无可见样本”，不能补零或相加独立P95。聊天首字、完整推流、生成时长分开；新旧ready定义不能直接比较。性能修复按iOS、Android分别复验，错误修复同时检查性能是否回退。

线上复验完成后，才按团队既有授权决定是否在Sentry标记对应版本已解决；本流程不自动改Issue状态，不自动提交、推送、合并、部署或改生产配置。没有错误事件但也没有业务曝光或健康采集，结论必须为“验证不足”。

## 六、报告与失败恢复

文件名统一为 `错误报告_开始-结束_时区_环境_v1.md` 和 `修复情况_汇报日_周二或周五_v1.md`，时间包含时分秒以避免同日不同窗口撞名；同周期补充用v2并保留旧版。报告中填完整带时区时间；文件名可用 `20261117T150000+0800` 格式。

每次修复汇报带上新问题、上期积压、已上线待观察、已验证、回归和外部阻塞；没有修改也出具报告并说明原因。下一周期继续沿用Issue和任务标识，不复制成新问题，不把跨周积压清零。

| 异常                           | 处理                                                                                           |
| ------------------------------ | ---------------------------------------------------------------------------------------------- |
| 401/403、项目不匹配            | 停止取数并说明权限或目标问题，不切换到猜测的组织                                               |
| 429或临时服务错误              | 只对读取有限重试，尊重Retry-After；建议单次读最多3次尝试、总等待不超过60秒，超过预算记录待重试 |
| 没有游标、条数达到上限         | 拆分范围并交叉核对；不能完整枚举则标明部分数据                                                 |
| 查询字段不支持、来源不明确     | 调整后记录实际字段和范围，未核实部分单列                                                       |
| 数据过期、采集丢弃、延迟或断报 | 标明缺失时间和证据，不把缺口解释为改善                                                         |
| 修复引入回归                   | 立即停止扩大发布，按已审核方案回滚或前向修复，保留失败记录                                     |

未来若接入调度：仅先自动生成只读草稿，再由工程师执行和审核修复。调度需显式配置 `Asia/Shanghai` 的周二/周五15:00，或UTC `0 7 * * 2,5`，并处理执行失败、重复运行及截止后补报。当前没有安装、创建或启用任何调度。
