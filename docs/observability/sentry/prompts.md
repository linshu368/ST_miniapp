# Sentry错误治理执行指令

执行前阅读[流程](README.md)。以下是给拥有现有Sentry连接的助手使用的指令模板，不是已安装的定时任务。Windows目录中的文件名不要使用冒号；所有时间使用显式时区。

## 一、获取任意时间范围的错误报告

替换日期即可使用；例子是北京时间48小时窗口。

```text
请连接现有Sentry，按 docs/observability/sentry/README.md 流程生成错误报告。
组织：wangqiao
项目：st-miniapp
区域：https://de.sentry.io
开始时间：2026-11-17 15:00:00 +08:00
结束时间：2026-11-19 15:00:00 +08:00
时区：Asia/Shanghai，左闭右开，以事件发生时间统计
环境：production；release：全部
来源核验：前端正式origin为https://app.themijing.com；后端按服务与实际部署确认；未核实来源单列。
输出模板：docs/observability/sentry/templates/error-report.md
输出目录：docs/observability/sentry/错误治理报告/2026-11/
文件名：错误报告_20261117T150000+0800-20261119T150000+0800_production_v1.md

要求：
1. 使用Errors统计error/fatal，查询整窗总数、去重Issue、已识别去重用户，按Issue、iOS/Android/未知、release拆分。
2. 核查executedSearch实际起止时间，保留查询字段、筛选、链接、抓取时间、条数限制和完整性；不得用Issue生命周期次数代替窗口次数。
3. 已解决和归档问题也纳入窗口统计；补充当前状态与本窗首末时间，检查新增、回归及旧版本残留。
4. 分组达到上限时继续枚举或无重叠拆分，无法取全则标明部分数据；用户和Issue跨分组去重，不相加。
5. 优先分析冷启动、聊天会话、角色创作、影像创作；其他高风险问题不得遗漏。区分已确认根因与推断，关联已有任务和实际commit。
6. Logs、HTTP失败、性能另列；不与Errors混加。数据缺口不补零；无用户标识不能说无人受影响。
7. 取数后必须分析全窗问题，按有证据的同根因合并问题组并保留Issue映射；没有证据不强行合并，不只输出Top列表或统一写建议修复。
8. 每组给出业务优先级及互斥处置结论：必须处理/可暂缓/待核实；说明理由、负责人和最晚动作。分别标注专项治理/小修复/常规修复/外部跟进/待定，汇总严重专项、必须优先处理项、可小修项和暂缓项；方式标签不与处置结论数量相加。
9. 说明实际影响：哪些流程/平台/版本、什么失败、发生时段与持续情况、核心流程是否阻塞、是否仍在发生、有无绕行及资金/安全/隐私/数据风险。事件数、去重业务失败、已识别人数和业务分母分别列；不混用、不推测，缺分母不报比例，缺证据不判断低影响，潜在风险单列。
10. 专项说明为何单点修复不足、止损与阶段验收；小修说明局部边界和风险/回滚，不能按代码行数判定。暂缓必须有影响可接受的证据、监测、复查时间和升级条件；严重外部故障仍须安排止损，待核实项给补证动作和期限。不照抄Sentry/告警P0标签作为业务定级，也不把其他请求成功当原问题已恢复。
11. 给出可执行验收及下一周期顺序；只生成报告，不改产品代码、不改Issue状态或发布。脱敏保存Markdown；同名文件存在时新增修订，保留原版。
```

## 二、根据报告执行已确认的修复

```text
请根据【填写错误报告路径】开始处理其中【填写Issue或任务清单】。
先核对当前代码、已有Trellis任务和相关commit，避免重复修复或恢复已退役入口。
按根AGENTS.md、相关spec与Trellis门禁完成规划及适用审核，明确根因、最小改动、日志、Android/iOS性能护栏和回滚。
完成授权范围内的代码修改，运行适用的typecheck、既有相关测试和静态检查，记录失败路径与未覆盖的真实场景。
已有本地验收优先复用；复杂流程应提出可重复验收场景。真实计费、供应商、生产迁移或配置依照已有授权边界执行。
在任务记录中保留Issue→改动→commit/PR→部署→验证的证据。修复汇报按当前repair-report.md保留窗口分析结论、实际影响、专项/小修安排、修复状态，以及暂缓依据/待核实缺口和复查升级条件；技术细节留任务记录。
不自动git add/commit/push、合并、生产部署、改运营配置或将Sentry问题标记已解决。
```

## 三、每周二、周五15:00出具修复说明

```text
请按 docs/observability/sentry/README.md 生成本次周二/周五的错误报告和修复情况说明。
时区：Asia/Shanghai；本期截止：填写实际汇报日期15:00:00 +08:00。
本期开始：上一份正式周期报告的截止点；首次没有前期报告时明确初始化起点。
通常周二为上周五15:00到本周二15:00，周五为本周二15:00到本周五15:00。
上期汇报：填写路径或说明首次。
已处理任务：填写Trellis任务路径；如为空，查阅已有相关任务和commit，不编造已修复记录。
错误模板：docs/observability/sentry/templates/error-report.md
修复模板：docs/observability/sentry/templates/repair-report.md
输出目录：D:/JobExe/ST/sentry/错误治理报告/填写YYYY-MM/

1. 通过现有Sentry连接读取本期错误；检查实际范围、环境来源、release和采集健康，保留查询证据。
2. 对全窗问题逐组分析实际影响、业务优先级和处理必要性；汇总必须处理、可暂缓、待核实，并标注严重专项与可小修项及理由。影响写清流程/平台/版本、实际量级、时段、是否持续、绕行与高风险后果；缺分母/人数或覆盖不足明确写未知，不按事件数或告警等级直接下结论。
3. 在任务记录中核对代码、commit、部署与验证证据；汇报保留日期、周期、对应错误报告、本期分析结论及两张表：处理中的问题（含优先级/方式、影响、状态和下一动作），暂缓与待核实的问题（含判断依据、原因/缺口、负责人、复查时间与升级条件）。正文简明，技术细节不展开；没有对应问题写“无”。
4. 状态只用已修复、待上线、待验证、未修复。只有上线后验证通过才填已修复；未上线填待上线，观察时间或样本不足填待验证。采集异常不能作为已修复的依据。
5. 必须处理但未开工也列第一张表，填未修复及负责人/时限；严重外部故障不放进可暂缓清单。专项/小修是处理方式，不与必须处理数量相加。暂缓要有影响可接受的证据、保护措施、复查时间和升级条件，不能只写偶发、影响小、等上游或后续处理；待核实给补证期限。
6. 不修改代码、不自动关闭Sentry、不发布；同名报告新增修订，保留旧版。
```

本次已确认按上述时间交付模板；实际自动执行尚未启用。手动使用时将“填写”项换成实际值；如助手不能访问工作区、Sentry或部署证据，须明确未完成项，不声称已保存或已验证。
