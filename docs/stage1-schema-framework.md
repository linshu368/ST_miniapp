## 0. 一页纸结论

- **阶段一的 schema 框架已经冻结**：包含 6 张已建表 + 1 张待建凭证表，已全部带上结构化标签，可以从数据库本身反向校验同步规则
- **核心方法是一个两维分类法**：第一维"谁说了算"，第二维"长什么样"。这两个维度相互独立、可解释、不重叠
- **覆盖未来 6-12 个月可预见的所有迭代**：包括新增默认资源、用户私有内容、API key 加密、高级配置开放等
- **3 项关键决策已落地，1 项决策显式延后**：延后的事项不会变成隐藏负债，因为它们在文档里被明确标记
- **阶段一明确不做的事比要做的事更值得关注**：这是控制项目范围、避免烂尾的关键

接下来 D2-D9 的同步引擎和 Bridge 工作都将基于这套 schema 推进，不会再有"该建哪张表 / 数据流方向 / 权限策略怎么定"的反复讨论。

## 1. 这套框架要解决的真实问题

### 项目本质回顾

一句话：**我们不是在重写 ST，而是把 ST 当作一个黑盒发动机部署，外面包一层"鉴权 + 数据同步"的商业化外壳**。

这意味着：

- ST 仍然是一个完整的 Node.js 服务，它的"配置真相"住在它自己的文件系统里（`data/<用户>/` 下面的一堆 JSON 文件和图片）
- 我们的"业务真相"住在 Supabase（用户、付费、平台默认配置等）
- 这两个真相必须双向流动

### 难在哪里

**难点不在"双向同步"四个字本身**，而在**不同字段的流动规则方向完全相反**：

- "平台默认提供哪些角色卡" —— Supabase 是权威，覆盖到 ST 文件系统
- "用户当前选了哪个角色卡" —— ST 文件系统是运行时权威，回流到 Supabase
- "API Key" —— Supabase 权威，下发到 ST，但绝不能反向暴露给前端
- "用户的字体大小偏好" —— ST 文件系统权威，但跨设备时 Supabase 接替

如果不把这些字段先按规则归类，同步引擎就会变成一堆 if-else 的 special case 堆叠，3 个月后没人敢动。

### Schema 错了的代价

- **轻**：表结构需要重建，已写入的数据需要迁移
- **中**：同步引擎要为每个 special case 单独写代码，配置清单变成空架子
- **重**：用户数据丢失或写错方向（典型：用户操作被错误地写到了 Supabase 但没回写 ST，或反过来）

所以 schema 框架是阶段一**最不能凑合**的部分。即使 D1 多花一两天打磨，也比 D5 推翻重做便宜。

## 2. 设计思路：用两个独立维度把数据切清楚

我们用两个相互独立的维度来给每一份数据"挂标签"：

### 维度一：谁说了算（控制权 / partition）

回答"出现冲突时，以谁的版本为准"。这是**业务规则维度**，决定了数据怎么流、谁有权限写、出问题谁负责。

| 类别                 | 通俗解释                                                                                                                            | 例子                                        |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| **A 类：平台管控**   | 平台是绝对真相。Supabase 改了什么，ST 那边必须照办；ST 那边即使被人改了，下次同步会被覆盖                                           | 默认角色卡库、默认预设、API Key、模型白名单 |
| **B 类：用户运行时** | 用户的实际操作发生在 ST。ST 是当下的真相；但用户关掉浏览器后 ST 临时数据会清掉，所以 Supabase 充当"备份"角色，下次登录时再投影回 ST | 用户当前选的角色、聊天记录、个人偏好        |
| **身份/系统类**      | 既不是 Supabase 也不是 ST 说了算，而是一个**确定性的派生规则**说了算（比如根据 Telegram ID 派生出 ST 用户名）。写一次后就不再变     | 用户的 ST handle                            |

**这三类的本质区别是数据流方向**：A 类是单向下发，B 类是反向镜像，身份类不参与同步。

### 维度二：长什么样（实体形态 / shape）

回答"这种数据物理上怎么存"。这是**数据结构维度**，决定了表怎么建、字段怎么放、查询性能怎么保证。

| 形态       | 通俗解释                                               | 表怎么建                                            |
| ---------- | ------------------------------------------------------ | --------------------------------------------------- |
| **资源型** | 一个完整的内容单元，可以被引用（一张角色卡、一份预设） | 一行一个资源，业务字段独立列 + 大块内容塞 JSON 字段 |
| **凭证型** | 敏感数据，必须严格控制谁能读                           | 独立表 + 严格权限隔离 + 绝不返回前端                |
| **选择型** | 用户"选了什么"的指针，指向某个资源（高频改）           | 一用户一行，每个 `当前活跃的XX` 一列                |
| **偏好型** | 零散的个人配置（颜色、字体、各种开关）                 | 一用户一行，常用字段独立列 + 一个 JSON 字段兜底其余 |

**资源型有两个亚型**（这是后来补充的，详见决策三）：

- 平台池资源（`platform_<资源>`）：A 类，单向下发
- 用户池资源（`user_<资源>`）：B 类，反向镜像

两个亚型的表结构会高度相似，但数据流方向相反、权限策略相反，**必须分开建表**。

### 为什么是这两个维度，不是别的

我考虑过几种替代方案：

| 备选方案                 | 为什么没选                                           |
| ------------------------ | ---------------------------------------------------- |
| 只用"控制权"一维         | 解决不了"同样是 A 类，角色卡和 API Key 怎么放"的问题 |
| 只用"形态"一维           | 丢掉数据流方向，每次都要 case-by-case 决定怎么同步   |
| 加第三维"按 ST 源文件切" | 把同步实现细节污染到 schema 层，过度工程             |
| 加第三维"按读取者切"     | 跟控制权维度高度重叠，冗余                           |

两维方案的好处：

- **正交**：每个字段都能落在唯一格子里，不重叠不漏
- **可解释**：维度一对应业务问题（谁负责），维度二对应工程问题（怎么存）
- **可演化**：新增配置时，决策路径固定——先问归属、再问形态，落到哪张表基本不需要讨论

## 4. 三个关键决策的"通用语言"解释

阶段一 D1 收尾前，我们补了三条关键决策（D006/D007/D008），下面用非技术语言解释每条的来龙去脉。

### 决策一（D006）：ST 有 11 类资源池，阶段一只搬 3 类上来

**背景**：

ST 这个软件本身把配置切得非常细。光在用户目录下，就有 11 个独立的"内容池"目录：

- 角色卡、4 类不同 API 的预设（OpenAI / TextGen / NovelAI / KoboldAI）、世界书、对话格式化模板、上下文模板、系统提示词模板、推理模板、快捷回复、UI 主题等

每一种内容的字段结构都完全不同。

**两个错误做法**：

1. **全部建表**：阶段一就要建 11+ 张 `平台_xxx` 表，但其中大半在阶段一根本用不到。建出来的表会变成永远没有数据的空架子，但维护成本（权限、迁移、文档）一分不少
2. **统一一张大表**：搞一个 `平台_所有资源` 表，用一个 `类型` 列区分。后果是丢失所有类型化字段的查询能力，未来想给角色卡加 tag 索引时要把整张表重建

**决策**：

阶段一只暴露 **3 类资源**：角色卡、API 预设、世界书。
其余的内容池（对话格式化模板、系统提示词等）**先在 ST 配置层锁定一个默认值**，不在 Supabase 建表，等阶段三平台真要把它们做成可选项时再补。

**关键原则**：**"延后建表"是合法决策，不是技术债**。建一张永远没数据的表，比承认"现在不做"更糟糕。

### 决策二（D007）：用户私人内容和平台内容是两类不同的表

**背景**：

阶段一的底线交付里有一条：用户能在 ST 里**切换角色卡**和**导入角色卡**，且这些操作能反向同步回 Supabase。

但是"切换"和"导入"是两件不一样的事：

- 切换 = 在已有的平台默认卡之间换一个，只是改了一个指针
- 导入 = 用户带了一张自己的卡进来，这是一份**用户私有的资源**，平台从来没见过

如果我们只准备好"平台默认资源"这一类表，用户导入的卡片就**无家可归**。

**决策**：

资源型显式拆成两个亚型：

- **平台池资源**：表名前缀 `平台_`，控制权属于平台，数据从 Supabase 单向下发到 ST
- **用户池资源**：表名前缀 `用户_`，控制权属于用户，数据从 ST 反向镜像到 Supabase

两类表的结构可能高度相似（用户的角色卡和平台的角色卡字段几乎一模一样），但**数据流方向相反、权限策略相反，必须分开建表**。

**阶段一的具体范围**：

- 已建的 `user_st_chats`（聊天记录）就是一张用户池表，作为占位
- **阶段一不新建** `user_characters` 等用户池资源表
- 反向同步验证**只覆盖"平台池角色卡之间的切换"**；用户在 ST 里导入的私有卡，阶段一不做镜像，等阶段二接入 PostMessage 时统一处理

**为什么阶段一不做用户池资源同步**：

- 阶段一目标是"框架可运行"，不是"功能完备"
- 用户池资源的权限规则、引用关系、冲突策略比"选择型"复杂得多，强行赶到阶段一会拖垮节奏
- 但**框架本身已经留好位置**，阶段二可以直接套用，不需要回头改 schema

### 决策三（D008）：API Key 阶段一明文存，阶段二再加密

**背景**：

阶段一需要把平台的 OpenRouter / OpenAI 等 API Key 从 Supabase 下发到每个用户的 ST。这些 Key 是平台真金白银付费换来的，**不能泄露给用户**，更不能泄露到 GitHub 之类的地方。

第一反应：肯定要加密存。

但我们仔细想了下：**加密到底防的是什么**？

**威胁模型分析**：

| 威胁                               | 加密能防吗？                                            | 真正的防护手段                                               |
| ---------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------ |
| Key 通过接口泄露到前端             | ❌ 服务端解密后照样能泄露                               | **代码层硬约束**："这个字段永远不返回客户端"，是规约不是技术 |
| 用户偷到自己 ST 文件里的 Key       | ❌ ST 那边本身就是明文 `secrets.json`，加密只在传输路径 | 用户隔离 + 用户付费                                          |
| 操作员在 Supabase 后台肉眼看到 Key | ✅ 加密能防                                             | Supabase Vault 等加密扩展                                    |
| 数据库被脱库                       | ✅ 加密能防                                             | Supabase 平台自身的安全 + 加密                               |

也就是说，**加密真正防的是后两条**：操作员误看和数据库被脱库。这两条在阶段一的威胁优先级**远低于**"代码层保证不返回客户端"。

**决策**：

阶段一采用 **明文存储 + 严格权限隔离 + 代码层硬约束**：

- Supabase 列直接存明文
- 数据库权限规则：只有后端服务账号能读，普通用户账号完全禁读
- 应用层硬约束：API Key **永远不出现在返回给前端的任何响应中**，这是写到代码评审清单里的红线
- 所有读取走同步引擎，进操作日志

**加密延后到阶段二**：使用 Supabase 提供的 Vault 扩展（行业标准做法）。延后的代价是：阶段一期间，运营人员在 Supabase 后台可以肉眼看到明文。考虑到团队规模小、API Key 数量有限（少数几个平台账号），这个窗口期可接受。

**表命名也改了**：从原计划的 `platform_secrets` 改为 `platform_api_credentials`。理由是"secrets" 这个词太宽，未来还会有 webhook secret、签名密钥、OAuth client_secret 等，命名混在一起会出事。

## 5. 显式延后的事项（一份"不做清单"）

下面是阶段一**明确不做**的事。每一条都做了主动决策，不是"忘了"或"来不及"：

| 不做的事                                                          | 为什么不做                                             | 计划在哪个阶段做                         |
| ----------------------------------------------------------------- | ------------------------------------------------------ | ---------------------------------------- |
| 用户私有资源的反向同步（用户导入的角色卡 / 自建世界书）           | 阶段一目标是验证框架，不是功能完备；用户池表的复杂度高 | 阶段二（PostMessage 接入时）             |
| 高级 ST 配置开放（instruct / context / sysprompt 模板的可选切换） | 这些是高级用户向功能，对当前商业化模型贡献低           | 阶段三                                   |
| API Key 加密存储                                                  | 威胁模型分析后，阶段一加密的边际收益低于落地成本       | 阶段二（Supabase Vault）                 |
| 多 ST 实例 / 负载均衡                                             | 阶段一目标用户量远未到需要分片的级别                   | 用户量达到阈值后再说，**框架不预先支持** |
| 偏好字段从 JSON 兜底字段升列的明确触发规则                        | 阶段一的偏好数据使用面窄，触发条件不清晰               | 阶段二开工前补                           |
| MiniApp 大厅的角色切换 UI 入口                                    | PostMessage 没就位，强行做意义不大                     | 阶段二                                   |
| 反向同步的复杂冲突解决                                            | 阶段一分区清晰、单源写入，结构上不会产生冲突           | 不计划做（不需要）                       |

**这份清单的价值在于"显式"**：每一条都有一个明确的位置（这份文档、DECISIONS.md），新人接手时不会以为"框架漏掉了某某能力"，而是会看到"框架知道这件事但选择不做"。

## 6. 未来 6-12 个月的演进路径

下表对照常见迭代场景，说明这套框架怎么承接：

| 未来 6-12 个月可能发生的迭代                                        | 框架的承接方式                                                                         | 改动成本                               |
| ------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | -------------------------------------- |
| 新增一类平台默认资源（如平台主题包、平台音效包）                    | 加一张 `platform_<资源>` 表，套现有模式                                                | 低（1-2 小时）                         |
| 新增一类用户私有资源（用户可上传自定义角色卡）                      | 加一张 `user_<资源>` 表 + 同步规则，套 D007 亚型                                       | 中（1 天）                             |
| 平台批量改某个默认配置（如把所有用户的 max_context 从 8K 改到 16K） | 把该字段从偏好 JSON 提升为独立列，做一次 SQL migration                                 | 中（半天 + 一次回滚演练）              |
| API Key 切换为加密存储                                              | 上 Supabase Vault，替换 `platform_api_credentials` 的列为加密列；查询接口不变          | 中（1-2 天）                           |
| 开放某类高级配置（如允许用户切换 instruct 模板）                    | 解锁 ST 那边的锁文件 + 新建 `platform_instruct_templates` 表 + 配置清单加一行          | 中（1-2 天）                           |
| 接入 PostMessage、做 iframe 嵌入                                    | 这是阶段二的核心工作，框架已为其留位（user_st_chats 占位、active_character_id 已存在） | 阶段二主任务                           |
| 用户分级 / 付费等级影响可用资源                                     | 给 `platform_<资源>` 表加 `required_tier` 列，配合后端权限校验                         | 低（半天）                             |
| **多 ST 实例 / 跨实例迁移**                                         | **框架不支持，需要重新设计**                                                           | **高，明确不在阶段一框架的承诺范围内** |

**这份表的承诺是诚实的**：标了"低 / 中"的迭代，团队有信心在 1 天内消化；标了"高"且**不在框架内**的（多 ST 实例），坦诚承认。

## 7. 框架可能撑不住的场景与应对

诚实的列一下这套框架的极限。技术决策必须把"什么时候这套不灵了"也想清楚。

### 极限场景 1：用户偏好出现了大量需要平台聚合的字段

**触发条件**：商业化做风控时，需要按"用户的某项偏好"批量筛选用户（如"所有 max_context > 16K 的付费用户"）。

**问题**：这些字段如果全在 `st_settings_snapshot` JSON 里，查询要全表扫，性能崩。

**应对**：决策 D008 之后会补的"字段提升规则"——满足"被平台批量查询 / 计费 / 风控读取"的字段从 JSON 升列。这是已规划但未细化的事项，阶段二前补。

### 极限场景 2：用户私有资源数量爆炸

**触发条件**：业务方向转成"用户社区，用户大量自创角色卡互相分享"，单个用户私有资源数千个。

**问题**：当前 `user_<资源>` 表的设计假设是"用户私有 + 数量有限"，没考虑用户间共享、点赞、评论等。

**应对**：这是**业务模型变化**，不是 schema 框架的失败。如果真朝这个方向走，应当新增"社区资源"作为第四种归属（已超出 A/B/身份三类），届时是整个框架的一次重大演化，预期会有专门的设计周。

### 极限场景 3：ST 升级带来配置结构破坏性变更

**触发条件**：ST 上游某次更新里，把 `settings.json` 的某个字段移到了别处，或字段含义变了。

**问题**：我们的 schema 字段名和 ST 字段名是耦合的（如 `active_preset_name` 对应 ST 的 `oai_settings.preset_settings_openai`）。

**应对**：

- 这是同步引擎层而不是 schema 层的问题——配置清单（schema/registry）会作为隔离层吸收 ST 字段名变化
- 已经在 DECISIONS 总览里强调"配置清单从 information_schema 反向校验"，保证 schema 标签与同步规则永远一致
- 每次 ST 升级走 SAAS_CHANGES.md 流程，强制评估字段映射

### 极限场景 4：多端登录的反向同步冲突

**触发条件**：用户在两台设备同时登录 ST，A 设备改了 active_character，B 设备同时改了 active_preset。

**问题**：两边同时反向同步可能互相覆盖。

**应对**：

- 已经在 `user_st_state` 表加了 `sync_version` 字段做乐观锁
- 阶段一不深做冲突解决（D5 决策），等阶段二真出现多端场景时再上分布式锁或 last-write-wins 策略
- 这个风险**已知且已留位**，不是盲区

## 9. 需要项目负责人决策或关注的开放问题

下面几条，建议项目负责人现在看一眼，方便后续决策：

### Q1：API Key 阶段一明文 vs 阶段一就上 Vault

**当前决策（D008）**：阶段一明文，阶段二上 Vault。
**主要权衡**：阶段一不加密 = 不阻塞 D4-D7 sync 引擎开发；运营在 Supabase 后台可肉眼看到明文（团队规模 X 人，可控）。
**如果你判断"运营人数会很快增加"或"安全合规优先级更高"**，可以拍板"阶段一就上 Vault"，代价是 sync 引擎要多 1-2 天处理 Vault 接入。

### Q2：阶段一是否要在底线验收里包含"用户导入私有角色卡的反向镜像"

**当前决策（D007）**：阶段一**不做**，验证范围限定在平台池角色之间的切换。
**主要权衡**：缩小验收范围 = 阶段一稳；如果业务侧近期就要用户上传卡功能上线，需要把这个能力前移到阶段一末，代价是 D7-D9 要多 2-3 天。

### Q3：偏好字段从 JSON 升列的触发规则什么时候定

**当前决策**：阶段二开工前定。
**主要权衡**：阶段一同步引擎只接触一张偏好表，规则缺位短期无影响。但如果阶段一末就要做"按用户偏好做付费计算"，规则要前移。
**判断依据**：商业化模块对用户偏好字段的依赖时间表。

### Q4：未来是否真的会走"多 ST 实例"

**当前决策**：框架不预先支持。
**主要权衡**：如果业务量预期 6 个月内会达到单 ST 实例性能瓶颈，需要现在就开始铺设多实例架构（这不是 schema 层的事，是整个部署架构层的事）。建议**现在不动**，等用户量到达阈值时再回头评估。

## 10. 一句话总结

**阶段一 schema 框架的核心承诺是**：把数据用两个独立的维度切清楚，每张表的归属和形态都写在数据库自己身上，让同步引擎能从数据库反向校验自己的规则；该做的现在做，能延后的显式延后，不在框架内的（如多实例）坦诚标出来。

未来 6-12 个月的迭代我们已经预演过，框架能承接；崩塌的场景我们也想过，应对方案有的已落地有的留了位。

接下来 D2 起进入同步引擎实现，进度可以按计划推进。
