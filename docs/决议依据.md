# 主题 4 :Bridge Protocol 与 bridge\-client / st\-extension 规约

# 重要概念约定

| 名称                             | 定义                                    | 位置                                                                                            |
| -------------------------------- | --------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Bridge Protocol                  | postMessage 协议契约本身，纯类型/Schema | packages/bridge\-protocol，仅 ESM                                                               |
| bridge\-client                   | 平台前端运行时桥实现                    | packages/frontend/src/lib/bridge/                                                               |
| st\-extension                    | 注入 ST 的 IIFE 桥载荷                  | packages/st\-extension 构建产物 → vendor/sillytavern/public/scripts/extensions/miniapp\-bridge/ |
| provision\-api（原 bridge\-api） | sync\-engine 的 HTTP 入口进程           | packages/sync\-engine，启动命令 start:provision（原 start:bridge 同步改名）                     |
| 鉴权桥                           | 阶段一交付的 SSO 模块                   | packages/backend                                                                                |
| provisioning                     | 物化行为（职责），不是独立模块          | sync\-engine 内部 provisioner                                                                   |

**强制约束**:文档与代码中"bridge"一词若不带前缀,默认指 Bridge Protocol 三件套\(协议\+client\+extension\)。其他场景必须带前缀\(鉴权桥、provision\-api 等\)。

## §1 消息结构

### 1\.1 顶层信封\(所有消息共用\)

```TypeScript
// bridge-protocol/src/envelope.ts
type BridgeEnvelope = {
  /** 协议命名空间,用于跨 iframe 消息过滤 */
  channel: 'miniapp-bridge'
  /** 协议主版本号,见 §2 */
  protocolVersion: 1
  /** 消息类型 */
  type: 'request' | 'response' | 'event' | 'handshake' | 'ping' | 'pong'
  /** UTC 毫秒时间戳,发送方填入 */
  timestamp: number
}
```

任何不携带 `channel: 'miniapp-bridge'` 的消息一律忽略\(避免与 ST 自身或第三方扩展的 postMessage 流量混淆\)。

### 1\.2 Request / Response

```TypeScript
type BridgeRequest<A extends ActionName = ActionName> = BridgeEnvelope & {
  type: 'request'
  requestId: string                       // UUID v4,bridge-client 生成
  action: A
  payload: ActionPayloadMap[A]            // Zod schema 在协议包内定义
}

type BridgeResponse<A extends ActionName = ActionName> = BridgeEnvelope & {
  type: 'response'
  requestId: string                       // 与 Request 对应
  success: boolean
  data?: ActionResultMap[A]               // success === true 时存在
  error?: BridgeErrorPayload              // success === false 时存在
}
```

1\.3 Event\(单向推送\)

```TypeScript
type BridgeEvent<E extends EventName = EventName> = BridgeEnvelope & {
  type: 'event'
  eventName: E
  payload: EventPayloadMap[E]
}
```

1\.4 Handshake\(三段\)

```Go
type HandshakeMessage = BridgeEnvelope & {
  type: 'handshake'
  phase: 'handshake' | 'ready' | 'context-ready'
  /** 仅 phase === 'handshake' 时携带,后续 phase 可省略 */
  meta?: {
    stCommit: string                      // vendor 锁定的 ST commit hash
    extensionBuildId: string              // st-extension 构建 ID
    supportedActions: ActionName[]        // 该 build 支持的 action 列表
    supportedEvents: EventName[]
    boundUserId: string | null            // ST session 当前绑定的 userId,null 表示 ST 没识别到 session
  }
}
```

1\.5 Ping / Pong\(mirror state 周期同步\)

```Go
type PingMessage = BridgeEnvelope & { type: 'ping' }
type PongMessage = BridgeEnvelope & {
  type: 'pong'
  mirrorState: STMirrorState              // §6 定义
}
```

### 1\.6 大小限制

- 单条消息序列化后硬上限 **32KB**,超限发送方直接 throw `MESSAGE_TOO_LARGE`

- 软建议 **\< 4KB**,超过 4KB 在 dev 环境打 warning\(prod 静默通过\)

- 检查在 bridge\-client 与 st\-extension **双向**做\(发送前检查 \+ 接收后检查\)

## §2 协议版本与兼容性

### 2\.1 单向兼容原则

由于 vendor ST **真·永不升级**,st\-extension 的协议版本一旦发布即冻结\(除非主动重构 vendor\)。平台前端持续演进,因此:

- **平台前端必须向后兼容旧 st\-extension**

- st\-extension **不需要**向前兼容新前端

### 2\.2 版本字段

`protocolVersion: 1` 为整数主版本号。

| 变更类型                     | 是否升主版本 | 处理                                                                                         |
| ---------------------------- | ------------ | -------------------------------------------------------------------------------------------- |
| 新增 action                  | 否           | 旧 extension 收到未知 action，回 UNKNOWN_ACTION 错误；前端通过 supportedActions 提前判断回避 |
| 新增 event                   | 否           | 旧 extension 不会发，前端订阅时也不会触发，无害                                              |
| 新增 mirror state 字段       | 否           | 字段必须 optional；旧 extension 不返回该字段时前端容忍 undefined                             |
| 新增 action payload 必填字段 | 是           | 旧 extension 无法解析新字段，行为未定义，必须升版                                            |
| 删除 action / event          | 是           | 同上                                                                                         |
| 修改 action 语义             | 是           | 必须改名（等价于"删旧加新"）                                                                 |
| 修改错误码字符串             | 是           | 错误码视为公共契约                                                                           |

### 2\.3 协商机制

- 握手阶段 `meta.supportedActions` / `supportedEvents` 是 **唯一可信能力声明源**

- bridge\-client 在握手收到后,把 supported 列表存入内部状态;调用未支持的 action 直接 reject\(`ACTION_NOT_SUPPORTED`\),不发到 iframe

- **不做主版本号自动协商**:版本不匹配直接报错由人工介入。理由:vendor 永不升级 = 版本错位 = 部署事故,不该静默兼容

⚠️ **SPIKE 假设**:st\-extension 的 IIFE 在 ST 初始化早期就能执行 supportedActions 的静态声明\(不依赖 ST 运行时状态\)。如果 ST 扩展加载机制要求扩展自身先初始化才能拿到能力清单,需要调整握手时序。

## §3 三段握手时序

### 3\.1 时序图

```Gherkin
parent (bridge-client)              child (st-extension in iframe)
        |                                  |
        | iframe 挂载完成 (load 事件)       |
        |--------------------------------->|
        |                                  | st-extension IIFE 加载
        |                                  | 注册 message listener
        |  <--- handshake(phase=handshake) | meta: stCommit, supportedActions, boundUserId
        |                                  |
        | 校验 protocolVersion / userId 一致性
        | 校验 supportedActions 满足前端最低需求
        | 通过 → 标记阶段 ①                  |
        |                                  | 等待 ST 核心初始化完成
        |                                  | (监听 ST APP_READY 等价信号)
        |  <--- handshake(phase=ready)     |
        | 标记阶段 ② → flush ②级 buffer     |
        |                                  | 等待 ST 用户上下文加载完成
        |                                  | (监听 chats_loaded 等价信号)
        |  <--- handshake(phase=context-ready)
        | 标记阶段 ③ → flush ③级 buffer     |
        |                                  |
        | 进入正常通信                       | 进入正常通信
```

### 3\.2 阶段与 action 可用性绑定

每个 action 在 protocol 包内声明 `requiredPhase: 'handshake' | 'ready' | 'context-ready'`:

### 3\.3 buffer 与超时

- 阶段 ① 之前调用任何 action:**buffer**,上限 32 条,溢出 reject `BUFFER_OVERFLOW`

- 阶段未达但 action 要求该阶段:**buffer**,默认 30s 超时 reject `HANDSHAKE_TIMEOUT`

- action 元数据可声明 `waitable: false`,该 action 在阶段未达时立即 reject `ACTION_NOT_AVAILABLE_IN_PHASE`,不入 buffer

- 整体握手总超时 **60s**\(从 iframe load 到阶段 ③\),超时报 `HANDSHAKE_TOTAL_TIMEOUT` 并触发"iframe 不可用"全局事件

### 3\.4 兜底:`getReadyState`

- 阶段 ① 之后任何时刻 parent 可调用 `getReadyState`,extension 同步返回当前阶段

- 用于:bridge\-client 启动时若 miss 了某个 handshake 消息\(理论上不会,但作为冗余\),可主动查询

⚠️ **SPIKE 假设**:

- ST 核心初始化完成有可订阅的 event\(候选:`APP_READY` / `app_ready` / 类似\)。spike 必须在锁定 commit 上**列出准确的 event 名**。

- ST 用户上下文加载完成同上,候选 event 是 `chats_loaded` / `characters_loaded` 之一,**待 spike 确认**。

## §4 错误码体系

错误码采用 `BRIDGE_<CATEGORY>_<SPECIFIC>` 三段命名,分类如下。

### 4\.1 错误信封

```TypeScript
type BridgeErrorPayload = {
  code: BridgeErrorCode               // 见 §4.2
  message: string                     // ≤ 512 字,无 stack
  requestId?: string                  // 关联的请求(若有)
  context?: Record<string, string | number | boolean>  // 调试上下文,小型 KV
}
```

### 4\.2 完整错误码清单

#### 协议层\(BRIDGE_PROTOCOL\_\*\)

- `BRIDGE_PROTOCOL_VERSION_MISMATCH` —— 主版本号不一致

- `BRIDGE_PROTOCOL_INVALID_ENVELOPE` —— 缺字段或字段类型错

- `BRIDGE_PROTOCOL_PAYLOAD_SCHEMA_INVALID` —— Zod 校验失败

- `BRIDGE_PROTOCOL_MESSAGE_TOO_LARGE` —— 超 32KB

- `BRIDGE_PROTOCOL_UNKNOWN_TYPE` —— `type` 字段值不在枚举内

#### 握手层\(BRIDGE_HANDSHAKE\_\*\)

- `BRIDGE_HANDSHAKE_TIMEOUT` —— 单 action 等待握手超时

- `BRIDGE_HANDSHAKE_TOTAL_TIMEOUT` —— 整体握手 60s 超时

- `BRIDGE_HANDSHAKE_USER_MISMATCH` —— extension 报告的 userId 与平台已知 userId 不符

- `BRIDGE_HANDSHAKE_USER_MISSING` —— extension 报告 boundUserId === null

- `BRIDGE_HANDSHAKE_BUFFER_OVERFLOW` —— buffer 32 条溢出

#### 调用层\(BRIDGE_CALL\_\*\)

- `BRIDGE_CALL_UNKNOWN_ACTION` —— extension 不识别该 action

- `BRIDGE_CALL_ACTION_NOT_SUPPORTED` —— extension 声明的 supportedActions 不含该 action\(在 client 侧拦截,不发出去\)

- `BRIDGE_CALL_ACTION_NOT_AVAILABLE_IN_PHASE` —— 当前阶段不允许调该 action

- `BRIDGE_CALL_TIMEOUT` —— 单 RPC 30s 超时

- `BRIDGE_CALL_INVALID_PAYLOAD` —— payload 不符合 schema

- `BRIDGE_CALL_DUPLICATE_REQUEST_ID` —— extension 收到重复的 requestId\(理论上不应发生\)

#### 执行层\(BRIDGE_EXEC\_\*,extension 内部转发 ST 失败时使用\)

- `BRIDGE_EXEC_ST_INTERNAL` —— ST 内部抛错\(具体原因放 message\)

- `BRIDGE_EXEC_TARGET_NOT_FOUND` —— DOM selector 命中失败 / ST 内部函数缺失

- `BRIDGE_EXEC_PRECONDITION_FAILED` —— 比如 selectCharacter 但角色不在 ST 内存中

- `BRIDGE_EXEC_USER_ACTION_REJECTED` —— ST 自身拒绝\(如生成中无法切角色\)

#### 连接层\(BRIDGE_CONN\_\*\)

- `BRIDGE_CONN_IFRAME_UNAVAILABLE` —— iframe contentWindow 为 null

- `BRIDGE_CONN_IFRAME_NAVIGATED` —— iframe URL 变化\(不应发生,作为 sanity check\)

- `BRIDGE_CONN_DISCONNECTED` —— iframe 被卸载或长时间无响应

### 4\.3 错误归一化

- bridge\-client 内部抛 `BridgeError` 类\(继承 `Error`\),业务组件 `try/catch BridgeError`

- BridgeError 实例的 `code` 字段是上述清单中的字符串字面量\(TypeScript 强类型枚举\)

- 错误详情走 §8 日志通道,不在 BridgeError 自身

## §5 Action 与 Event 演进规则

### 5\.1 增加新 action

1. 在 `bridge-protocol/src/actions/` 新增 action 定义文件,导出 payload schema、result schema、`requiredPhase`、`waitable` 默认值

2. 注册到 `ActionRegistry`\(运行时注册表\)

3. 在 st\-extension 中实现 handler

4. **不升主版本**;前端调用前检查 `supportedActions` 命中

### 5\.2 删除 action

1. **必须升主版本**;但因 vendor 永不升级,实际操作上等于"标 deprecated 但不删"

2. 平台前端不再调用即可;st\-extension 保持响应

### 5\.3 修改 action

**等价于"删旧 \+ 加新"**。永远不要原地改语义,改名字。

### 5\.4 增加新 event

- 在 protocol 包注册;st\-extension 增加发送点

- 旧 extension 不发该 event,前端订阅无副作用

### 5\.5 增加 mirror state 字段

- 必须 optional

- 前端 `useSTMirror()` hook 对未提供字段返回 `undefined` 不报错

## §6 Mirror State 同步机制

### 6\.1 字段清单\(阶段二最小集\)

```TypeScript
type STMirrorState = {
  userId: string                              // 握手即定,不变
  currentCharacterId: string | null
  currentChatId: string | null
  currentPresetName: string | null
  generationPhase:
    | 'idle' | 'started' | 'streaming' | 'finished' | 'aborted'
  messageCount: number
  lastUpdatedAt: number                       // 快照生成时间戳,extension 填
}
```

### 6\.2 同步通道\(混合模式\)

#### 通道 A:事件驱动推送

关键离散事件由 st\-extension **主动发 event**,bridge\-client 收到后**部分更新** mirror store:

| 事件名              | 触发时机                                   | 影响字段                                   |
| ------------------- | ------------------------------------------ | ------------------------------------------ |
| characterChanged    | ST 切角色完成                              | currentCharacterId                         |
| chatChanged         | ST 切 chat 完成                            | currentChatId， messageCount               |
| presetChanged       | ST 切预设完成                              | currentPresetName                          |
| generationStarted   | ST 开始生成                                | generationPhase: 'started'                 |
| generationStreaming | ST 收到第一个 token（节流，1s 最多发一次） | generationPhase: 'streaming'               |
| generationFinished  | ST 生成结束                                | generationPhase: 'finished'， messageCount |
| generationAborted   | 用户停止/出错                              | generationPhase: 'aborted'                 |

MVP阶段只实现通道A，周期 ping 兜底暂时不做。

## §7 跨边界数据传输红线\(完整清单\)

### 7\.1 禁止走 Bridge Protocol\(必须走其他通道\)

### 7\.2 允许走 Bridge Protocol

- 引用类:`characterId / presetName / chatId / messageId`\(短字符串 ID\)

- 小型枚举:`generationPhase` 等

- 小型结构化状态:mirror state 7 字段

- 配置 patch:`setModelTier(level: number)` / `setMaxTokens(n: number)` / `patchPresetField({ key, value })`\(value 必须 \< 4KB,超出走 sync\-engine 通道\)

- 错误对象:`BridgeErrorPayload`\(message ≤ 512 字\)

### 7\.3 量化阈值

- 单条消息硬上限 **32KB**

- 软建议 **\< 4KB**

- ping/pong 频率:活跃 1s / 空闲 5s

- 单 RPC 默认超时 **30s**

- 整体握手超时 **60s**

## §8 日志与可观测性\(部分推后到主题 4\.5\)

### 本主题敲定的部分

- bridge\-client 在 dev 环境把所有消息打 console\.debug\(可关闭\)

- bridge\-client 把所有 `BridgeError` 打 console\.error

- mirror state 变更打 console\.debug\(dev only\)

## §9 与外部模块的边界

| 外部模块                    | 与 Bridge Protocol 的关系                                                                                                  |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 鉴权桥                      | Bridge Protocol 不参与身份注入。userId 由 ST 通过 Cookie SSO 自行获得，握手时回报给 parent 做一致性校验                    |
| sync\-engine provision\-api | Bridge Protocol 不参与 provisioning 触发或状态查询。前端走 frontend → backend → provision\-api 的 HTTP 链路（React Query） |
| LLM 代理网关                | Bridge Protocol 不参与 LLM 调用。ST 自己向 backend /api/platform/llm\-proxy/v1/ 发请求                                     |
| sync\-engine watcher        | Bridge Protocol 不参与回流。ST 写文件 → watcher 监听 → Supabase                                                            |

## §10 bridge\-client 状态机概要

```YAML
States:
  IDLE → IFRAME_LOADING → HANDSHAKED(①) → READY(②) → CONTEXT_READY(③)
                                      ↓                ↓
                                   FAILED          DISCONNECTED

Transitions:
  IDLE → IFRAME_LOADING: 调用 mount()
  IFRAME_LOADING → HANDSHAKED: 收到 phase=handshake 且校验通过
  HANDSHAKED → READY: 收到 phase=ready
  READY → CONTEXT_READY: 收到 phase=context-ready
  *                  → FAILED: 任意阶段超时或一致性校验失败
  CONTEXT_READY      → DISCONNECTED: ping 连续 3 次无响应
  DISCONNECTED       → IFRAME_LOADING: 调用 reconnect()(可选,阶段二是否实现待定)
```
