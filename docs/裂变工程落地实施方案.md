## 整体实施策略

- **底层先行，端侧并行：** 归因与账务的表结构、RPC 先定稿并评审；C 端 UI 与 B 端配置可并行开发。
- **重核轻表：** 精力放在"归因唯一性"与"发奖幂等性"，全部收敛到数据库约束 + 单一 RPC 事务；页面展示依赖后端直接下发。
- **能复用不新建：** 深链通道、账务流水、config 发布体系、环境隔离全部复用存量能力，本期不引入新基础设施。

## 核心设计（数据与账务）

### 1. 专属邀请码与链接

- ~~`app_core.users` 增加 `invite_code TEXT UNIQUE`~~ **阶段一定稿调整（D3）：** 改由 `miniapp_traffic.invite_codes` 表承载（含 `center_first_entered_at`），裂变属可删功能，不动 `app_core.users` 表结构；短码首次进入邀请中心时懒生成并持久化，对用户永久固定。
- 专属链接格式：`https://t.me/{bot}/{app}?startapp=inv_{invite_code}`。
- **命名空间约定：** `start_param` 以 `inv_` 前缀标识邀请，与渠道归因 `source_id`、支付回跳 `payment_return_` 互不干扰。前端解析入口统一在 `providers.tsx` 的 `getStartParam()` 分发。
- **与渠道归因的关系（需拍板）：** 建议邀请链接进入时 `source_id` 记为固定渠道值（如 `invite`），便于流量报表区分，不与既有渠道混淆。

### 2. 邀请关系表（归因唯一性）

`app_core.invite_relations`：

| 列                | 约束                 | 说明                                           |
| ----------------- | -------------------- | ---------------------------------------------- |
| `id`              | PK                   |                                                |
| `inviter_user_id` | FK users             | 邀请人                                         |
| `invitee_user_id` | FK users，**UNIQUE** | 下级用户，唯一索引兜底"一人只绑一次、不可覆盖" |
| `invite_code`     |                      | 绑定时使用的码，留档                           |
| `bound_at`        |                      |                                                |

- CHECK 约束 `inviter_user_id <> invitee_user_id` 兜底防自邀。
- **绑定时机落点：** TMA 无匿名态，"首次完成登录/账户创建" ≈ 首次打开 MiniApp 时 `getOrCreateMiniappUserByTgId` 完成 insert。让该函数返回"本次是否新建"标志，新增绑定接口（或并入 `/api/growth/miniapp-entry` 同一链路）仅在 **本次新建 = true** 时写入关系——已有账户点链接天然不绑定，无需额外判断。
- **防漏归因：** 复用 `GrowthEntryReporter` 模式，前端把 `inv_` 参数缓存到 sessionStorage，绑定接口成功返回前带重试，避免首次进入的网络抖动把新用户漏成自然量。

### 3. 奖励规则（运营可配）

- managed config key：`miniapp_invite_reward_rules`（JSON），示例结构：

```json
{
  "total_cap_credits": 2200,
  "rules": [
    { "rule_key": "invitee_registered", "credits": 200, "enabled": true },
    { "rule_key": "invitee_first_paid", "credits": 2000, "enabled": false }
  ]
}
```

- `rule_key` 一经发布不可改（发放流水引用它做幂等键）；金额、开关可随时改并走 draft/publish。
- 本期按 PRD 只保证结构可配，不写死具体阶段值。

### 4. 发奖流水与幂等（账务）

`billing.invite_reward_logs`：

| 列                                  | 约束                                         | 说明                                       |
| ----------------------------------- | -------------------------------------------- | ------------------------------------------ |
| `id`                                | PK                                           |                                            |
| `relation_id`                       | FK invite_relations                          |                                            |
| `rule_key`                          |                                              | 引用配置中的规则                           |
| `event_ref`                         |                                              | 业务事件引用（如 invitee user_id、订单号） |
| —                                   | **UNIQUE(relation_id, rule_key, event_ref)** | 防重唯一键                                 |
| `credits` / `status` / `granted_at` |                                              |                                            |

- 新增 SECURITY DEFINER RPC **`grant_invite_reward(relation_id, rule_key, event_ref)`**，单事务内完成：读已发布规则 → 校验单关系累计 ≤ `total_cap_credits` → 插入 `invite_reward_logs`（唯一键冲突即静默返回，天然幂等）→ 写 `billing.wallet_ledger`（新 `entry_type = 'invite_reward'`）并更新 `user_wallets`。对齐 `grant_new_user_signup_bonus` / `admin.grant_user_credits` 既有先例，**不在 TS 层手动加减余额**。

### 5. 事件挂点（替代"通用事件引擎"）

不建事件总线，在有限的既有路径显式调用 RPC：

| 事件                  | 挂点                                                     |
| --------------------- | -------------------------------------------------------- |
| 被邀请人完成注册绑定  | 绑定接口写入 `invite_relations` 成功后同事务/紧随调用    |
| 完成 N 轮对话（备用） | `increment_user_total_round` 路径（chat-history-logger） |
| 首次付费（备用）      | `PaymentSettlement.settlePaidOrder` 唯一入账出口         |

后两个挂点本期只预留 `rule_key`，代码挂点随运营启用对应规则时再接。

### 6. 数据中心查询（实时优先）

- C 端接口直接实时聚合：累计邀请人数（count relations）、累计星尘（sum reward_logs）、最近到账记录（reward_logs 按时间倒序），对 `inviter_user_id` 建索引。当前量级无需预聚合。
- 页面"更新时间"实时态显示为查询时刻。**批量降级（06:00/12:00/19:00/24:00）仅作为预案文档化**：若压测发现实时查询不达标，按支付对账先例用 Railway cron/worker 写快照表，不引入 pg_cron。

**⚠️ 主要风险点：**

- **剪贴板：** `navigator.clipboard.writeText` 必须在用户物理点击的同步执行栈内调用；链接与文案在进入页面时已在本地，复制流程不得插入任何异步请求。
- **并发发奖：** 唯一约束 + RPC 单事务是底线；应用层重试或重复回调都必须被数据库层吸收，禁止任何绕过 RPC 的手动余额修改。
- **绑定竞态：** 首次打开时多个鉴权请求并发，都可能触发 user insert（现有回读幂等）；"本次是否新建"的判定要与绑定接口在同一请求链路内，避免绑定请求到达时用户已被其它请求先建而误判为老用户。

## 阶段三：归因全链路联调与沙盘测试

**🎯 核心目标：** 归因不漏不重、异常拦截有效、发奖幂等经受重放。

**📦 核心产物：**

1. **UAT 用例全量执行**，重点覆盖 PRD 边界情况：
   - A 自邀（点自己链接注册）→ 不建关系不发奖（CHECK 约束兜底）；
   - B 点 A 链接未注册，次日点 C 链接注册 → 归 C；
   - 已注册用户反复点他人链接 → 不新增不覆盖（UNIQUE 兜底）；
   - 同一注册事件重放多次 → `invite_reward_logs` 唯一键只入账一次；
   - 无效/失效邀请码 → 不建关系，前端正常降级展示。
2. **数据中心口径核对：** 邀请人数 / 累计星尘 / 到账记录与流水表逐条对齐；实时查询压测（不达标才启动批量快照预案）。
3. **iOS / Android / Desktop 三端冒烟：** 深链参数、剪贴板、海报展示比例。

**⚠️ 主要风险点：**

- 防刷验证不能只跑接口层，要直接对库重放（并发写 relations、并发调 RPC），确认约束在真实并发下生效。
