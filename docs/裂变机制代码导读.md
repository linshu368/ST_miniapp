## 1. 一句话架构

用户在邀请中心拿到永久固定的 8 位邀请码与深链 `https://t.me/{bot}/{app}?startapp=inv_{code}`；新用户经深链首次打开 MiniApp 时，前端捕获 `inv_` 参数并上报后端，后端在**单个数据库事务**内完成"绑定邀请关系 + 发放注册奖励 + 记账"；归因唯一性和发奖幂等性全部由**数据库约束 + SECURITY DEFINER RPC** 兜底，TypeScript 层不做任何余额加减。

核心原则（读代码前先记住这三条，所有实现都围绕它们）：

1. **归因唯一**：`invite_relations.invitee_user_id` 上的 UNIQUE 约束是唯一事实源——一个用户只能被绑定一次，不可覆盖，任何并发/重放都被这个约束吸收。
2. **发奖幂等**：`invite_reward_logs` 上的 `UNIQUE(relation_id, rule_key, event_ref)` 是幂等键——同一事件重放多少次都只入账一次。
3. **账务收敛**：星尘到账只发生在 `grant_invite_reward` RPC 事务内（写 `billing.user_wallets` + `billing.wallet_ledger`），应用层任何地方都不允许手动改余额。

| 表                   | 关键约束                                                                        | 职责                                                                                     |
| -------------------- | ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `invite_codes`       | `user_id` PK；`code` UNIQUE 且 `CHECK (code ~ '^[A-Z0-9]{8}$')`                 | 用户专属邀请码（懒生成、永久固定）；`center_first_entered_at` 控制"2200星尘"提醒标签显隐 |

**RPC**（均 SECURITY DEFINER，只授 `service_role, postgres`，backend 用 service key 调用）：

| RPC                                                             | 签名 → 返回                                          | 职责                                                                 |
| --------------------------------------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------------- |
| `ensure_invite_code(p_user_id)`                                 | → `(code, first_visit)`                              | 懒生成邀请码 + 标记首次进入邀请中心，码撞车自动换码重试（上限 5 次） |

| `grant_invite_reward(p_relation_id, p_rule_key, p_event_ref)`   | → `(status, credits)`                                | 幂等发奖 + 单关系累计上限 + 记账，所有规则共用                       |

## 3. 核心链路一：深链绑定与发奖（最重要）

```
新用户点 https://t.me/{bot}/app?startapp=inv_{CODE}
  │
  ▼ Telegram 把 inv_{CODE} 注入 initData 的 start_param
┌─ frontend: providers.tsx ──────────────────────────────────────────┐
│ getStartParam() 读出 start_param（唯一的深链参数解析入口）          │
│   ├─ PaymentReturnRedirect：payment_return_ 前缀 → 支付回跳        │
│   ├─ GrowthEntryReporter：非 inv_/payment 前缀 → 渠道归因上报      │
│   │    （inv_ 前缀被显式跳过，否则会被当渠道码走 botlinks 逻辑）    │
│   └─ InviteBindReporter：inv_ 前缀 →                               │
│        1. 剥前缀，正则校验 /^[A-Za-z0-9]{8}$/                      │
│        2. 码存 sessionStorage['invite_bind_pending']（防抖动丢参） │
│        3. POST /api/invite/bind { invite_code }                    │
│        4. 任意终态 → 写 done 标记 + 清 pending；                   │
│           网络失败 → 保留 pending，下次启动重试                    │
└────────────────────────────────────────────────────────────────────┘
  │
  ▼ POST /api/invite/bind（requireTelegramAuth）
┌─ backend: routes/invite.ts ────────────────────────────────────────┐
│ 1. normalizeInviteCode()：非 string / 不合正则 → 直接返回          │
│    invalid_code（HTTP 200，不进 DB；防非字符串入参 500）           │
│ 2. getOrCreateDbUser()：users 行不存在则 insert（≈"注册"时刻；     │
│    并发 insert 冲突时回读，幂等）                                  │
│ 3. 调 RPC bind_invite(invitee_id, code)                            │
│ 4. status='bound' 且 source_id 为空 → 守卫式 UPDATE                │
│    users.source_id='invite'（AND source_id IS NULL，不覆盖渠道值； │
│    失败仅记日志，不影响绑定结果）                                  │
└────────────────────────────────────────────────────────────────────┘
  │
  ▼ RPC bind_invite —— 单事务，判定顺序即代码顺序
┌─ db: miniapp_traffic.bind_invite ──────────────────────────────────┐
│ ① 按 upper(trim(code)) 查 invite_codes → 无 → invalid_code         │
│ ② inviter == invitee → self_invite                                 │
│ ③ 已有关系 → already_bound（返回既有 inviter/relation）            │
│ ④ users.created_at 早于 now()-30min → not_new_user                 │
│    （30 分钟窗是函数内常量，吸收"并发建号与绑定上报的时差"，       │
│      同时保证老账户点链接不绑定）                                  │
│ ⑤ INSERT invite_relations ON CONFLICT (invitee) DO NOTHING         │
│    → 没插进去（并发另一请求先绑）→ 回读按 already_bound 返回       │
│ ⑥ 插入成功 → 内联调 grant_invite_reward(relation,                  │
│    'invitee_registered', invitee_id::text) → 返回 bound            │
│    （绑定与发奖同事务：不存在"绑了没发奖"的中间态）                │
└────────────────────────────────────────────────────────────────────┘
  │
  ▼ RPC grant_invite_reward —— 幂等发奖 + 上限 + 记账
┌─ db: miniapp_traffic.grant_invite_reward ──────────────────────────┐
│ ① SELECT relation FOR UPDATE（锁关系行，串行化同关系并发发奖，     │
│    保证上限校验不被穿透）                                          │
│ ② 读 runtime_config 奖励规则：规则不存在 / enabled=false /         │
│    credits<=0 → 返回 skipped                                       │
│ ③ 该关系已发累计 >= total_cap_credits → 返回 cap_reached           │
│    未超但本次会超 → 截断本次金额（累计恰好 = cap）                 │
│ ④ INSERT invite_reward_logs ON CONFLICT (invite_reward_dedup)      │
│    DO NOTHING → 没插进去 → 返回 duplicated（幂等出口，账务零变化） │
│ ⑤ UPDATE user_wallets bonus_credits += 金额                        │
│    + INSERT wallet_ledger（entry_type='invite_reward'，            │
│    reference_id=发奖明细 id，metadata 带 rule_key/relation/event） │
│    → 返回 granted                                                  │
└────────────────────────────────────────────────────────────────────┘
```

### PRD 边界情况在此链路中的落点

| 边界情况                             | 由谁兜底                                                            |
| ------------------------------------ | ------------------------------------------------------------------- |
| A 点自己的链接注册                   | `bind_invite` ② + 表上 `CHECK (inviter <> invitee)` 双保险          |
| B 点 A 链接未注册、次日点 C 链接注册 | 绑定发生在"首次完成登录"时刻，谁的码在场归谁（last click wins）     |
| 已注册用户反复点他人链接             | ④ 时间窗 → `not_new_user`；若已有关系则 ③ → `already_bound`，不覆盖 |
| 同一注册事件重放 N 次                | invitee UNIQUE（关系层）+ `invite_reward_dedup`（发奖层）双层吸收   |
| 无效/乱码邀请码                      | 后端正则先拦（不进 DB），进了 DB 也在 ① 拦 → `invalid_code`         |

## 4. 其余核心链路

### 4.1 邀请中心初始化（拿码、素材）

```
进入 /profile/invite（前提：entry_enabled=true，否则页面展示"暂未开启"且不发请求）
  → useInviteCenterQuery（POST /api/invite/center-view，幂等 POST 按查询建模，staleTime=Infinity）
    → backend：ensure_invite_code RPC（首次：生成 8 位大写码 + 落 center_first_entered_at；
       此后：码不变，first_visit=false）
    → 并行读 miniapp_invite_center_config + buildMiniappDeepLink('inv_'+code)
    → 返回 { invite_code, invite_link, poster_url, copy_templates, first_visit }
  → first_visit=true 时前端本地翻转 entry-status 缓存 → "2200星尘"标签立即消失
    （服务端字段已同步落库，多设备/清缓存后一致）
```

细节（都是代码事实，容易被想当然）：

- `ensure_invite_code` 的懒生成写在 **insert-first** 风格里：直接尝试 INSERT，撞 unique 再区分"用户已有码"（回读，必要时补记首次进入时间）与"码撞车"（换码重试，上限 5 次）。
- bot token 不可用时（本地 MOCK_AUTH），`invite_link` 降级为空串，前端展示"链接暂时无法生成"提示，复制内容不含链接。
- **`center-view` 服务端不校验入口开关**——开关只在前端页面层拦（`useInviteCenterQuery(centerEnabled)` 的 enabled 参数）。直接打接口仍会生成码，这是刻意的（开关关闭期间绑定链路仍要生效，见 §5.6）。

### 4.2 文案编辑与复制（纯本地，无请求）

邀请 Tab 的文案框逻辑全部在 `profile/invite/page.tsx` 的 `InviteTabPanel`：

- 初值 = `copy_templates[0]` 做 `{link}` 替换（`replaceAll`）；模板库为空时降级为裸链接；
- 刷新按钮：`templateIndexRef` 取模轮换模板，**覆盖用户手动修改**，不发请求；
- 复制按钮：`navigator.clipboard.writeText(draft)` 是 onClick 的**第一个调用，前面没有任何 await**（硬约束：writeText 必须在用户点击的同步栈内，否则 Telegram 内嵌 WebView 会拒绝）。成功后 1.5s 行内反馈。迭代时若要在复制前加逻辑，**不得插入异步操作**。

### 4.3 数据中心（实时聚合）

```
数据中心 Tab 激活 → useInviteStatsQuery（staleTime=0 + refetchOnMount='always'）
  → GET /api/invite/stats
    → 并行两查（invite_relations count + invite_reward_logs 全量行按时间倒序）
    → invited_count = count；total_reward_credits = 全量行求和；
      recent_rewards = 前 10 条（RECENT_REWARDS_LIMIT）；
      updated_at = 查询时刻；update_mode 恒 'realtime'
```

- 阶段三实测聚合额外开销 ≈0ms，**维持实时方案**；`update_mode: 'batch'` 是批量快照预案的占位字段，前端已实现对应展示分支，但后端永远返回 `realtime`。若未来量级上来要做快照降级，改后端此接口 + Railway cron 即可，契约无需变。
- 注意 `total_reward_credits` 是把该邀请人**全量**发奖行拉回来在 JS 里求和（当前量级无压力）；数据量大后应改成 DB 侧 SUM。

### 4.4 运营配置链路（B 端 → C 端）

```
admin config 视图（三个专用编辑器）→ 保存草稿 → 发布
  → admin.config_releases（白名单 CHECK + validate_managed_config_value 分支校验）
  → 生效到 app_core.runtime_config
  → backend fetchRuntimeConfigEntry 读取（有进程内缓存，分钟级生效）
```

### 4.5 admin 邀请数据查询

```
InviteProgramView 邀请数据 Tab
  → lib/inviteAdminApi.listInviteRecords
  → supabase client.schema('admin').rpc('list_invite_records', {...})（经 /api/admin/supabase 代理，持 anon key + admin 用户 JWT）
  → 106 的 SECURITY DEFINER RPC：函数体内先 can_access_environment 鉴权（依赖 auth.uid()），
    再查 relations 左联 reward_logs 聚合（LATERAL）+ 双侧用户昵称，窗口函数给 total_count
```

- 筛选口径：邀请人/被邀请人同时匹配 UUID 或 tg_id（`resolve_invite_user_ref`，查无此人直接返回空集）；奖励状态 `granted`（有到账）/`none`（零到账）；绑定时间闭开区间 `[from, to)`（前端把结束日 +1 天保证整天覆盖）；分页 limit 1..200 缺省 50。
- 权限模型：函数 GRANT 给 `authenticated`，但真正的鉴权在函数体内（无有效 admin JWT 即 42501）；`resolve_invite_user_ref` 不 GRANT 给任何客户端角色；`anon` 无 EXECUTE（迁移尾部自检保证）。
- **admin 侧任何 `.from('invite_*')` 直查都是错误路径**（RLS 拦截），新增 admin 查询需求一律新增/扩展 admin RPC。

## 5. 必须维持的设计不变量（迭代红线）

改动裂变代码前逐条核对，破坏任何一条都会产生资损或归因事故：

### 5.1 幂等键 `rule_key` 一经发布不可改名

`invite_reward_logs` 的幂等唯一键包含 `rule_key`。改名 = 同一事件换了幂等键 = **重复发奖**。admin 编辑器已在 UI 层锁死（`InviteRewardRulesEditor` 中 rule_key 只读、无删除入口），迭代时不得开放。金额与 enabled 可随时改。

### 5.2 发奖只走 `grant_invite_reward` RPC

任何新奖励事件（如未来启用首付奖励）都必须调这个 RPC，禁止在 TS 层手动 UPDATE 钱包。RPC 内的 `FOR UPDATE` 行锁 + 唯一键 + cap 截断是完整的并发安全闭环，绕过任何一环都会出账务问题。

### 5.3 `start_param` 通道的前缀命名空间

一条 `startapp` 深链通道三方共用，解析统一收敛在 `providers.tsx` 的 `getStartParam()` 及三个并列 Reporter：

| 前缀                                 | 归属                 | 消费者                                                 |
| ------------------------------------ | -------------------- | ------------------------------------------------------ |
| `payment_return_` / `payment_return` | 支付回跳             | `PaymentReturnRedirect`                                |
| `inv_`                               | 邀请绑定             | `InviteBindReporter`（`GrowthEntryReporter` 显式跳过） |
| 其它任意值                           | 渠道归因 `source_id` | `GrowthEntryReporter`                                  |

新增深链场景必须：定义新前缀 + 在 `GrowthEntryReporter` 加跳过分支，否则新参数会被当渠道码上报 `/api/growth/miniapp-entry` 走 botlinks 逻辑。

### 5.4 `source_id='invite'` 是守卫式写入

只在 `status='bound'` 且 `source_id IS NULL` 时 UPDATE（SQL 里带 `AND source_id IS NULL`），不覆盖既有渠道值，不调渠道表的 `increment_click`。邀请人↔被邀请人的对应关系由 `invite_relations` 承载，`source_id` 只用于流量报表分类。

### 5.5 绑定终态语义与前端重试

除 `invalid_code` 外所有 bind 状态都是幂等终态。前端的重试协议依赖这一点：`sessionStorage['invite_bind_pending']`（网络失败保留，下次启动重试）+ `invite_bind_done`（终态去重）。若未来新增 bind 状态，必须保证它要么是终态、要么明确加入前端"保留 pending"分支。

### 5.6 入口开关不拦截绑定链路

`miniapp_invite_entry_enabled=false` 只隐藏 C 端三处入口和邀请中心页内容，`/api/invite/bind` **依旧生效**（UAT `entry_switch` 场景显式断言了这一点）。目的：运营临时关开关期间，已散发出去的链接不漏归因。迭代时不要"顺手"在 bind 里加开关校验。

### 5.7 新用户判定 = 30 分钟时间窗

`bind_invite` 内常量 `INTERVAL '30 minutes'`（对 `users.created_at`）。不能改成"本次请求是否 insert"判定：首开时多个鉴权请求并发建号，绑定请求到达时用户行可能已被别的请求先建，会误判老用户漏归因。调整窗口值走新迁移改函数。

### 5.8 邀请码正则有三处副本，必须同步改

`^[A-Za-z0-9]{8}$`（大小写在 RPC 内 `upper(trim())` 归一）分布在：

1. `packages/backend/src/routes/invite.ts` 的 `INVITE_CODE_RE`；
2. `packages/frontend/src/app/providers.tsx` 的 `INVITE_CODE_RE`；
3. `105` 迁移中 `invite_codes.code` 的 CHECK（`^[A-Z0-9]{8}$`，存储侧只有大写）。

若未来改码长/字符集，三处 + `ensure_invite_code` 的生成逻辑要一起动。

## 6. 常见迭代场景怎么做

### 6.1 启用"被邀请人首次付费"奖励

代码挂点已就绪（109 迁移 + backend），**剩下的只是运营在 admin 把 `invitee_first_paid` 的 `enabled` 翻 `true` 并发布**，金额可同时调整。链路：

```
PaymentSettlement.settlePaidOrder  ← 四条入账路径（webhook/return/query/cron）的唯一出口
  └─ orders.complete() 成功后
     └─ lib/invite-rewards.ts  checkInviteFirstPaidReward({ userId, orderId }, log)
        └─ RPC check_invite_first_paid_reward(invitee, order_id)
           ├─ 无邀请关系            → no_relation
           ├─ 订单未入账            → not_settled
           ├─ 该用户已入账订单 > 1  → not_first_paid
           ├─ 本关系已发过首付奖     → duplicated
           └─ 否则 grant_invite_reward(relation_id, 'invitee_first_paid', order_id)
                                     → granted / skipped（规则未启用）/ cap_reached
```

接手时需要知道的四件事：

1. **"首次"判定数的是已入账订单笔数，不是 `user_wallets.first_paid_at`**。`complete_payment_order` 会把 `first_paid_at` 置成本次付费时间，而挂点跑在入账之后，那个字段永远非空、区分不出首笔。代价是同一用户两笔订单几乎同时入账时会双双判成非首付、漏发一次——宁可漏发不重发。
2. **挂点不按 `order.status` 跳过重放**：判定 RPC 自带幂等，重放反而给上一次失败的判定一次重试机会（挂点失败只写日志不抛，不会拖垮入账）。
3. **`event_ref` 是订单号**，同时另有一层"同一关系只发一次 `invitee_first_paid`"的规则级去重，跨订单也不会重发。
4. **cap 会截断**：`total_cap_credits` 默认 2200，轮次奖励 200 + 首付 2000 刚好卡满。运营调高轮次金额后，首付这笔会被 `grant_invite_reward` 静默截断（`LEAST`），只表现为流水金额变小。

UAT 覆盖：`first_paid_reward_grant`（首笔发奖 / 同单重放 / 复购不发）与 `first_paid_reward_late_enable`（规则中途启用不给老付费用户补发），两者都会临时改 config 并在 finally 里还原。C 端与 admin 文案早已收录该 key，无需改动。

### 6.2 新增一条奖励规则（全新 rule_key）

1. admin 奖励规则编辑器加规则行（或直接改 config JSON 发布）——注意当前编辑器**没有"新增行"入口**（阶段二刻意后置），需要先给 `InviteRewardRulesEditor` 补新增能力或走 DB seed；
2. 在对应业务路径挂 `grant_invite_reward` 调用点（无事件总线，显式挂点是本设计的刻意选择）；
3. 给 C 端 `RULE_LABELS` 和 admin `INVITE_RULE_KEY_LABELS` 补中文名（未收录会回落展示原始 rule_key，不会坏）。

### 6.3 调整奖励金额 / 总上限

纯运营操作：admin → 裂变邀请奖励规则 → 改 `credits` / `total_cap_credits` → 发布。注意 cap 只对"单个关系的累计"生效且触顶时**截断**本次金额（不是拒发），把 cap 调小不会追回已发的。

### 6.4 上线 / 下线功能

- 上线：生产库按序执行 105、106、108、109 迁移（GHA Database Migration）→ 代码随 Railway/Vercel 发布 → admin 生产环境把 `miniapp_invite_entry_enabled` 发布为 `true`；
- 临时下线：开关翻 `false` 即可（入口全隐，绑定链路保留）；
- 永久下线：裂变三表设计上归 `miniapp_traffic` 域、可整体删除，但 `wallet_ledger` 的 `invite_reward` 流水是不可删账务，会留存。

### 6.5 数据中心改批量快照

契约已留口（`update_mode: 'batch'`，前端展示分支已实现）。做法按支付对账先例：Railway cron/worker 写快照表 → `/api/invite/stats` 改读快照并返回 `batch` + 快照时间。不引入 pg_cron。
