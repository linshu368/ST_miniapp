## 0. 先回答：现在能不能在 preview 上验？

**能验九成，但裂变最核心的那一成（`startapp` 深链入口）不能直接在 PR preview 上验。**

各层现状：

| 层                                | PR preview 状态                                                              | 结论 |
| --------------------------------- | ---------------------------------------------------------------------------- | ---- |
| 前端                              | Vercel Preview 自动构建本 PR                                                 | ✅   |
| 后端                              | `railway-pr-env.yml` 自动拉起 `stminiapp-pr-{N}`（仅当 PR base = `dev`）     | ✅   |
| 前端 → 后端指向                   | `next.config.mjs` 按 `VERCEL_GIT_PULL_REQUEST_ID` 自动拼 pr-{N} 域名，免配置 | ✅   |
| 数据库                            | pr 环境继承 development 变量 → **test 库**；105/106 已在 test 库执行         | ✅   |
| CORS                              | pr 后端带 `DEV_AUTH_BYPASS=1` → 放行 `*.vercel.app`                          | ✅   |
| initData 鉴权                     | 只校验 bot token，与前端域名无关                                             | ✅   |
| **`t.me/{bot}/app?startapp=...`** | Telegram 只会打开 BotFather 里给该 bot 注册的**固定** Web App URL            | ❌   |

深链不会带你去 PR preview 域名——它只认 bot 上登记的那一个 URL。而"新用户点邀请链接首开完成绑定"正是本期的核心链路，绕不过去。

### 两条可选路径（在开跑前先选定）

**路径 A（推荐）：先合进 `dev`，在 dev 栈上验。**
Vercel dev 部署 + Railway `development` + test 库，测试 bot 的 Mini App URL 本来就指向这里，零配置，和阶段二联调是同一套环境。
代价：`dev` 上先落一份未经真机验收的代码。可接受的理由是——生产 `miniapp_invite_entry_enabled` 保持 `false`（代码上线 ≠ 功能上线），且 105/106 尚未对生产库执行，`dev` 到生产之间还隔着阶段四。

**路径 B：临时把测试 bot 的 Mini App URL 指向 Vercel Preview。**
在 BotFather 里把短名 `app` 的 URL 改成 Preview 的**分支固定别名**（形如 `xxx-git-dev-viral-loops-xxx.vercel.app`，不要用每次 commit 都变的那个 URL），验完改回。

> ⚠️ 路径 B 的**前置红线**：必须先确认测试 bot 与生产 bot 是两个不同的 bot（对比 Railway `development` 与 `production` 两个环境的 `TELEGRAM_BOT_TOKEN` 是否相同）。若是同一个 bot，改 URL 会把生产用户一起切到 preview，**直接否决路径 B**。

下面的步骤两条路径通用，差别只在 §1.1「打开哪个 MiniApp」。

### 0.1 本次选定：路径 B —— 开跑前的四步准备

**第 1 步：过安全红线（不通过就停，改走路径 A）**

Railway 控制台 → 项目 `stminiapp` → 分别打开 `development` 和 `production` 两个环境的 Variables，对比 `TELEGRAM_BOT_TOKEN`。
只需要看**冒号前的那串数字**（bot id），不用看完整 token。

- 两个 bot id **不同** → 测试 bot 与生产 bot 是两个 bot，路径 B 安全，继续
- 两个 bot id **相同** → 改 URL 会把生产用户一起切到 preview，**立即停止，改走路径 A**

**第 2 步：拿到 Vercel Preview 的分支固定别名**

Vercel Dashboard → frontend 项目 → Deployments → 找到分支 `dev_viral_loops` 的最新 Preview 部署，进详情页的 Domains 区。
那里会列出两类 URL：

- 每次 commit 都变的 `xxx-<随机hash>-xxx.vercel.app` —— **不要用这个**
- 分支固定别名 `xxx-git-dev-viral-loops-xxx.vercel.app` —— **用这个**

用固定别名的原因：验收过程中如果往分支推了修复 commit，别名会自动指向新部署，不用回 BotFather 再改一次。

**第 3 步：确认 pr-{N} 后端已就绪**

PR 页面里 Railway 机器人的评论会给出 `https://stminiapp-pr-{N}.up.railway.app`。
前端 Preview 构建时会按 PR 号自动指向它，不需要在 Vercel 里手配环境变量。
若 PR 评论不存在，检查 PR 的 base 分支是不是 `dev`——`railway-pr-env.yml` 只对 base 为 `dev` 的 PR 生效；同时 PR 不能是 Draft 状态。

**第 4 步：在 BotFather 改测试 bot 的 Mini App URL**

BotFather → `/myapps` → 选测试 bot 的短名 `app` 的那个 App → `Edit Web App URL` → 贴第 2 步的分支别名。
（若该 bot 没有配 App、走的是菜单按钮，则改 `/mybots` → 选 bot → `Bot Settings` → `Menu Button`。但注意：**深链 `?startapp=` 依赖的是 App 短名那条配置**，菜单按钮不承载 `startapp`，两者别改混。）

改完先做一次冒烟。**冒烟必须带 `startapp` 参数**，光验「App 能打开」是不够的（原因见 §0.2）：

1. 手机上点开 `https://t.me/<测试bot>/app?startapp=inv_ZZZZ9999`（一个不存在的码，故意的）
2. MiniApp 正常拉起 → 说明 App 短名那条配置指过来了
3. Desktop 端开 webview 控制台，应能看到 `[Invite] bind result: invalid_code` → 说明 `startapp` 确实传到了前端

只做到第 1 步不能算通过：菜单按钮和 App 短名是两条独立配置，菜单按钮指对了也能把 App 打开，但它不承载 `startapp`。

> ⚠️ **冒烟跑完必须杀进程重开。** 拿到任何终态（含 `invalid_code`）后前端会把 `invite_bind_done=1` 写进 sessionStorage，同一会话内不再发第二次绑定请求。用这台设备上的哪个号做冒烟，就别让那个号在同一会话里接着跑组 3——否则真链接会被静默跳过，复现出一模一样的"没痕迹"假象。冒烟建议用账号 A（邀请人，本来就绑不上）而不是烧掉一个新号。

> ⚠️ **验收结束后立刻把 URL 改回 dev 固定域名**（不是"改回原值"——路径 B 用完时 PR 多半已经合并，preview 别名已经失效，见 §0.2）：
> dev 固定域名 = `https://st-miniapp-frontend-dev.vercel.app/`

### 0.2 ⚠️ 路径 B 的退场陷阱（0901 真机验收踩过，必读）

**症状：** 新号点邀请链接后，MiniApp 能正常打开、`app_core.users` 里账号也正常落库，但 `invite_relations` 零新增、邀请人没有奖励到账。看起来像"App 好好的，就是不发奖"，很容易把矛头指向 Supabase 函数或发奖规则配置。

**根因：** PR 合并进 `dev` 之后，`railway-pr-env.yml` 拉起的 `stminiapp-pr-{N}` 后端会被**销毁**，而 BotFather 里 App 短名 `app` 的 URL 还停在 preview 分支别名上。此时：

- **菜单按钮**指向的是能正常工作的地址 → 用户还是能把 MiniApp 打开、账号照常创建
- **App 短名**那条配置已经失效 → `t.me/<bot>/app?startapp=inv_XXXXXXXX` 拉不起小程序

用户点链接失败后，往往会顺手从 bot 菜单按钮进 App。这一次进入**不带 `startapp`**，前端 `InviteBindReporter` 取不到参数直接 return，**连绑定请求都不会发出**，所以库里不留任何痕迹。

**三十秒定位法：** 查被邀请人的 `app_core.users.source_id`。

| `source_id`                        | 含义                                                                       |
| ---------------------------------- | -------------------------------------------------------------------------- |
| `invite`                           | 绑定成功过。没奖励要往发奖规则 / cap 方向查                                |
| `NULL`，且 `invite_relations` 零行 | 绑定请求压根没发或没成功。**先查 BotFather 的 App 短名 URL，不要查数据库** |

**确认后端和数据库是否无辜**（这一步能把 §0.2 和真正的库层问题一刀切开）：

```bash
# 不带任何鉴权头也能通（dev 环境 DEV_AUTH_BYPASS=1 会回落到 mock 用户）
curl -s -X POST https://stminiapp-development.up.railway.app/api/invite/bind \
  -H 'content-type: application/json' -d '{"invite_code":"<某个真实存在的邀请码>"}'
```

返回 `{"status":"not_new_user"}` 就说明**路由已部署、`bind_invite` RPC 执行正常、邀请码查得到**，问题一定在深链没送达，不在后端和库。返回 404 说明后端没部署，返回 `invalid_code` 说明码不存在。

> 该接口在 dev 环境无鉴权即可访问是 `DEV_AUTH_BYPASS=1` 的预期行为；**阶段四上生产前必须确认 production 的 Railway 变量里没有这一项**。

**避坑做法：** 合并进 `dev` 的那一刻就把 App 短名 URL 改成 dev 固定域名 `https://st-miniapp-frontend-dev.vercel.app/`，不要等验收跑完再改。

## 1. 开跑前置检查（约 10 分钟，逐项确认再开始）

## 4. 组 3：核心归因链路（账号 B）★ 本轮最重要

**3-1 新用户经邀请链接首开**

- 操作：把 A 复制的链接发给 B（或发到收藏夹后在 B 的设备上打开）。B 必须**从未打开过**这个测试 MiniApp。B 点链接 → MiniApp 启动 → 走完首次进入流程
- 预期（B 侧）：正常进入首页，**不出现任何邀请相关的提示或弹窗**（设计如此，被邀请人无感知）
- 结果：☐

**3-2 五方数据交叉核对**（跑 §6.2 的 SQL，把 A、B 的 tg_id 填进去）

| #   | 核对点               | 期望                                                                        | 结果 |
| --- | -------------------- | --------------------------------------------------------------------------- | ---- |
| a   | `invite_relations`   | 新增**恰 1 行**：inviter = A，invitee = B，`invite_code` = A 的码           | ☐    |
| b   | `invite_reward_logs` | 新增**恰 1 行**：`rule_key = invitee_registered`，`credits` = 配置值（200） | ☐    |
| c   | `wallet_ledger`      | A 名下新增**恰 1 行** `entry_type = 'invite_reward'`，`bonus_delta = +200`  | ☐    |
| d   | `user_wallets`       | A 的 `bonus_credits` 增量 = 200，且与 ledger 的 `balance_bonus` 一致        | ☐    |

### 9.2 一把梭核对（组 3 主链路）

```sql
with a as (select id from app_core.users where tg_id = '<A的tg_id>'),
     b as (select id from app_core.users where tg_id = '<B的tg_id>')
select
  (select count(*) from miniapp_traffic.invite_relations
     where inviter_user_id = (select id from a))                         as 关系数,
  (select count(*) from miniapp_traffic.invite_relations
     where invitee_user_id = (select id from b))                         as B被绑次数,
  (select count(*) from miniapp_traffic.invite_reward_logs
     where inviter_user_id = (select id from a))                         as 发奖明细数,
  (select coalesce(sum(credits),0) from miniapp_traffic.invite_reward_logs
     where inviter_user_id = (select id from a))                         as 明细星尘和,
  (select coalesce(sum(bonus_delta),0) from billing.wallet_ledger
     where user_id = (select id from a) and entry_type = 'invite_reward') as 账务星尘和,
  (select bonus_credits from billing.user_wallets
     where user_id = (select id from a))                                 as A当前bonus余额,
  (select source_id from app_core.users where id = (select id from b))    as B的source_id;
```

**判定：`关系数` = `发奖明细数`；`明细星尘和` = `账务星尘和`；`B被绑次数` = 1；`B的source_id` = `invite`。**

### 9.3 明细逐条看

```sql
select r.bound_at, r.invite_code,
       ui.tg_id as 邀请人, uv.tg_id as 被邀请人,
       l.rule_key, l.credits, l.granted_at
from miniapp_traffic.invite_relations r
join app_core.users ui on ui.id = r.inviter_user_id
join app_core.users uv on uv.id = r.invitee_user_id
left join miniapp_traffic.invite_reward_logs l on l.relation_id = r.id
where ui.tg_id = '<A的tg_id>'
```

### 9.6 附录：回收一个已被绑定的账号（仅限 test 库，账号不够时用）

> ⚠️ 会删掉账务流水，破坏"账务不可删"原则。**只能在 test 库跑**，且跑完后 §9.2 的历史累计数会失真。优先用新账号。

```sql
-- 把 <B的tg_id> 换成要回收的被邀请人
with b as (select id from app_core.users where tg_id = '<B的tg_id>'),
     rel as (select id, inviter_user_id from miniapp_traffic.invite_relations
             where invitee_user_id = (select id from b)),
     logs as (select id, credits, inviter_user_id from miniapp_traffic.invite_reward_logs
              where relation_id in (select id from rel))
-- 1) 回滚钱包
update billing.user_wallets w
set bonus_credits = w.bonus_credits - (select coalesce(sum(credits),0) from logs)
where w.user_id = (select inviter_user_id from rel limit 1);

delete from billing.wallet_ledger
where entry_type = 'invite_reward'
  and reference_id in (
    select l.id::text from miniapp_traffic.invite_reward_logs l
    join miniapp_traffic.invite_relations r on r.id = l.relation_id
    where r.invitee_user_id = (select id from app_core.users where tg_id = '<B的tg_id>'));

delete from miniapp_traffic.invite_reward_logs
where relation_id in (
  select id from miniapp_traffic.invite_relations
  where invitee_user_id = (select id from app_core.users where tg_id = '<B的tg_id>'));

delete from miniapp_traffic.invite_relations
where invitee_user_id = (select id from app_core.users where tg_id = '<B的tg_id>');

-- 2) 把账号推回 30 分钟新用户窗
update app_core.users set created_at = now(), source_id = null
where tg_id = '<B的tg_id>';
```

回收后 C 端必须**杀进程重开**（清掉 sessionStorage 里的 `invite_bind_done`），否则不会再发绑定请求。
