## 1. 绑定链路时序（编码依据）

```
新用户点 https://t.me/{bot}/{app}?startapp=inv_{code}
  → MiniApp 启动，providers.tsx getStartParam() 读到 inv_ 前缀
  → 前端缓存到 sessionStorage（防网络抖动丢参）
  → POST /api/invite/bind { invite_code }（requireTelegramAuth）
      → getOrCreateDbUser（不存在则 insert，触发既有注册赠送 trigger）
      → RPC miniapp_traffic.bind_invite(invitee_id, code)  ←—— 单事务
           ├─ 查 invite_codes 拿 inviter；查不到 → status='invalid_code'
           ├─ inviter = invitee → status='self_invite'
           ├─ invitee.created_at 超出 30 分钟窗 → status='not_new_user'
           ├─ INSERT invite_relations（invitee 唯一索引，冲突 → status='already_bound'）
           └─ 绑定成功 → 内部调 grant_invite_reward(relation, 'invitee_registered', invitee_id)
      → 绑定成功后：UPDATE users SET source_id='invite' WHERE id=… AND source_id IS NULL
  → 前端收到成功/终态响应后清 sessionStorage；网络失败则下次启动重试
```

要点：

- 除 `invalid_code` 外所有状态均为**终态**（幂等，重复请求返回同一结果），前端可安全重试。
- `bind_invite` 与发奖在同一个数据库事务里，不存在"绑了没发奖"的中间态。
- 已有账户点任何邀请链接：`not_new_user` / `already_bound`，不新增不覆盖，满足 PRD 唯一关系要求。

## 2. 任务一：迁移脚本 `105_invite_program.sql`

位置 `packages/shared/migrations/`（顺延当前最大号 104；101/102 历史缺号不补）。经 GHA `Database Migration` 先 test 后 production 手动执行。以下为 DDL 草案，编码时以此为准微调。

### 2.1 邀请码表

```sql
CREATE TABLE miniapp_traffic.invite_codes (
  user_id                 UUID PRIMARY KEY REFERENCES app_core.users(id),
  code                    TEXT NOT NULL UNIQUE,          -- 8 位大写 base32 随机短码，永久固定
  center_first_entered_at TIMESTAMPTZ,                   -- 首次进入邀请中心时间（控制"2200星尘"提醒标签显隐）
  created_at              TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

- 懒生成：用户首次打开邀请中心时由后端生成并插入（冲突重试）。
- "首次提醒标签"不用 localStorage，读 `center_first_entered_at IS NULL`。

### 2.2 邀请关系表（归因唯一性核心）

```sql
CREATE TABLE miniapp_traffic.invite_relations (
  id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  inviter_user_id  UUID NOT NULL REFERENCES app_core.users(id),
  invitee_user_id  UUID NOT NULL UNIQUE REFERENCES app_core.users(id),  -- 一人只绑一次、不可覆盖
  invite_code      TEXT NOT NULL,
  bound_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT invite_no_self CHECK (inviter_user_id <> invitee_user_id)
);
CREATE INDEX idx_invite_relations_inviter ON miniapp_traffic.invite_relations (inviter_user_id, bound_at DESC);
```

### 2.3 发奖流水表（幂等核心）

```sql
CREATE TABLE miniapp_traffic.invite_reward_logs (
  id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  relation_id      UUID NOT NULL REFERENCES miniapp_traffic.invite_relations(id),
  inviter_user_id  UUID NOT NULL,                        -- 冗余列，数据中心按邀请人聚合用
  rule_key         TEXT NOT NULL,                        -- 引用 config 中的规则，发布后不可改名
  event_ref        TEXT NOT NULL,                        -- 业务事件引用（本期为 invitee user_id）
  credits          INTEGER NOT NULL CHECK (credits > 0),
  granted_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT invite_reward_dedup UNIQUE (relation_id, rule_key, event_ref)
);
CREATE INDEX idx_invite_reward_inviter ON miniapp_traffic.invite_reward_logs (inviter_user_id, granted_at DESC);
```

- 星尘到账本体记在 `billing.wallet_ledger`（不可删账务）；本表是裂变业务明细，随功能可整体下线。

### 2.4 运营配置 seed（`app_core.runtime_config`）

| key                            | 初值（草案）                                                                                                                                                           | 说明                                                                              |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `miniapp_invite_reward_rules`  | `{"total_cap_credits":2200,"rules":[{"rule_key":"invitee_registered","credits":200,"enabled":true},{"rule_key":"invitee_first_paid","credits":2000,"enabled":false}]}` | `rule_key` 稳定不可改；金额/开关运营随时发布调整。**注册奖励占位 200 待运营确认** |
| `miniapp_invite_center_config` | `{"poster_url":"","copy_templates":["快来和我一起玩…{link}"]}`                                                                                                         | 海报 URL + 已发布文案库（C 端刷新按钮轮换来源）                                   |
| `miniapp_invite_entry_enabled` | `false`                                                                                                                                                                | 全局入口开关；生产先关后开，代码上线 ≠ 功能上线                                   |

同一迁移内完成 **admin 管理白名单注册四件套**（对齐 095 模式与教训）：`admin.config_drafts` / `admin.config_releases` 两处 `config_key` CHECK 重建、`admin.is_managed_config_key`、`admin.validate_managed_config_value` 新增分支（其中 `miniapp_invite_reward_rules` 配一个结构校验函数 `admin.validate_invite_reward_rules(jsonb)`：校验 cap 为正、rules 数组结构、rule_key 非空且唯一）。**必须复制当前完整 key 列表整段重建，并在迁移尾部加 DO 块自检**（095 曾因并行迁移互相覆盖白名单出过事故）。

### 2.5 账务：`entry_type` 扩展

```sql
ALTER TABLE billing.wallet_ledger
  DROP CONSTRAINT IF EXISTS wallet_ledger_entry_type_check;
ALTER TABLE billing.wallet_ledger
  ADD CONSTRAINT wallet_ledger_entry_type_check
  CHECK (entry_type IN ('recharge', 'chat_debit', 'refund', 'adjustment',
                        'checkin_bonus', 'wish_reward', 'invite_reward'));
```

（沿用 021/086 加 `wish_reward` 的先例；同样注意与并行迁移的覆盖冲突。）

### 2.6 RPC：发奖（幂等 + 上限）

```sql
CREATE FUNCTION miniapp_traffic.grant_invite_reward(
  p_relation_id UUID, p_rule_key TEXT, p_event_ref TEXT
) RETURNS ... SECURITY DEFINER
```

事务内逻辑（模板：031 `grant_new_user_signup_bonus`、066 `admin.grant_user_credits`）：

1. 读 `runtime_config.miniapp_invite_reward_rules`，规则不存在 / `enabled=false` / `credits<=0` → 直接返回 `skipped`；
2. 校验单关系累计：`SUM(credits)` over 该 `relation_id` + 本次 ≤ `total_cap_credits`，超限截断或跳过；
3. `INSERT invite_reward_logs … ON CONFLICT ON CONSTRAINT invite_reward_dedup DO NOTHING`，未插入行 → 返回 `duplicated`（幂等出口，吸收一切重放）；
4. `SELECT … FOR UPDATE` 锁邀请人钱包 → `UPDATE billing.user_wallets SET bonus_credits = bonus_credits + …` → `INSERT billing.wallet_ledger`（`entry_type='invite_reward'`，`reference_type='invite_reward'`，`reference_id=` 流水 id，`metadata` 带 `rule_key`/`relation_id`/`event_ref`）。

权限：`REVOKE ALL FROM PUBLIC, anon, authenticated; GRANT EXECUTE TO service_role, postgres;`

### 2.7 RPC：绑定（归因唯一 + 内联发奖）

```sql
CREATE FUNCTION miniapp_traffic.bind_invite(
  p_invitee_user_id UUID, p_invite_code TEXT
) RETURNS TABLE (status TEXT, inviter_user_id UUID, relation_id UUID) SECURITY DEFINER
```

判定顺序（全部为终态返回，见 §1）：

1. 按 code 查 `invite_codes` → 无 → `invalid_code`；
2. 自邀 → `self_invite`（CHECK 约束兜底）；
3. 已有关系 → `already_bound`（UNIQUE 兜底并发）；
4. `users.created_at < now() - interval '30 minutes'` → `not_new_user`；
5. INSERT 关系成功 → 调 `grant_invite_reward(relation, 'invitee_registered', invitee_id::text)` → `bound`。

时间窗先以常量写在函数内并注释，调整走后续迁移。权限同 2.6。

### 2.8 迁移不做的事

- 不建 pg_cron / 快照表（实时查询方案，主方案 §6）；
- 不动 `app_core.users` 表结构（invite_code、首次进入标记均在 `miniapp_traffic` 域内闭环）；
- 不建独立 `invite_reward_rules` 表（规则走 managed config）。
