## 2. 产物：`invite-uat` 脚本

仿 `mvp-regression` 既有先例（同为"占端口 + 写真库 + 手动跑"定位，不塞进 `pnpm test`）：

```
packages/backend/src/scripts/invite-uat/
  run.ts        入口：环境守卫、起 app、跑场景、还原核对、快照
  scenarios.ts  20 个场景与断言
  fixtures.ts   造数与库侧读写（带重试的脚本专用 Supabase 客户端）
  client.ts     四条邀请路由的 HTTP 客户端（MOCK_AUTH initData）
```

跑法：

```bash
pnpm --filter @miniapp/backend invite:uat
pnpm --filter @miniapp/backend invite:uat -- --scenario concurrency_bind_http
pnpm --filter @miniapp/backend invite:uat -- --snapshot /tmp/invite-uat.json
```

### 关键设计决策

| #   | 决策                                                                     | 原因                                                                                                                                                                                                                                              |
| --- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F1  | 脚本内强制 `DEV_AUTH_BYPASS=0`（赋值而非 delete）                        | bypass 会把"不带 header"的请求兜底成 `tg_id=99999` 的固定用户，`auth_guard` 判据永远测不到，还会往真实用户身上写邀请数据。**必须赋值**：`app.ts` 依赖链（@prisma/client）会重新加载 `.env`，而 dotenv 只填充"不存在"的变量，delete 会被填回 `'1'` |
| F2  | 拒绝在非 test 库运行                                                     | 脚本真写邀请关系、发奖明细与钱包流水，对齐 mvp-regression 的守卫                                                                                                                                                                                  |
| F3  | 专用 tg*id 段 `89xxxxxxxx` + `invite_uat*` handle 双路认领               | 脚本直插的用户带前缀 handle；由接口层 `getOrCreateDbUser` 建出来的用户 handle 是 `tg-<id>`，只能靠 tg_id 段认领。开跑前扫一遍、跑完再扫一遍，保证零残留                                                                                           |
| F4  | 脚本自带重试 fetch，不改生产客户端                                       | 本机直连 Supabase 公网端点，单次运行几百个请求，偶发 `TypeError: fetch failed` 会把断言染成假红。重试是测试脚手架的诉求，不该塞进 `lib/supabase.ts` 改线上行为                                                                                    |
| F5  | 改过 `runtime_config` 的场景各自 `finally` 还原，`run.ts` 收尾再整体核对 | config 是**共享配置**，改的瞬间同库其他人可见。双保险：未还原时脚本按失败退出（exit 1）并打印提示                                                                                                                                                 |
| F6  | 被邀请人一律走"库里还没有这行"的真实首开链路                             | 用 `rec.freshTgId()` 只占 tg_id 不建行，让 bind 请求自己触发建号——这才是深链新用户的真实时序，也是 D4 时间窗要吸收的竞态                                                                                                                          |

### 3.3 防刷并发重放（库层 + 接口层双打）

并发度 8。判据统一为：关系恰 1 行、发奖恰 1 行、`invite_reward` 流水恰 1 条、钱包增量 = 单笔金额。

| 场景                       | 实测状态分布                                                                 | 结果 |
| -------------------------- | ---------------------------------------------------------------------------- | ---- |
| `concurrency_bind_rpc`     | `bound`×1 + `already_bound`×7，无其它状态                                    | ✅   |
| `concurrency_bind_http`    | `bound`×1 + `already_bound`×7，全部 200，`source_id` 恰为 `invite`           | ✅   |
| `concurrency_grant_reward` | `duplicated`×8（绑定时已发过），bonus 零变化                                 | ✅   |
| `concurrency_ensure_code`  | 库层 8 连发只产出 1 个码；接口层 8 并发码唯一；批次后 `first_visit` 恒 false | ✅   |

> `concurrency_bind_http` 是本阶段新增的关键判据：8 个请求在**用户行尚未创建**时同时到达，
> 每个都会走 `getOrCreateDbUser`，验证了阶段一 D4「30 分钟时间窗吸收建号与绑定上报时差」的
> 设计在接口层真实并发下成立——此前只在库层验证过。

## 4. 本阶段发现并修复的问题

### 4.1 后端缺陷：非字符串 `invite_code` 导致 500（已修）

`POST /api/invite/bind` 原实现：

```ts
const inviteCode = (body.invite_code ?? '').trim();
```

请求体里 `invite_code` 是数字（或对象、布尔）时，`.trim()` 抛 `TypeError` → **HTTP 500**。

**影响面：** 前端自己发的请求不会命中（`InviteBindReporter` 送的一定是 string），
但这是一条公开的鉴权后接口，任何手工构造的请求都能稳定打出 500。属健壮性缺口而非功能缺陷。

**修复：** 抽出 `normalizeInviteCode(raw: unknown): string | null`，先判 `typeof === 'string'`
再 `trim` + 正则，非法输入统一返回 `invalid_code` 终态（HTTP 200）。

**回归防线：** 新增 `packages/backend/src/routes/invite.test.ts`（16 例），覆盖 7 种非法字符串
与 6 种非字符串类型，断言不抛异常且返回 null。

### 4.2 用例自身的两处返工（记录以免重犯）

| 问题                                                      | 根因                                                                                                                                     | 处置                                                            |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `auth_guard` 首轮全部返回 200                             | `delete process.env.DEV_AUTH_BYPASS` 无效：`app.ts` 依赖链的 @prisma/client 会重新加载 `.env`，dotenv 只填充"不存在"的变量，删掉即被填回 | 改为赋值 `= '0'`（见 F1）                                       |
| `stats_latency` 用绝对毫秒 / 分位数比值判定，连续两轮误报 | 本机到 Supabase 走公网，绝对延迟主要由 RTT 决定。链路劣化时同一份代码 p50 从 1.1s 涨到 11s、p95 到 79s，判据测的是网络不是查询           | 改判"两条同构路由的**最快样本之差**"，RTT 在相减时抵消（见 §5） |

## 5. 数据中心口径核对与实时查询结论

### 5.1 口径逐条对齐（`stats_alignment` / `stats_truncation`）

| 字段                   | 口径                                              | 核对方式                                               | 结果 |
| ---------------------- | ------------------------------------------------- | ------------------------------------------------------ | ---- |
| `invited_count`        | `invite_relations` count（按邀请人）              | 造 3 个下级后与库内 count 逐值比对                     | ✅   |
| `total_reward_credits` | `invite_reward_logs` sum                          | 含"一个下级多笔奖励"的场景（人数 1、明细 13）          | ✅   |
| `recent_rewards`       | 时间倒序，截断 10 条                              | 逐条比对 credits 与 rule_key 序列；13 条时下发恰 10 条 | ✅   |
| 账务三方对齐           | 钱包 bonus 增量 = `invite_reward` 流水和 = 明细和 | 每个发奖场景都断言                                     | ✅   |
| `update_mode`          | 本期恒 `realtime`                                 | 空数据与有数据两态均断言                               | ✅   |

空数据态（无下级）返回 0 / 0 / 空列表，不报错。

### 5.2 实时查询：维持实时方案，**不启动**批量快照预案

判据设计为「`/api/invite/stats`（count + 聚合）与 `/api/invite/entry-status`（单行读）两条
同构路由的最快样本之差」。两者都是"鉴权 + 两个并行 Supabase 查询"的形状，相减即聚合本身的
额外开销，公网 RTT 被抵消。

实测（16 样本/组，交替测量）：

```
baseline_min_ms: 535    stats_min_ms: 539    aggregation_overhead_ms: 3
baseline_p50_ms: 727    stats_p50_ms: 579
```

聚合额外开销 **3ms**（另一轮为 0ms），远低于 500ms 阈值。`idx_invite_relations_inviter` 与
`idx_invite_reward_inviter` 两个索引生效，当前量级实时聚合无压力。

**结论：按方案 §6 维持实时方案，批量快照预案（06:00/12:00/19:00/24:00）继续只作文档化预案，不实施。**

> ⚠️ 这只证明"聚合没有数量级开销"。**真实用户侧延迟必须在部署环境测**（Railway 与 Supabase
> 同区，无公网绕行），归入阶段四上线后观测。本机测得的 500ms+ 绝对值全是公网 RTT，不代表线上。

### 5.3 admin 侧查询口径

`admin.list_invite_records` 的正常路径需要 admin 用户 JWT（函数体内 `can_access_environment`
依赖 `auth.uid()`），service_role 与脚本都拿不到，**其筛选/分页口径已在阶段二任务一的
dry-run 中逐项验过**（uuid/tg_id 双匹配、granted/none 筛选、分页 total_count、时间窗、
非法状态 22023），本阶段不重复。

本阶段补验的是它的**鉴权防线**：以 service_role 调用 → `42501 admin is not permitted to
access current environment`，确认无 `auth.uid()` 即无权，RLS 与函数内鉴权双层生效。
`anon` 无 EXECUTE 权限由 106 迁移尾部自检 DO 块保证。
