# 降复杂度重构实施方案

> 2026-09-10 立项。宗旨：只偿还已经在收利息的技术债，其余地方允许脏乱差。
> 背景数据：近 3 个月 779 个提交中 257 个含 fix/revert（33%）；三个方向均有近月高频改动/hotfix 佐证。

## 优先级总览

| 优先级 | 方向             | 一句话目标                                         | 预估   |
| ------ | ---------------- | -------------------------------------------------- | ------ |
| P1     | 数据库迁移账本   | 迁移是否已执行从"人记"变成"库里可查"，编号根治撞号 | 1–2 天 |
| P2     | LLM 计费结算收口 | 扣费判定与拼装只有一份实现，settle/sync-job 共用   | 2–3 天 |
| P3     | 聊天页编排拆分   | 加消息类型/改生成行为只动一个 hook，不动 page      | 3–5 天 |

刻意不做：cs-platform 巨石收拾、Prisma/supabase-js 双栈统一、奖励发放统一层（未到 4 次重复线）、任何"通用框架"。

## P1 迁移账本与编号治理

**痛点**：`packages/shared/migrations/` 无 applied 记录，靠人记哪个文件在哪个库跑过；编号撞号是惯犯（021…095 历史撞号，100 号立规后 105/108/109 又各撞一对）；存在 Management API 直改生产的第二通道（110 的注释是活证据）；"不要在生产跑 104"这类规则只在人脑和文档里。

**改动**：

1. 新迁移 `20260910_schema_migrations_ledger.sql`：建 `app_core.schema_migrations(filename PK, applied_at, applied_by, checksum)`。
2. `.github/workflows/db-migrate.yml`：执行前查账本，已记录则拒绝重跑（可加 `force` 入参绕过）；执行成功后写入账本。
3. **编号规则切换**：新迁移一律 `YYYYMMDD_描述.sql`（日期戳 + 语义名），并行分支天然不撞号。存量文件不改名。
4. CI 检查（并入 `scripts/check-legacy-references.mjs` 或独立脚本）：迁移目录出现旧式纯数字编号新文件、或重名 → CI 报错。
5. `migrations/README.md` 更新规则，明确"改库只有仓库迁移一条路，Management API 直改列为禁手"。

**验收**：test/生产各跑一次新流程；重复触发同一文件被 workflow 拒绝。

**回填策略**：账本只对新迁移生效；存量迁移不回填（历史已无法精确对账，不为它花时间）。

## P2 LLM 计费结算收口

**痛点**：`features/generation/settle.ts`（即时结算）与 `sync-job.ts`（30s 回捞）平行实现了同一套「finish_reason 闸门 → 扣费参数拼装 → reply_outcome 标签」；闸门语义另散落在 `execute.ts#isBillableReply`、`billing/usage-pricing.ts#resolveUsageBillingGate`。改一处漏一处 = 漏扣/多扣/明细说谎，8–9 月已多次 hotfix。

**改动**：

1. 新文件 `features/generation/apply-charge.ts`：单一入口 `applyLlmCharge(decision)`，包含闸门判定 → charge 参数拼装 → `chargeLlmUsage` 调用 → 免费额度收口 → 计费列回写。
2. `settle.ts` 退化为：等 OpenRouter 元数据 → 组 decision → 调 `applyLlmCharge`。
3. `sync-job.ts` 退化为：回捞 pending 行 → 补元数据 → 组 decision → 调同一个 `applyLlmCharge`（对账分支 `reconcileLlmUsage` 保留）。
4. 闸门判定（billable 与否、reply_outcome 归类）收进一个函数，`execute.ts` / `usage-pricing.ts` 引用它而非各自维护。
5. legacy guard 加规则：`apply-charge.ts` 之外禁止调用 `chargeLlmUsage`。

**不动**：语音计费 `features/voice/billing.ts`（有意设计的平行链路）；RPC 层。

**验收**：`pnpm --filter @miniapp/backend mvp:regression` 全绿（含计费对拍）；`execute.test.ts` 等单测通过。

## P3 聊天页编排拆分

**痛点**：`app/chat/[characterId]/page.tsx` 667 行、11 useState + 3 useRef + 8 路 React Query，是全仓最热业务文件（月 19 次改动）；语音/图片/文本选项的后续需求全落在这。另「余额不足 → 跳充值」复制了 4 份且错误码不统一（`insufficient_balance` vs `INSUFFICIENT_CREDITS`）。

**改动**：

1. `hooks/use-chat-session.ts`：会话创建、URL `?session=` 同步、失效重建（`creatingRef` 语义收进来）。
2. `hooks/use-conversation-turn.ts`：`runTurn`（发消息/重生成/abort）、流式临时态与落库消息合并、卡顿计时、失败分流（402/流内 error）。
3. `lib/recharge-redirect.ts`：统一 `redirectToRecharge({ returnTo, requiredCredits? })`；四个调用点（聊天页 SSE、聊天页语音、自定义台词页 `voice/[messageId]`、`chat-model-switcher`）全部改调它；错误码判定统一成一个谓词函数。
4. page 只做接线与布局，目标 < 300 行。
5. 顺手删死代码：`stores/ui-store.ts`（零引用）、`font-scale-store` 半死链路、`chat-splash.tsx` 的 `/tavern/` 兜底。

**不做**：不引入新状态库；不做消息类型插件化。

**验收**：`pnpm --filter @miniapp/frontend typecheck` + 现有测试通过；手动回归发消息/重生成/断流/余额不足/语音生成五条路径。

## 执行纪律

- 三个方向各自独立 PR，互不依赖，可分开 review 与回滚。
- 行为不变是底线：P2/P3 是纯重构，任何口径变化都算 bug。
- 每项完成后同步更新 `docs/ARCHITECTURE.md` 对应小节（§7.4 迁移、§4.5 结算、§7.1 前端）。
