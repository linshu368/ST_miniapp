当前代码库结构（monorepo）
本项目使用 pnpm workspace monorepo，包结构：
miniapp-monorepo/
├── packages/
│ ├── frontend/ ← Next.js 前端,部署到 Vercel
│ │ ├── app/ ← 页面
│ │ ├── components/ ← 组件
│ │ ├── lib/mock-data.ts ← mock 数据集中处
│ │ └── lib/api/ ← 真实 API service 层(开发维护)
│ ├── backend/ ← Node 后端,部署到 Railway
│ └── shared/ ← 前后端共享代码
│ └── types/ ← TypeScript 类型,前后端 API 契约
├── pnpm-workspace.yaml
└── package.json
核心纪律

- PM 只改 packages/frontend/，不碰 backend 和 shared
- 旧功能在 frontend 中使用真实 API（通过 lib/api/ service 层）
- 新功能在 frontend 中使用 mock 数据（集中在 lib/mock-data.ts）
- mock 数据的类型应引用自 packages/shared/types/，这样真实 API 接入时类型自动对齐
- 真实 API 接入时，开发只需把 mock 的来源替换为 API 调用，不动类型、不动组件结构

🚦0️⃣ 合并路径判断

判断规则
第一层：monorepo 边界检查（任一为“是”即无条件必须走开发 review，且跳过其他检查）

- 是否修改了 packages/backend/ 下的任何文件？

- 是否修改了现有组件的 props 接口？
- 是否修改了路由配置？
- 是否新增了 package.json 的 dependencies？
  第三层：允许项确认（如前两层全部通过，确认是否命中允许项）

🟥1️⃣ 审查清单
仅当判定为“必须走开发 review”时输出此节。PM 自合并时跳过。
这是判断本次提交是否为合格交付物的关键。每一项必须给出明确判断。
审查项 1：Mock 隔离（三包检查）
检查目标

- 新功能的 mock 数据是否完全收口在 packages/frontend/lib/mock-data.ts 中
- packages/shared/ 下不应包含 mock 数据（只能有类型定义和纯工具函数）
- packages/backend/ 下不应包含 mock 数据
- mock 数据不应硬编码在前端组件内部、页面文件或其他非 mock-data.ts 的位置
- mock 数据不应混入真实 API 的调用路径（lib/api/ 或 fetch 层）
  判断逻辑
  mock 数据和真实 API 路径必须物理隔离，跨包边界的 mock 泄漏尤其严重。后端开发接入数据时应该只需要把 mock-data.ts 的数据源替换为真实接口，不动其他部分。
  三包边界违规的标记级别
- mock 数据进入 shared：必须修
- mock 数据进入 backend：必须修
- mock 数据硬编码在组件或页面里：必须修
- mock 数据混入 lib/api/ 路径：必须修
  额外标注：Mock 数据改动类型
  如果本次涉及 mock 数据改动，明确标注：
- 仅值改动（文案、URL、标签、数值）
- 包含结构改动（新增字段、删字段、改类型）
- 无 mock 数据改动
  如包含结构改动，列出具体变化：
- 新增字段：fieldName（类型：string，含义：xxx）
- 删除字段：fieldName
- 类型变更：fieldName（number → string）

例外情况：

1. USE_MOCK 环境变量切换模式属于有意设计，不列为 mock泄露，归为正常改动。

---

审查项 2：代码结构
检查目标

- 组件职责是否清晰，有没有一个组件承担过多职责
- props 和 state 的设计是否合理，数据流方向是否清晰
- 开发在接入真实数据时，有没有明显的结构障碍（比如数据逻辑和渲染逻辑强耦合，导致无法单独替换数据源）
  判断逻辑

  不要求完美，早期团队对技术栈保持缓和态度。结构判断的标准只有一个：后端开发接入数据时，这段代码是否会给他制造比较大的阻力。

  量化指标

- 单个组件文件是否超过 300 行
- 单个组件的 useState 数量是否超过 5 个
- 是否存在深度超过 4 层的条件嵌套
- 是否存在重复出现 4 次以上的内联样式或字符串常量

审查项 3：旧功能变更罗列
检查目标
扫描 diff 中所有涉及旧功能的改动，完整罗列，不做有意/误动的判断，由 PM 自行决定这些改动是否符合预期。
输出格式
逐条列出，每条包含：

- 文件路径
- 改动内容简述
- 类型：前端交互层 / 前端接口调用层 / 公共模块
  如果本次 diff 中没有任何旧功能改动，直接输出“无”。
  级别
  本项固定为信息项，不参与整体结论的阻塞判断，由 PM 自行核对。

---

审查项 4：类型契约一致性
检查目标

- 新功能涉及的 mock 数据，其类型是否引用自 packages/shared/types/ 下的类型定义？
- 如果 PM 在 mock-data.ts 里本地定义了新的 interface，该类型是否应该被迁移到 shared？
- 如果前端代码引用了 packages/shared/types/ 中尚不存在的类型，需要开发先在 shared 里定义
  判断逻辑
  shared 里的类型是前后端 API 契约。mock 数据作为契约的前端实现，应该引用 shared 的类型，而非自己本地定义一份。这样真实 API 接入时类型自动对齐，不会出现“mock 和真实数据字段对不上”的返工。
  判断是否应该迁移到 shared 的启发式
- 类型包含 id、name 等数据实体字段（代表一个业务对象，如 Character、Message、User）→ 应该在 shared
- 类型只包含 UI 状态或展示用字段（如 isExpanded、hoveredIndex）→ 留在 frontend 本地即可
  级别标记
- 前端引用了 shared 中不存在的类型：必须修（需开发先在 shared 定义）
- 本地定义了应该在 shared 的类型：建议（提示迁移，不阻塞合并）
- mock 数据类型引用已正确来自 shared：无需标注

🟦3️⃣ 开发视角（核心交付物）
仅当判定为“必须走开发 review”时输出此节。PM 自合并时跳过。
这是本文档最重要的部分。目标是让后端开发在不需要和 PM 额外沟通的情况下，完整理解这次功能的意图、数据结构和接入方式，并能顺利完成后续开发。尽可能详细，消除一切模糊地带。

1. 功能意图与产品逻辑
   说明 PM 在做什么、为什么这样设计。不是描述代码，是描述功能背后的产品逻辑和用户行为路径。让后端开发理解“这个功能对用户意味着什么”，而不只是“这段代码做了什么”。
   如果功能涉及业务规则（比如积分扣减、用户分层、体验次数判断），明确说明规则逻辑，不要让后端开发自己从代码里反推。功能意图的描述应该和产品背景文档里的术语对齐。
2. Mock 数据结构说明
   以 TypeScript interface 形式输出，直接可复制到 packages/shared/types/ 的类型定义中：
   // 本次新功能涉及的 mock 数据类型
   interface ExampleType {
   id: string; // 字段含义
   name: string; // 字段含义
   isLocked: boolean; // true 时展示锁定徽章,禁用卡片点击
   creditCost: number; // 0 表示免费
   tags: string[]; // 空数组表示无标签,UI 隐藏标签区域
   }
   额外说明

- 该类型目前位置（shared 中已存在 / 前端本地定义 / 尚未定义）
- 边界值和特殊状态（空数组、null、0 值对应什么用户状态）
- 哪些字段会影响 UI 渲染分支，影响什么

3. 数据接入清单（三包联动）
   开发接入真实数据需要在三个包里联动操作，逐一列出：
   【shared 包】

- 当前类型定义位置：packages/shared/types/xxx.ts（如已存在，给出路径；如不存在，说明需要新建）
- 需要新增或修改的类型：...
- 前端 mock 是否已引用该类型：是 / 否（如否，建议本次接入时顺手迁移）
  【backend 包】
- 需要新增或修改的 API endpoint：METHOD /api/xxx
- 返回值类型：应匹配 shared 中的 XxxType
- 涉及的业务逻辑提示（PM 在 mock 中体现出的规则）：积分扣减 / 用户鉴权 / 权限判断 / ...
  【frontend 包】
- 当前 mock 数据来源：packages/frontend/lib/mock-data.ts 的具体变量名或函数名
- 替换后：改为调用 packages/frontend/lib/api/xxxService.ts 的 fetchXxx 函数
- 数据流向：fetchXxx → useXxx hook（如有） → XxxComponent 的 props → 驱动哪个渲染逻辑
  如涉及多个接入点，每个接入点独立列出，不合并描述。

4. 旧功能接口层变更提示
   如果审查项 3 中存在“前端接口调用层”类型的旧功能改动，在此处逐条引用并说明：

- 这个改动对后端开发当前的数据接入工作是否有直接影响
- 是否需要后端开发在接入新功能数据之前先确认旧接口行为是否正常
  如无，输出“无”。

5. 边界情况与潜在风险
   列出后端开发在接入真实数据时可能遇到的问题：

- 真实数据结构和 mock 数据结构可能存在的字段差异（尤其当 mock 类型未引用 shared 时）
- 异步加载时的 loading 状态和 error 状态，UI 是否已经处理
- 用户行为边界（未登录、积分不足、角色未解锁等），UI 是否覆盖
- 任何在 mock 环境下正常但真实数据可能触发异常的逻辑

6. 不需要后端开发动的部分
   明确说明哪些部分 PM 已经处理完毕，后端开发不需要介入。减少误改的概率。
